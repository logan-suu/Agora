# Commit and open an Agora PR

Read task context through `node scripts/task-status.mjs summary`, then `task <id>`, `phase <id>`, or `decisions <id...>` as needed. Do not dump the entire index or batch-load histories. Read the selected decisions’ source sections before implementation or review; summaries are navigation, not complete specifications. For recovery or gate evidence, follow the task notes into `docs/task-history/<id>.md` and linked reports; `history <id>` returns a bounded tail with explicit pagination, not complete evidence. Keep notes as a current summary (at most 800 Unicode code points); append detailed records to task history before updating the index, and run `node scripts/task-status.mjs check`. Follow [task tracking maintenance](../../../docs/task-tracking.md) for record ownership and migration rules.

Use only when the user explicitly requests delivery. Inspect the branch, worktree, diff, task status, and required documentation. Never commit feature code on `main` or `dev-1.0.0`; create or use a `{type}/{kebab-description}` branch based on `dev-1.0.0`. Preserve unrelated changes and stage exact files only.

Before creating or updating a PR, audit the full changed-file set (including untracked files) for future value. Remove task-owned temporary/debug files, duplicate source or data copies, repeated logs, superseded intermediate reports and obsolete PR drafts. Keep the minimum sufficient final validation, version/hash, security/cleanup and meaningful failure evidence; never hide failures or remove the only proof for an acceptance criterion or an unresolved issue. Raw test output belongs in Git-ignored `test-outputs/`; explicitly select evidence for `docs/reviews/`, then remove confirmed unused raw output after recording the result. Check ownership and active references before deletion, point historical references to an already-pushed immutable commit when appropriate, and summarize cleanup counts/reasons/exceptions in task history and the PR. Preserve unrelated files, active resources and user data. Do not rewrite Git history to reduce artifact size. See TEST-CLEANUP in the blueprint and task-tracking guide.

Apply [TEST-STRATEGY](../../../docs/testing-strategy.md) to the entire PR diff before delivery. Code changes require typecheck, lint, the complete unit/lightweight integration baseline, dependency-based affected regressions, applicable real-chain G5, and a sensitive-data review. Run cumulative full regression for phase exits, release candidates, major shared-foundation changes, uncertain impact, or explicit full-test requests. Reuse results only after verifying their complete relevant inputs and environment; committing or updating a PR alone does not invalidate evidence. Pure documentation/workflow text changes require consistency, index, link, and applicable validator checks; task-required spikes and acceptance remain mandatory. Record selected and omitted scope with reasons, actual coverage, failures, and evidence provenance. Stop delivery on any required failure or missing result. Existing `pnpm test` remains full; do not invent unavailable fast/affected scripts or treat targets as deadlines.

Use an English imperative commit message and English PR title/body, push the feature branch, and open the PR with base `dev-1.0.0`. For tasks with code changes, keep `in_progress` until human PR merge. For a pure non-code task already accepted and marked `done` under AGENTS.md section 8.1.2, preserve that state; do not reset it merely because its documentation is being delivered. Unaccepted deliverables cannot become done through a commit. Append full PR/gate evidence to task history, keep concise notes, and never merge the PR. Task-type rules are in [task tracking maintenance](../../../docs/task-tracking.md).
