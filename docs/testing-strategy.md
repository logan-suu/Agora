# Agora 研发测试策略

**生效日期：2026-10-02。** Leader已批准；决策来源为[项目蓝图§21 TEST-STRATEGY](项目蓝图.md#test-strategy)。本文是研发验证的执行细则，不修改产品内部TESTER的累计产物验证、D16终审或阶段出口标准。

## 1. 调整依据与当前实现

12.5修复后的完整回归为339个Vitest文件、2661项测试及7项Node脚本测试，全通过，耗时19629.75秒（约5小时27分钟）。前五个慢文件约占总耗时67.2%，三条真实模型链路合计约6分20秒；瓶颈不能简单归因于模型调用。证据见[12.5任务历史](task-history/12.5.md)。具体慢点仍需分解测量，不能把fixture开销当成已证明的产品性能问题。

本次只修订文档和工作流规则。现有`pnpm test`仍执行Node脚本测试及Vitest全量，`vitest.config.ts`的`fileParallelism: false`保持。尚未建立自动分组、依赖影响选择或证据缓存；不宣称提速已经实现。正式Eval仍为显式独立入口，不混入默认回归。

## 2. 验证层级与门禁

| 层级 | 覆盖 | 执行时机与结论 |
| --- | --- | --- |
| 快速基础 | 全仓类型/lint、全部单元测试、已分类的轻量集成及研发脚本测试 | 代码PR的基础证据；开发小步先跑直接相关测试，交付前补齐基础层。单个目标通过不能宣称基础层全部通过 |
| 受影响回归 | 变更模块、传递依赖的消费者、跨包/跨阶段数据流、历史缺陷与失败路径 | 每个代码PR及修复后按完整差异选择；不能只按改动文件名或当前Phase筛选 |
| 真实链路G5 | 适用的真实Harness、MCP、文件、进程、Git、授权、恢复与模型链路 | 相关执行能力变化或任务明确要求时必做；可由前两层的真实案例提供证据，但不能用test double代替 |
| 累计全量 | 当前及此前已实现的全部适用单元、集成、跨阶段与真实模型回归，加静态检查和任务专项验证 | 阶段出口、发布候选、重大共享基础变更、影响范围不能证明或用户明确要求全量时执行 |

同一案例可同时满足多个层级，无需重复执行。快速基础约2分钟、普通PR受影响回归约5–15分钟是优化目标，不是当前承诺、超时上限或截断覆盖的理由。慢单元测试仍属于全部单元覆盖，不能因耗时被改名排除。轻量集成的归类依据真实资源、隔离性与覆盖职责；未分类项目必须先审查，不能默认为无关。

纯文档、任务记录或工作流文字变更：验证规格一致性、索引/依赖、来源链接和适用文档/Skill校验器；不为此启动运行时或付费回归。若同时改动可执行代码、测试、构建/执行脚本、被程序消费的配置，按代码变更选择门禁。任务自身要求的协议Spike、真实验收或阶段出口不受此例外影响。

G3/G4/G5须分别记录适用性。G4的结论写为“受影响范围通过”或“累计全量通过”，附范围与证据；纯文档写“运行时G4不适用”。选择范围内的失败、意外过滤、跳过或缺失均阻断相应门禁。耗时或资源不足时记录未完成，不能改写为通过。

## 3. 影响选择与升级

每轮执行前保存短验证计划，包含比较基线、候选提交及未提交差异、变更类别、依赖/消费者分析、预期测试文件清单、适用G5与全量触发判断。PR检查覆盖整个PR差异；修复重跑覆盖新修复及其依赖，其他证据只能按§4复用。

| 改动 | 必须扩展的范围 |
| --- | --- |
| State、reducer、schema、共享接口 | 序列化/回放、所有消费者、并发与幂等、跨阶段兼容 |
| 调度、WorkerRuntime、队列 | 容量/公平性、取消、暂停与收敛、失败后独立任务继续 |
| 授权、沙箱、文件入口、原生helper | 真实正反例、越界/凭据隔离、漂移、固定输入、接管、依赖此边界的执行链路 |
| 持久化、恢复、D4/D9/D16 | 崩溃窗口、重放、lineage、陈旧回执拒绝、终审及恢复的真实链路 |
| 局部UI或业务逻辑 | 直接单元、实际消费者与交互/接口集成；涉及公共契约时继续沿依赖扩展 |
| 锁文件、工具链、测试框架/发现配置、公共fixture | 所有依赖该输入的测试和构建；无法可靠限定时全量 |

改变共享身份、不变量、持久格式、权限边界或跨模块调度语义属于重大共享基础变更，必须全量。上述模块的局部修复也必须扩展覆盖；只有能明确证明未改变公共语义且依赖闭包完整时，才可采用受影响回归。无法说明某个既有案例为何无关，就不能仅以慢为由移出本轮计划；影响分析不可靠时回退全量。

当前过渡期可人工列明文件清单，用现有Vitest定向入口执行，并核对实际收集范围。全部单元/轻量集成基线也须有可审阅清单，不能以“还没有分组脚本”为由只跑少量目标。需要Node研发脚本覆盖时使用既有`pnpm test:task-tracking`。不要把参数盲目追加到`pnpm test`包装器后宣称定向成功；检查真正执行命令。无法建立完整分类与影响清单时使用原全量入口。

## 4. 证据复用与失效

开发、提交、评审复用同一有效结果，避免在无输入变化时重复重跑。证据至少包含：

- 来源提交/工作树差异和完整输入清单/hash；覆盖相关生产代码、传递依赖、测试、fixture、配置、锁文件及实际原生helper二进制。
- 实际命令、测试文件和用例范围、失败/跳过/缺失统计、退出结果、时长与必要日志/hash。
- 相关系统/架构、Node/包管理器/工具版本、隔离与权限条件；真实模型的提供方/模型及配置身份，禁止保存凭据正文。
- 清理结果、未完成项和已有失败，复用时对当前输入与原结果的逐项核对。

只写“同一HEAD”不够：未提交改动、二进制重建、环境变化也可能失效。任一覆盖输入变化、证据丢失、相关新失败或未解释漂移使相应证据失效；不能证明失效范围时扩大至全量。纯文档文字或交付记录变化可保留已证明不受影响的运行时结果，但必须明确原测试版本和当前差异。

阶段出口与发布候选需要绑定候选的完整累计证据。允许复用同一候选、相同输入与环境下已完成的完整全量结果；不能将仅受影响回归或无关旧全量拼称为出口全量。候选相关输入变化后，重新执行完整累计回归。发布重建产物仍按TEST-CLEANUP与发布协议重验必要证据。

## 5. 失败、真实依赖与清理

保留R11：禁止弱化断言或mock绕过真实代码。修复先确认生产、测试或环境根因；不得为缩时移除应执行用例、skip、延长/缩短期限规避失败或静默换提供方。当前通用真实测试按已批准规则使用OpenCode Go的`deepseek-v4-flash`，缺凭据或失败报错；官方专项及历史证据保留。真实模型用例仍属于累计全量，定向计划中所有受影响模型链路照常执行。

首失败停止可减少无效等待，但剩余计划记未完成；修复后补齐失效与未执行范围。运行中的Harness仍自然到安全点收敛，不因研发效率要求硬杀token流。按[任务追踪规范](task-tracking.md)留证和TEST-CLEANUP清理，不删除唯一失败/验收证据或用户数据。

## 6. 后续实现顺序

本轮不改测试脚本或配置，后续实现按代码任务流程推进：

1. 生成可审阅的测试分类/依赖清单及耗时分布，验证所有既有案例都有归属，未知归类默认全量。
2. 建立快速、受影响、真实链路和全量入口及输入证据核验，保留`pnpm test`的明确全量语义，验证选择器不会漏测。
3. 分解最慢的fixture准备、文件/Git事务、helper调用与实际验证开销；仅合并无状态污染的重复准备，保留独立断言、故障路径与真实边界。
4. 证明目录、端口、凭据作用域、资源配额和清理互不干扰后，才为可隔离测试启用有界并行；共享宿主资源的测试继续串行。优化前后用相同覆盖对照耗时与结果。

不得以这一实施清单宣称工具已存在、测试已经提速或阶段已验收。
