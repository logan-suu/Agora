## 实施中复评：识别、基线与停服接缝

- 原“授权后有限识别、不全仓预扫描”与“首次写入前展示已有修改基线”需区分语义分析和文件保全。语义识别仍只读有限声明；受信LocalVersionStore按既有4096条目/256MiB总量/16MiB单文件限制保全可操作文件，秘密和控制目录排除，基线不送模型。inspectionRef绑定实际基线，开始前变化要求刷新并再次确认，不能把仅绑定grant的回执当作内容确认。
- 独立连接检查也是执行中的Harness请求。最小停服必须等待其完成及检查证明落盘，停止新配置准入，不能只等待任务worker。该接缝已补红绿测试；不取消在途token流。
- 历史关闭/官方会话证据读取与当前范围准入不能互相递归。首次入口的历史身份适配改为读取canonical TaskState和registry并核验scope，调用者继续执行原grant、根、关闭、版本和Fork证据核验。底层严格校验不因接线错误被放宽；真实活跃交还复验见任务历史。
- 停服允许裁决、拒绝新执行需区分两个结果。旧resume端口在D9裁决提交后才抛停止准入错误，让已保存裁决被展示成失败。明确退出期间保存裁决并确认applied，保留未恢复事实、不新建Fork/marker；D16完成条件不变。红绿用例覆盖收尾尚未结束时裁决/重复请求，真实本机专项另验；不把延迟恢复写成13.2已交付。
- 只读重开不能只靠普通start对旧状态的拒绝。实际离线重开后`@CODER`仍被保存，且D9恢复/解释入口未绑定本次首次准备。补当前实例scope准入，在Leader写入、解释和composition创建前分别限制；旧launch不能靠重选目录重获资格。只读显示字段为派生值，TaskState/Entry不复制它；非首次桌面宿主不注册该阶段限制。真实模型专项证明正常当次执行、停服裁决仍通过，重开指令和重选目录拒绝且状态不变。
