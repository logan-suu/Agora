## 问题与反例

| 旧文缺口或错误推论 | 具体反例 | 修正 |
| --- | --- | --- |
| 文件版本变化等同于新任务 | 同一需求已完成，用户只改了另一文件，合并候选需要复验，却被要求重新描述需求、迁移上下文 | 同需求保留taskId，显式创建新验收轮次 |
| 批准产物等同于已交付到目录 | A已批准，但文件事务失败或只应用部分文件，任务仍显示全部完成 | 产物验收、目录当前版本、实际应用分开留证；应用目标未满足不finalize |
| 必须先完成任务才能生成应用提案 | 应用被要求作为完成条件，又要求done才允许应用，形成循环 | 可执行提案绑定固定受测/受审C、当前目标和Leader应用确认，不要求task已done |
| 为等未来应用无限延迟完成 | 用户明确只要可下载产物，却因未应用一直占用工作状态 | 交付目标明确锁定，产物模式在D16及归档完成后可结束 |
| 重新验收就是重开旧worker | 旧session/lease与新权限、输入版本不一致，旧归档被替换 | 新轮次使用新dispatch/worker/Context/lease，保留不可变历史 |
| 旧批准或apply重放能够重新启动 | 刷新或重试旧请求触发新模型调用，费用与执行意图不对应 | 仅新显式revalidate动作能登记重入，同action只复核原回执 |

## 修正后的产品与控制规则

正常路径在最终审阅/终审前尽量纳入当前用户修改，形成固定C。C不同于A必须重新验证；不同文件的无冲突合并也不能推导整体已通过。无法自动确定的文本冲突保持显式，不擅自拼接。

同需求后续复验保留taskId，新的roundId由受信控制面登记。当前状态与当前完成资格随新轮次更新，历史通过事实不改写。新worker从C及结构化需求/既有证据开始；不复活done/failed worker，不复制原始聊天，不为了复验重跑整套需求规划。

本机开发默认交付到所选目录，用户可明确选只要产物；目标属于需求及控制指纹，不能在应用失败后由Agent改写。D16批准与文件应用确认分别校验，同一C的必要事实全部闭合才允许finalize。用户目录的后续外部变化不改写“当时C通过”，但会使旧应用资格失效。

显式控制动作、严格请求结构、当前授权/目标/index核验、旧run/claim收尾、幂等重放、累计限制与不可变分轮归档详见[详设§12.2.5.1](../详细设计方案.md#local-delivery-lifecycle-124)。D19旧引擎只读边界保持；项目/根/需求或授权范围改变时走相应正常准入，不能用复验扩权。新的执行仍可能产生模型费用，产品必须在该动作中说明并取得执行意图。

不采用“所有新版本都另建任务”：它把存储/终态限制转嫁给用户。不采用“所有任务永久等待未来应用”：它使明确的产物交付无法结束。新任务仍适用于独立业务目标或用户明确选择，不被禁止。
