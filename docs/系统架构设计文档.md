## 1. 架构概述与设计哲学

### 1.1 架构定位
Agora 是一套**以人为中心的多智能体编排系统**。它不是单一的程序，而是一个**“可插拔的虚拟软件公司内核”**。

### 1.2 核心设计哲学（4 大支柱）
1. **上下文即工程（Context as Code）**：不依赖模型的“长上下文”记忆，而是通过显式的**投影（Projection）**在运行时构建 Agent 的认知边界。
2. **最终一致性（Eventual Consistency）**：不追求分布式强一致性锁，通过**可交换的 Reducer 合并函数**容忍并行乱序写入。
3. **数据驱动编排（Data-driven Routing）**：拓扑结构不写死在代码里，而是由 `Coordinator` 根据 State 中的 `complexity` 信号动态决定。
4. **防腐层隔离（Anticorruption Layer）**：核心业务逻辑（编排/状态）与外部依赖（LLM/沙箱/工具）通过 Ports & Adapters 彻底解耦。

## 2. 分层逻辑架构（4+1 视图）

自内向外分为四层，严格遵循依赖倒置（Dependency Inversion）：

| 层级   | 名称                          | 核心职责                                                     | 禁止行为                                                     |
| :----- | :---------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **L1** | **领域模型层 (Domain)**       | 定义 State 实体、Reducer 语义、RoleSpec 接口。**纯 TypeScript 类型与纯函数**。 | 禁止引入任何 I/O 库（fs, http, child_process）。             |
| **L2** | **编排应用层 (Application)**  | 实现主循环（Orchestrator）、路由策略（Coordinator）、并发控制（Preemptor）与 ChannelLifecycleService。 | 禁止直接调用 LLM 或 Docker API，只能调用 L3 定义的端口接口。 |
| **L3** | **端口抽象层 (Ports)**        | 定义 Executor、SandboxManager、TaskStateStore、ProjectChannelStore、ProjectCollaborationStore、MessageBus 接口。定义“系统需要什么能力”。 | 不包含具体实现；MessageBus 不修改 State 或保存 inbox。                    |
| **L4** | **基础设施适配层 (Adapters)** | **具体实现**：Harness Executor、LocalTemp Sandbox、JSON TaskStateStore/ProjectCollaborationStore、ProjectChannelStore 兼容视图、MCP Client、SSE 投递适配器。 | 可以依赖第三方库（Harness, dockerode, express）。            |

## 4. 核心组件交互序列（Critical Paths）

### 4.1 标准任务执行流（无抢占）
1. **Entry**：`Orchestrator.run()` 初始化 `AppState`。
2. **路由决策**：调用 `Coordinator.decide(state)`，返回 `{ kind: 'worker', batch: [Coder] }`。
3. **执行**：`WorkerRuntime.runOne()` -> 调用 `SandboxManager.createWorktree()`（Phase 0 由 `LocalTempSandbox` 返回本地临时目录句柄）-> 实例化 `HarnessExecutor`。
4. **上下文注入（关键）**：在 Harness 的 `agent/pre-step` 钩子中，**覆写（Overwrite）** `messages` 数组为 `Projection.project(state, role)` 的返回值。
5. **写回**：Executor 返回 `StepResult.mutations` -> `applyMutations(state, mutations)`（Reducer 合并）。
6. **循环**：回到步骤 2，检查 `testResults`，若失败则路由回 Coder，成功则路由至 `finalize`。

### 4.2 配合式抢占流（Leader 中途改需求）
1. **校验与提交**：UI 发送带 `projectId/taskId/channelId` 作用域的 Leader 输入（浏览器只提交满足 `[A-Za-z0-9][A-Za-z0-9._:-]*` 的稳定 `msgId` + `display`，不自报可信意图） -> HTTP 边界先拒绝非法 msgId -> 服务端解析并构造 `Message.payload` -> Phase 6 起先从 `ProjectChannelStore` 校验 Channel 存在、sub 任务绑定、participant 资格与未关闭 -> 应用服务在同任务串行区内把唯一主消息与本阶段有效的非消息动作 mutations 交给一次 `TaskStateStore.commit()` -> reducer 原子写入并持久化 State。planned message 的动作 mutations 禁止追加 `messages`；多消息路径统一走逐条校验与投递的批量服务。校验失败时不写 State、不发布事件。
2. **投递**：提交成功且非幂等重放 -> `MessageBus.publish(MessageCommitted)`；SSE 适配器只推不含 `payload` 的展示信封。角色 inbox 每次从持久 Channel 注册表 + 任务 State 派生，MessageBus 事件可用于唤醒消费者，但不得成为另一份 inbox 存储。
3. **全局中断信号（Phase 9）**：`Preemptor.requestPause()` 设置全局 `paused = true`；Phase 8 回合制单 worker 不广播抢占，只在已到达的 `step/end` 边界进入 gate。
4. **安全点（Phase 9 多 worker）**：各 Worker 的 Harness Loop 在 `agent/turn-stopping` 检测到标志，**在当前 Step 结束时**暂停；每个 `safePointRef` 必须指向已 flush 的持久 source session 与已闭合 turn boundary，仅有进程内 sessionId 不算 checkpoint。
5. **D4 suspend（Phase 8）**：gate 生产者只返回瞬态请求；生命周期服务先 flush Harness session JSONL，全部成功后才在同任务串行区一次持久化完整 `{gateId,reason,options,phase,openedTs,safePointRefs}`，不得写入缺 checkpoint 的半成品 gate。随后销毁进程内 executable composition/Harness context 与可重建运行资源，使 run 进入 `needs_attention`。冻结的 `SandboxManager.teardown()` 会移动 worktree，暂停时不得调用；组合根改用不改变基接口的 `RecoverableSandboxManager.suspend()` companion capability，仅停止容器而保留 host root，恢复时以 `resume(taskId,bindings)` 校验并重新挂载 State 中的原 worktree。TaskState、worktree 与 session 必须保留，不做终态产物归档；不支持该恢复能力的 Sandbox fail-closed。Phase 8 释放本地运行容量，Phase 9 才向 GlobalScheduler 交还槽位。
6. **D4 resolve + resume（Phase 8）**：Leader 经 `POST /api/messages` 以稳定 `msgId=actionId` 提交绑定 `gateId` 的 `/resolve-gate <gateId> <option> [argument]`；同一 Task State commit 追加含 `{gateId,option,argument?,safePointRefs,resumeSessionId}` resolution receipt 的规范裁决消息、应用 reason-specific mutations 并清除活动 gate，child id 从 actionId 确定性派生。然后从该 receipt + 持久 State/worktree 新建 composition：child 不存在时在全新 Harness context 中 load source、截取 boundary 前缀，经 `ctx.agents.create({sessionId:resumeSessionId,seed,meta:{parentSession,seedLength},...})` 原子创建；已存在时严格复核 lineage 后由 `ctx.agents.resume()` 接管。暂存 D1 最新投影并提交稳定 `human-gate-resumed:<actionId>` 控制消息后才继续；此前 run 保持 `needs_attention`。直接 `ctx.sessions.fork()` 因只创建 live Session 而不能通过公开 API 再原子绑定 Agent，不作为该流程实现。

### 4.3 Sub Channel 生命周期流（Phase 6）
1. **可信入口**：Leader 通过 `POST /api/messages` 提交稳定 `msgId` 与确定性 `/channel open|close` 文本；Worker 只可在最终回复末尾输出一个严格 channel-action 控制块，Harness 校验并剥离 display 后以同一步 assistant msgId 绑定 actionId，通过既有 `StepResult.output` 在 Step 安全边界交付。open 控制块可显式给安全稳定的 threadId，但浏览器/模型不得自报 actor/actionId；组合根绑定 actor，畸形控制块 fail-fast。纯控制回复保留审计 Message，并生成确定性非空 display。
2. **预校验与标准化**：Leader 入口在同任务串行区先检查持久 State 的重复 msgId，命中即在任何 Channel 副作用前返回。随后加载项目 Channel 快照，校验 actionId、task、enabled roster、topic、关闭权限；participants 作为集合标准化为 leader 在前、其余按 roster 顺序。同 `taskId+threadId` 的同语义 open 和重复 close 为 no-op，冲突语义明确失败；channelId 用 taskId 长度前缀编码消除分隔符碰撞。
3. **项目级事实提交**：`ChannelLifecycleService` 按 project 串行执行 load→校验→`ProjectChannelStore.commit(expectedRevision)`；Channel 不进入 AppState Mutation，不修改冻结端口签名。sub 持久化 `threadId/topic/createdBy`，main 永不关闭。
4. **任务消息补齐**：Channel 提交成功后，原 Leader 消息或稳定 lifecycle announce 才经 MessageService 写入 TaskStateStore 并按 D6 发布。此处是两个真相源之间的可重试 saga，不假装跨文件原子事务；消息失败不回滚 Channel，同 actionId 重试只补消息。
5. **角色上下文派生**：6.3 的 `ChannelContextBuilder` 从 `ProjectChannelSnapshot + AppState.messages + role` 读时派生上下文，按 project/task/participants default-deny；只输出不含 display 的类型白名单结构化条目。每群的 `{entries,omittedRefs,omittedRefCount}` 共用 4000 字符动态消息预算：保留较新完整 entries 后，只在剩余空间保存最近的旧 refs，并以计数显式记录全部遗漏。Channel 不持久第二份 `localContext` 消息索引。
6. **关闭后处理**：6.2 close 置 `closed=true` 并阻止后续 sub 发言；6.3 对尚无 `bubbledSummaryRef` 的 closed sub，经 L3 `ChannelSummaryGenerator` 端口复用无工具薄 Harness，从该 sub 的全部白名单结构化条目生成 `ChannelSummary`。输入按完整 entry 装箱，超大单条用带 ref/序号的结构化 fragment；chunk 只可引用本块来源，中间输出有界，并在每次输入不超过 4000 字符的前提下多轮批次归并。以稳定 `channel-bubble:<channelId>` 先经 D6 写入 main，再以 revision CAS 只保存 MessageRef。main 消息是唯一摘要内容真相；恢复时先复用该消息再补引用，reconcile 返回前重新加载规范 State。Phase 8 才实现 thread 的 humanGate 裁决与 resume。
7. **发现与切换**：`GET /api/channels?projectId&taskId` 从持久 Channel 快照按字段白名单派生唯一 main + 当前 task sub 的展示元数据，不返回 `bubbledSummaryRef` 指向的内容或消息 payload。UI 初始化与动作完成时刷新一次，仅在 active run 持续短轮询；Channel 刷新错误独立呈现并在恢复后清除。选中群后复用既有 channel-scoped SSE/POST；不新增 Channel 事件总线或进程内列表真相。

### 4.4 Trace 只读派生流（Phase 8 / D15）
1. Web `GET /api/traces` 先经 `TaskStateStore.load(scope)` 验证任务存在与安全 scope，再调用 L3 `TraceReader`；Trace 不参与任务 mutation、MessageBus 或 Channel SSE。
2. L4 `HarnessTraceReader` 通过锁定版本官方 JSONL persistence 的 `list()/inspect()` 读取已校验 session header/events，不直接解析后端物理文件，也不持久第二份 trace。
3. 读侧按 `agentPreset` 绑定角色，以 `parentSession/seedLength` 校验 lineage；child 仅投影 seed 边界之后的 native 事件，父历史不重复。
4. DTO 只白名单投影 turn/step/tool 的身份、时间、状态、工具名与错误码；prompt、projection、assistant/reasoning 内容及工具 arguments/results 全部丢弃。响应有界并显式报告 `omittedEventCount`。
5. UI 在现有右侧栏按 role/session→turn→step→tool 展示；运行中短轮询，终态最终刷新。日志损坏、lineage 不一致或查询越界独立报错并 fail-closed，不以静态示例替代。

## 5. 数据一致性模型（并发控制）

### 5.1 Reducer 语义（State 写入）
由于多个 Worker 并行执行，State 更新必须满足**交换律（Commutative）**和**幂等性（Idempotent）**。

- **Append-only 字段**（`messages`, `objections`）：按身份键（`msgId`/`id`）去重追加，无身份键值深相等兜底（集合并语义）；时间戳排序留给读侧投影，乱序不影响最终事实追加。`Objection` 不原地修改 resolution status，未决视图从异议事实与规范 Leader 裁决消息派生；同一个异议的结构化事实与同 id 可见 Message 必须在一次 Task State commit 中原子追加。
- **D14 快照升级**：L4 `JsonTaskStateStore` 读取缺少 `objections` 的旧任务快照时补为 `[]`，使 D4 重启恢复可安全进入 Coordinator；已存在的非数组值视为损坏并 fail-fast。已持久的同 id 异议重放按不可变事实先判幂等，不因其 target 后续被 supersede 而失败。
- **[2026-09-04 架构决策更新] D14 裁决一致性**：objection resolution 是同一 Task State commit 内的规范 Leader 消息 + 确定性 `authority='leader'` resolution Decision + 可选 target effect。blocking accept decision-target 以 `supersedes` 撤回当前 Decision；blocking accept requirement-target 以 `withdrawnByDecisionId` 撤回 Requirement；reject 与 advisory 裁决不改变 target。`deriveObjectionResolutions()` 读时交叉验证三类事实，重复/缺失/漂移 fail-closed；`activeRequirements()` 排除已由规范 resolution Decision 撤回的 Requirement，旧快照缺字段视为 active。Decision 的 supersedes 只允许指向 current 项，阻止历史分叉。blocking 使用绑定 gate 的 `/resolve-gate` 并在清 gate 后走 D4 resume；advisory 使用 `/resolve-objection` 直接裁决。两者的非空自由文本 rationale 只作持久内容，不参与 ID/路径/命令；重放必须复核 resolution Decision 与 target effect。`project()` 向所有角色注入已验证的结构化 `objectionResolutions` 系统切片，不投 Leader display/raw log，保证 resume 后的实际执行者获得裁决事实。
- **Merge-by-ID 字段**（`workers`, `subtasks`）：按 `id` 进行深度合并（`Object.assign`），非 Owner 字段（如其他 Worker 的状态）不受影响。
- **Set 字段**（`phase`, `testResults`）：采用**最后写入者获胜（Last-Write-Wins）**。由 Coordinator 编排确保同一时刻只有一个 Worker 能输出此类覆盖型 Mutation。

### 5.2 文件系统一致性
- **真相源分离**：State 只存 `fileRefs`（路径+行号），文件实际内容存在于 Sandbox 的 Worktree/Temp 目录中。
- **读时拉取**：Agent 需要代码内容时，通过 `fs.read()` MCP 工具**实时拉取**，绝不依赖 State 中的缓存副本，防止版本漂移。

### 5.3 Channel 跨存储一致性
- **不持久派生索引**：Channel 注册表只保存生命周期、participants、任务绑定与可选 `bubbledSummaryRef`；inbox/ChannelContext 均从注册表 + Task State 读时重建，避免每条 sub 消息跨两个 JSON 文件双写。
- **摘要唯一真相**：结构化 `channel_summary` main 消息是摘要内容的唯一事实；Channel 只保存 `{taskId,msgId}` 引用，不复制字符串。
- **message-first/ref-second saga**：稳定 msgId 先经 TaskStateStore first-write-stays 提交，再经 ProjectChannelStore revision CAS 补引用。崩溃、投递失败或 revision 冲突后必须重新读取规范消息并有限重试，不得重新覆盖摘要或伪造跨文件事务。
- **恢复触发**：close 成功后与任务运行时恢复入口都运行 closed-without-ref reconciliation；不得依赖进程内 Map、常驻扫描器或活 Harness 才能发现未完成冒泡。

### 5.4 项目 roster 与 Channel 一致性（D12）

- **单一项目协作快照**：`ProjectCollaborationSnapshot={projectId,revision,roster,channels}` 是 roster 与 Channel 的共同持久真相；`AppState`、进程内 `DEFAULT_ROSTER` 与独立 `channels.json` 都不得成为第二份运行事实。
- **定义/成员分离**：`RoleSpec` 描述能力，`RosterEntry.status` 描述 `enabled | disabled | departing | departed` 生命周期；可选 `departure` 保存稳定 action/task、接任者、阶段与 handoffRef。所有普通路由、执行、agent 发言和新建 sub 都只接受 enabled；departing 只允许离职服务完成受限 drain，其中已登记活动 handle 的当前在途 Step 可经 role-bound 接缝提交 mutations 后保存安全点，但不得启动新 Step、执行额外 Channel 副作用或借此恢复普通发言；持久 roster 是必需权威源，缺失时 fail-closed。
- **原子成员变更**：add/enable/disable/depart 的每一步都在同一个项目串行区重算 main participants，并以一次 revision CAS 提交 roster+channels。离职跨任务 State 时使用 `departing CAS → step/end drain → TaskStateStore 幂等交接/责任 commit → departed CAS` 的可恢复 saga，不声称跨文件原子；重放入口先以持久 departure 阶段判断是否续办，再处理已有 Leader Message，内部 handoff id 冲突或交接/责任事实不完整时 fail-closed。既有 `ProjectChannelStore` 仅作为兼容视图，公开签名不变。
- **孤儿职责阻断**：存在未完成 subtask 且没有 enabled 接任者时，Task State 写入 handoff/humanGate 并把原 subtask 标 blocked，roster 保持 `departing/awaiting_replacement`；升级人工不等于责任已经转移，禁止进入 departed。只有职责全部完成或已转移后才能 `departed/completed`。
- **历史可读**：sub participants/createdBy 校验“项目已知身份”而不是“当前 enabled”；非 enabled 历史成员不能发送新消息或启动 worker，但其旧消息、关闭群和冒泡摘要仍可恢复。
- **迁移 fail-fast**：`channels.json → collaboration.json` 只做一次确定性迁移；正式快照写入后必须从正式路径重新读取并核对，再删除 legacy。两文件并存仅在 Channel 内容等价时由 initialize/load 幂等完成恢复清理，否则拒绝启动，禁止默认覆盖或长期双写。
- **任务接手不跨存储（D13）**：项目 `addRole` 只提交 collaboration；任务 `/role onboard` 只读取最新 enabled roster，并在单个 Task State commit 中提交符合 D9 安全 token 语法的稳定 Leader 主消息、`nextRole` 与规范离职 handoff Message 引用，不包装成跨 collaboration/Task State 事务。`onboardingContext` 从持久 Task State 的 applied onboarding 事实读时派生，不依赖进程内 Map、Channel 裁剪窗口或活 Harness；引用事实不完整、跨任务或重复认领时 fail-closed。同 ID applied 重放返回前重新校验既存主消息、完整 receipt 与当前 State 引用事实，不能把损坏数据当作幂等成功。onboard 提交与 Worker 消费之间若 roster 失效，使用既有 `required_role_unavailable:<role>` humanGate 收敛。

## 6. 错误处理与韧性（Resilience）

| 异常场景                           | 处理策略                                                     |
| :--------------------------------- | :----------------------------------------------------------- |
| **Harness LLM 调用超时/限流**      | 复用 Harness 的 `agent/request-error` 扩展点，执行 `{ kind: 'retry' }`，采用指数退避（Exponential Backoff）。 |
| **沙箱测试无限循环（死循环）**     | SandboxManager 强制设置 `timeout`（默认 30s），超时则杀死子进程，返回失败测试结果。 |
| **编排死循环（Agent 反复改不对）** | `iterationCount` 硬上限（默认 8），超限后 Coordinator 强制置 `humanGate`，升级给人。 |
| **humanGate checkpoint/fork 失败** | 任一 session 未 flush 时不得提交完整 gate；boundary 未闭合、作用域不匹配、source 缺失或 fork 失败均 fail-closed，run 保持 `needs_attention`。裁决前由 active gate、裁决后由 canonical resolution receipt 保存 checkpoint refs，同 actionId 可从事实断点重试。 |
| **humanGate suspend/resolve 竞态** | gate 可见后 resolve 可以耐久提交，但 resume 必须等待旧 run 的 suspend 收尾完成并重读 State；不得因旧注册项仍为 `running` 丢弃恢复。gate 已提交后的释放失败保持 `needs_attention` 且禁止终态归档。 |
| **恢复资源或身份校验失败** | composition 重建失败释放本次已取得的全部资源；既有 child 同时校验 header 与 source seed 事件前缀；sandbox worktree 必须属于当前 task 的规范 root，跨 task 引用 fail-closed。 |
| **知识库写入污染（决策 3）**       | 阶段 0 至阶段 N（直至另行启用）全量禁用写入（Write-Block）。未来启用时，仅在 `phase === 'done'` + `testResults.passed === true` 且收到 `/approve-kb` 命令时才执行蒸馏。 |
| **进程崩溃（Worker 意外退出）**    | `WorkerRuntime` 捕获 `unhandledRejection`，将对应 `WorkerState.status` 置为 `'failed'`，Coordinator 在下一轮路由检测到失败后，自动重试或升级人。 |

## 7. 扩展点设计（未来演进）

架构天然支持以下扩展，无需重构核心层：

1. **新角色（Role）**：在 `packages/roles/definitions/` 增加 `RoleSpec` 模板或由 Leader 提交自定义 spec，再作为 `RosterEntry` 写入项目协作快照。Phase 7 的通用 worker 可由 Leader 显式指派任意 enabled 角色；Coordinator 的默认自动拓扑仍只覆盖六个已定角色，任意自定义角色自主调度按 DEF-016 延期，禁止把“可装载”误写成“已自动路由”。
2. **新执行器（Executor）**：实现 `Executor` 接口（`step`, `saveSafePoint`, `injectInbox`）。例如 Phase 10 的 `OpenHandsExecutor` 只需放在 L4 适配层。
3. **新沙箱环境（Sandbox）**：实现 `SandboxManager` 接口（`createWorktree`, `run`, `read`, `write`）。例如将 `LocalTempSandbox` 替换为 `ECSSandbox`（AWS）或 `Firecracker`，编排层零感知。
4. **新工具（Tool）**：基于 MCP SDK 编写新的 Server，在 `RoleSpec.tools` 白名单中注册即可。

### 7.1 工程 Eval 扩展点（D11）

Eval 位于生产系统边界之外，通过 adapter 驱动公开任务或 Agora fixture，调用既有组合根并从评测专用持久 State、Harness 事件、工具结果和产物派生 `EvalResult`。依赖方向固定为 `eval adapter → L3 端口/生产组合根`，L1/L2 禁止 import 任何 SWE-bench、Terminal-Bench/Harbor 或 Eval runner 类型。每次运行拥有 `.data/evals/<runId>/` 独立 data root/workspace；生产组合根只在该边界内写评测 State，不能接触用户项目 `.data/projects/` 或 KB。

```text
版本化公开 Benchmark / Agora fixtures
              ↓ adapter
 AgoraEvalTask + canonical fingerprint
              ↓
隔离 run root → 生产组合根 → Harness/MCP/Docker/State/MessageBus
              ↓
 State + Trace + Patch + 资源指标
              ↓
Outcome / Process / Efficiency / Safety Graders
              ↓
结构化 checks + EvalResult + artifact hashes
```

结果正确性与过程正确性分开：公开 Benchmark 的测试/补丁 Grader 只能证明最终任务结果，Agora 自定义 Process Grader 负责验证角色投影、Channel/Leader 权威、安全点、交接和并行一致性。每个 Grader check 必须给出 `pass | fail | unknown`、说明和证据引用；缺失指标不可伪造，`pass` 只能从本次 run 的实际 State/trace/工具结果或明确分类错误派生。Runner 先保存 provisional 结果，再执行注册清理并原子定稿 final 结果；只有 final、无 failure、全部 Outcome/Process/Safety 通过且无已知 Efficiency 超限的结果可计为通过。`maxIterations` 对应实际编排轮次，不等同返工次数。实际执行与审计元数据共用冻结模型/环境配置；driver/schema/eval root 不合法均 fail-fast。Eval 运行失败可以留下隔离的评测 State/结果用于诊断，但不得修改用户产品 State 或触发知识库写入。deterministic 与真实 model profile 分开运行、分开汇总；结果与测试门禁分离，Benchmark 不能替代阶段集成测试/G5。

## 8. 架构权衡与取舍（Trade-offs）

> *这是面试官最看重的内容，体现工程务实精神。*

| 追求目标             | 做出的取舍                                                   |
| :------------------- | :----------------------------------------------------------- |
| **可控性 vs 性能**   | 为了 Leader 能随时裁决（可控），我们接受 **“秒级”** 的抢占延迟（等待安全点），而不做硬中断（会导致状态撕裂）。 |
| **简单性 vs 健壮性** | Phase 0 使用 **本地临时目录 Mock 沙箱**，舍弃 Docker 隔离。我们优先验证“逻辑正确性”，牺牲“环境安全性”，用快速迭代换取可行性。 |
| **成本 vs 效果**     | 严格限制并行度为 3，且规划/评审用强推理模型（贵）、编码用代码模型（便宜），通过**模型路由**做成本优化，而非无脑堆叠 Agent。 |
| **隔离 vs 复用**     | 项目间采用**默认 deny 导入（快照副本）**，舍弃了实时共享的便利性，换来了绝对的上下文隔离，防止“祖传代码污染新项目”。 |
| **公共可比性 vs 产品针对性** | 复用成熟 Coding Agent Benchmark 的任务/环境/Outcome Grader以获得外部可比性，同时自建小规模 Agora 协作语义 Grader；不为公共榜单反向定制生产 Agent。 |

## 9. 部署视图（Deployment View）

- **Phase 0**：单 Node.js 进程内运行 Harness context/Worker，State 存储在内存中；进程内 session 隔离不等于子进程隔离。
- **Phase 5–9**：增加 Next.js 前端；单实例自托管后端将任务 State 以 `.data/projects/{projectId}/tasks/{taskId}/state.json` 原子快照持久化。Phase 8/D4 起 Harness session 由锁定版本的 JSONL persistence plugin 写入 `.data/projects/{projectId}/tasks/{taskId}/harness-sessions/`，持久 header + 完整事件序列；`safePointRef` 引用其 source session 与已闭合 boundary，不再使用含义含混的单一 `events.jsonl`占位路径。D15 Trace 从同一规范 session root 读时派生白名单 DTO，不复制日志、不进入 MessageBus，运行中只在单实例边界内有界轮询。Phase 6 先以 `channels.json` 落 `Project.channels`；Phase 7/D12 确认 roster 与 main participants 不可跨文件短暂失配，迁移为 `.data/projects/{projectId}/collaboration.json` 的统一 `ProjectCollaborationSnapshot`。任务 State 与项目协作快照分别按 task/project 串行并原子替换；损坏、不变量失败或新旧快照冲突均 fail-fast。SQLite 只在需要复杂查询时作为可选迁移。Vercel 只承载前端，后端仍自托管。
- **Phase 10+**：若需将后端部署到 Serverless 或水平扩展，必须先将 `TaskStateStore` 与 `ProjectCollaborationStore`（包括 `ProjectChannelStore` 视图）都切换为外部耐久实现，并用跨实例事件传输取代进程内订阅；是否引入 Redis/托管数据库由部署任务根据实际需求裁决，不预置为必选依赖。
- **生产建议**：将 Sandbox 适配器切换为独立 Docker 容器，通过网络（REST/MCP）与主进程通信，彻底隔离文件系统。
