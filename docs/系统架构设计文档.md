## 1. 架构概述与设计哲学

### 1.1 架构定位
Agora 是一套**以人为中心的多智能体编排系统**。它不是单一的程序，而是一个**“可插拔的虚拟软件公司内核”**。

### 1.2 核心设计哲学（4 大支柱）
1. **上下文即工程（Context as Code）**：不依赖模型的“长上下文”记忆，而是通过显式的**投影（Projection）**在运行时构建 Agent 的认知边界。
2. **最终一致性（Eventual Consistency）**：不追求分布式强一致性锁，通过**可交换的 Reducer 合并函数**容忍并行乱序写入。
3. **数据驱动编排（Data-driven Routing）**：拓扑结构不写死在代码里，而是由 `Coordinator` 根据 State 中的 `complexity` 信号动态决定。
4. **防腐层隔离（Anticorruption Layer）**：核心业务逻辑（编排/状态）与外部依赖（LLM/沙箱/工具）通过 Ports & Adapters 彻底解耦。

## 2. 分层逻辑架构（4+1 视图）

自内向外分为四层，严格遵循依赖倒置（Dependency Inversion）：

| 层级   | 名称                          | 核心职责                                                     | 禁止行为                                                     |
| :----- | :---------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **L1** | **领域模型层 (Domain)**       | 定义 State 实体、Reducer 语义、RoleSpec 接口。**纯 TypeScript 类型与纯函数**。 | 禁止引入任何 I/O 库（fs, http, child_process）。             |
| **L2** | **编排应用层 (Application)**  | 实现主循环（Orchestrator）、路由策略（Coordinator）、并发控制（Preemptor）。 | 禁止直接调用 LLM 或 Docker API，只能调用 L3 定义的端口接口。 |
| **L3** | **端口抽象层 (Ports)**        | 定义 Executor、SandboxManager、TaskStateStore、MessageBus 接口。定义“系统需要什么能力”。 | 不包含具体实现；MessageBus 不修改 State。                    |
| **L4** | **基础设施适配层 (Adapters)** | **具体实现**：Harness Executor、LocalTemp Sandbox、JSON TaskStateStore、MCP Client、SSE 投递适配器。 | 可以依赖第三方库（Harness, dockerode, express）。            |

## 3. 物理模块结构（Monorepo 映射）

代码仓库 `packages/` 目录严格对应上述逻辑层级：

```text
packages/
├── core/                     # [L1 + L2] 核心不可变内核
│   ├── domain/               # State, Reducer, Entity (无副作用)
│   ├── orchestration/        # 主循环, Coordinator 路由
│   └── preemption/           # 配合式抢占信号控制
│
├── runtime/                  # [L3 + L4 混合] 执行与隔离
│   ├── executor/             # HarnessExecutor, ExternalExecutor (抽象+适配)
│   ├── sandbox/              # SandboxManager, LocalTempSandbox (适配)
│   └── state/                # TaskStateStore 端口 + JSON 快照适配器
│
├── comm/                     # [L3 + L4] 通信总线
│   ├── bus/                  # MessageBus 接口 (Port：只投递已提交事件)
│   └── channels/             # 项目级 Channel/Inbox 读模型与路由 Adapter
│
├── tools/                    # [L4] MCP 工具服务器 (独立进程/适配)
│   ├── fs-server/
│   ├── test-server/
│   └── ...
│
├── roles/                    # [L1 数据] 角色定义 (YAML/TS 配置)
│   └── definitions/
│
└── shared/                   # 类型与常量
```

## 4. 核心组件交互序列（Critical Paths）

### 4.1 标准任务执行流（无抢占）
1. **Entry**：`Orchestrator.run()` 初始化 `AppState`。
2. **路由决策**：调用 `Coordinator.decide(state)`，返回 `{ kind: 'worker', batch: [Coder] }`。
3. **执行**：`WorkerRuntime.runOne()` -> 调用 `SandboxManager.createWorktree()`（Phase 0 由 `LocalTempSandbox` 返回本地临时目录句柄）-> 实例化 `HarnessExecutor`。
4. **上下文注入（关键）**：在 Harness 的 `agent/pre-step` 钩子中，**覆写（Overwrite）** `messages` 数组为 `Projection.project(state, role)` 的返回值。
5. **写回**：Executor 返回 `StepResult.mutations` -> `applyMutations(state, mutations)`（Reducer 合并）。
6. **循环**：回到步骤 2，检查 `testResults`，若失败则路由回 Coder，成功则路由至 `finalize`。

### 4.2 配合式抢占流（Leader 中途改需求）
1. **提交**：UI 发送带 `projectId/taskId` 作用域的 Leader 输入（浏览器只提交稳定 `msgId` + `display`，不自报可信意图） -> 服务端解析并构造 `Message.payload` -> 应用服务在同任务串行区内把消息与本阶段有效动作 mutations 交给一次 `TaskStateStore.commit()` -> reducer 原子写入并持久化 State。
2. **投递**：提交成功且非幂等重放 -> `MessageBus.publish(MessageCommitted)`；SSE 适配器只推不含 `payload` 的展示信封，角色 inbox 由 Channel 读模型按 participants 派生。
3. **中断信号**：`Preemptor.requestPause()` 设置全局 `paused = true`。
4. **安全点**：各 Worker 的 Harness Loop 在 `agent/turn-stopping` 检测到标志，**在当前 Step 结束时**暂停并存储 `safePoint`（事件流游标）。
5. **资源释放（决策 4，仅进入 humanGate 时）**：调用 `worker.terminate()` **销毁子进程**（释放并发槽位）；非阻塞抢占（无 blocking 异议）**不销毁进程**，直接进入步骤 6。
6. **恢复**：Leader 裁决后 -> `Preemptor.applyAndResume()` -> 基于 `safePoint` 重新 `fork` 子进程 -> `inbox.inject` 新上下文 -> 继续。

> **[2026-08-31 架构决策更新] D9 阶段边界：** 上述步骤 3–6 是 Phase 9 的完整配合式抢占流，不是 Phase 5 的既有能力。Phase 5 的 Leader 输入统一经 `POST /api/messages`，只执行经校验的开头单一 `@ROLE` 定向激活（消息 + `nextRole` 在一次提交中落盘）与普通 chat；Coordinator 只消费最新 applied assignment 一次，追加 `sourceMsgId` 确认事件并经 Coordination Ledger 把 instruction 投给目标角色。其余意图显式 `rejected/deferred`。独立 `POST /api/commands` 临时投递不得绕过 State。

> **[2026-09-01 架构决策更新] D10 Web→编排桥接：** 新任务创建/启动是组合根的生命周期入口，不是 D9 的任务内消息旁路。单实例运行注册表按 `projectId/taskId` 保存任务摘要，但 Phase 5 全实例最多一个活动 run；另一 scope 已运行时返回容量冲突，避免 GlobalScheduler/Phase 9 并行能力抢跑。组合根复用既有 `runOrchestration()`、HarnessExecutor、沙箱与 L3 端口。编排安全边界产出的 State/消息必须先由 TaskStateStore 持久化，再发布 MessageCommitted→SSE；Web 层不得直接写 State，也不得用静态种子消息补画面。终态产物先归档到任务耐久目录并写回引用，再释放 Harness/MCP/Git/Docker 资源；最终 State/消息/产物支持刷新恢复而不依赖活容器。活动 run 的进程重启自动恢复不在 Phase 5 范围，但中断后不得误报 active。

## 5. 数据一致性模型（并发控制）

### 5.1 Reducer 语义（State 写入）
由于多个 Worker 并行执行，State 更新必须满足**交换律（Commutative）**和**幂等性（Idempotent）**。

- **Append-only 字段**（`messages`, `objections`）：按身份键（`msgId`/`id`）去重追加，无身份键值深相等兜底（集合并语义）；时间戳排序留给读侧投影，乱序不影响最终事实追加。
- **Merge-by-ID 字段**（`workers`, `subtasks`）：按 `id` 进行深度合并（`Object.assign`），非 Owner 字段（如其他 Worker 的状态）不受影响。
- **Set 字段**（`phase`, `testResults`）：采用**最后写入者获胜（Last-Write-Wins）**。由 Coordinator 编排确保同一时刻只有一个 Worker 能输出此类覆盖型 Mutation。

### 5.2 文件系统一致性
- **真相源分离**：State 只存 `fileRefs`（路径+行号），文件实际内容存在于 Sandbox 的 Worktree/Temp 目录中。
- **读时拉取**：Agent 需要代码内容时，通过 `fs.read()` MCP 工具**实时拉取**，绝不依赖 State 中的缓存副本，防止版本漂移。

## 6. 错误处理与韧性（Resilience）

| 异常场景                           | 处理策略                                                     |
| :--------------------------------- | :----------------------------------------------------------- |
| **Harness LLM 调用超时/限流**      | 复用 Harness 的 `agent/request-error` 扩展点，执行 `{ kind: 'retry' }`，采用指数退避（Exponential Backoff）。 |
| **沙箱测试无限循环（死循环）**     | SandboxManager 强制设置 `timeout`（默认 30s），超时则杀死子进程，返回失败测试结果。 |
| **编排死循环（Agent 反复改不对）** | `iterationCount` 硬上限（默认 8），超限后 Coordinator 强制置 `humanGate`，升级给人。 |
| **知识库写入污染（决策 3）**       | 阶段 0 至阶段 N（直至另行启用）全量禁用写入（Write-Block）。未来启用时，仅在 `phase === 'done'` + `testResults.passed === true` 且收到 `/approve-kb` 命令时才执行蒸馏。 |
| **进程崩溃（Worker 意外退出）**    | `WorkerRuntime` 捕获 `unhandledRejection`，将对应 `WorkerState.status` 置为 `'failed'`，Coordinator 在下一轮路由检测到失败后，自动重试或升级人。 |

## 7. 扩展点设计（未来演进）

架构天然支持以下扩展，无需重构核心层：

1. **新角色（Role）**：只需在 `packages/roles/definitions/` 新增 `YAML` 文件，定义 `systemPrompt` 和 `tools`。`Coordinator` 读取 `roster` 后即可路由（微内核特性）。
2. **新执行器（Executor）**：实现 `Executor` 接口（`step`, `saveSafePoint`, `injectInbox`）。例如 Phase 10 的 `OpenHandsExecutor` 只需放在 L4 适配层。
3. **新沙箱环境（Sandbox）**：实现 `SandboxManager` 接口（`createWorktree`, `run`, `read`, `write`）。例如将 `LocalTempSandbox` 替换为 `ECSSandbox`（AWS）或 `Firecracker`，编排层零感知。
4. **新工具（Tool）**：基于 MCP SDK 编写新的 Server，在 `RoleSpec.tools` 白名单中注册即可。

## 8. 架构权衡与取舍（Trade-offs）

> *这是面试官最看重的内容，体现工程务实精神。*

| 追求目标             | 做出的取舍                                                   |
| :------------------- | :----------------------------------------------------------- |
| **可控性 vs 性能**   | 为了 Leader 能随时裁决（可控），我们接受 **“秒级”** 的抢占延迟（等待安全点），而不做硬中断（会导致状态撕裂）。 |
| **简单性 vs 健壮性** | Phase 0 使用 **本地临时目录 Mock 沙箱**，舍弃 Docker 隔离。我们优先验证“逻辑正确性”，牺牲“环境安全性”，用快速迭代换取可行性。 |
| **成本 vs 效果**     | 严格限制并行度为 3，且规划/评审用强推理模型（贵）、编码用代码模型（便宜），通过**模型路由**做成本优化，而非无脑堆叠 Agent。 |
| **隔离 vs 复用**     | 项目间采用**默认 deny 导入（快照副本）**，舍弃了实时共享的便利性，换来了绝对的上下文隔离，防止“祖传代码污染新项目”。 |

## 9. 部署视图（Deployment View）

- **Phase 0**：单 Node.js 进程运行所有 Worker（Harness 子进程隔离），State 存储在内存中。
- **Phase 5–9**：增加 Next.js 前端；单实例自托管后端将任务 State 以 `.data/projects/{projectId}/tasks/{taskId}/state.json` 原子快照持久化，Harness 事件继续写 `events.jsonl`。SQLite 只在需要复杂查询时作为可选迁移，不是 Phase 5 门禁。Vercel 只承载前端，后端仍自托管。
- **Phase 10+**：若需将后端部署到 Serverless 或水平扩展，必须先将 `TaskStateStore` 切换为外部耐久实现，并用跨实例事件传输取代进程内订阅；是否引入 Redis/托管数据库由部署任务根据实际需求裁决，不预置为必选依赖。
- **生产建议**：将 Sandbox 适配器切换为独立 Docker 容器，通过网络（REST/MCP）与主进程通信，彻底隔离文件系统。
