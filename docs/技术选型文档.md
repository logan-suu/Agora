## 2. 语言与运行时

### 2.1 TypeScript (5.9+)

**选型理由**：

1. **全栈统一**：前后端 + Agent 运行时统一使用 TypeScript，减少上下文切换成本，类型定义可在全栈共享。
2. **类型安全**：State Schema、MCP 工具接口、RoleSpec 等核心数据结构均可获得完整的类型推导和编译时校验。
3. **生态成熟**：所有核心依赖（Harness、MCP SDK、Next.js）均为 TypeScript 原生或提供一流支持。
4. **单人项目友好**：统一的工具链（格式化、Lint、测试）降低维护成本。

**约束**：
- 启用 `strict: true`
- 启用 `moduleResolution: "bundler"` 或 `"node16"`
- 启用 `esModuleInterop: true`

### 2.2 Node.js (24 LTS host)

**选型理由**：

1. **Harness 持久化要求**：Phase 8 锁定的 `@deepseek-ai/dsh-session-persistence-jsonl` `0.1.1-rc.2` 在包入口直接导入 Node 原生 Zstandard API；Node 22.14/20 无法加载，Node 24.19 实测可用，因此宿主基线必须为 Node 24+。
2. **长期支持**：Node 24 为当前 LTS 基线；`package.json#engines` fail-fast 要求 `>=24`。
3. **原生 Fetch/WebStream/Zstandard**：宿主同时满足 MCP 流式传输与 Harness JSONL 默认 checksummed Zstandard frames。Docker 中执行用户产出仍固定 `node:20-slim`，不把宿主升级扩散为用户代码运行时变更。

> **[2026-09-03 实装记录] 任务 8.1：** `packages/runtime/executor` 已直接声明并接入 `@deepseek-ai/dsh-session-persistence-jsonl@0.1.1-rc.2`，生产组合根按项目/任务建立 session 根目录；Node 24.19 下的集成测试已真实执行 flush、cold load、lineage child create/resume。当前受限环境无法联网重跑 pnpm 9 安装，依赖声明与 lockfile 已同步，测试使用仓库现有 pnpm store 中同一锁定版本。
4. **事件循环适配并发模型**：Node 的事件循环 + Promise 天然适配"多 Worker 各自长跑、到边界让出"的并发形态。


## 3. 包管理器与 Monorepo

### 3.1 pnpm (9.x) + Workspaces

**选型理由**：

1. **磁盘效率**：pnpm 使用硬链接和符号链接，在 monorepo 下能极大节省磁盘空间并加快安装速度。
2. **严格依赖管理**：pnpm 的依赖提升策略更严格，能有效避免"幽灵依赖"，确保项目结构清晰。
3. **Monorepo 原生支持**：`pnpm-workspace.yaml` 提供一流的 monorepo 支持。
4. **Catalog 特性**：pnpm 9.x 的 catalog 特性可统一管理 TypeScript 等关键依赖的版本。

## 4. 单 Agent 内核

### 4.1 DeepSeek Harness (v0.1, MIT)

**[2026-09-09 选型同步] 10.3 用户逐 Agent 模型配置：** Harness 是统一执行内核，不限制用户只能使用 DeepSeek 模型。用户在界面配置 OpenAI 兼容服务的 Base URL、API Key 和模型名，支持逐 Agent 设置及一次应用到当前项目全部 Agent；优先复用锁定 Harness 官方模型适配器，不自研 agent loop，不把外部模型 API 等同于外部编码 Agent。已按 Leader 批准计划声明 `@deepseek-ai/dsh-llm-pi-ai@0.1.1-rc.2` 与 `@deepseek-ai/dsh-credentials@0.1.1-rc.2` 直接依赖，复用同一锁定版本。Web 另声明前者并列入 Next.js serverExternalPackages，避免 pi-ai 动态模块导入被打包器破坏。仅使用公开 plugin/CredentialProvider API；Chat Completions + SSE + function tools，配置默认 context=32768/maxTokens=4096。凭据 AES-256-GCM、task 不可变绑定与请求传输边界见详细设计 §3；实测证据见 docs/evals/phase10-model-settings-evidence.md。

**选型理由**：

1. **官方开源，活跃维护**：DeepSeek 于 2026-08-13 正式开源 Harness (DSH) v0.1 开发者预览版，以 MIT 协议开源。
2. **插件化架构**：Harness 的核心理念是"Everything is a plugin"——模型适配器、工具注册、Session Log、甚至 Agent Loop 本身都是可替换的插件。这与 Agora 的微内核架构高度契合。
3. **四个扩展点精确映射**：
   - `agent/pre-step` → 投影注入 / 覆写消息队列
   - `agent/request` → 模型路由
   - `agent/turn-stopping` → 配合式抢占落点
   - `agent/request-error` → 失败重试
4. **事件溯源会话日志**：天然支持 checkpoint、fork、resume、replay，是配合式抢占的基础设施。
5. **`ctx.agents` / `ctx.subagents` 边界**：`ctx.agents.create()` + `followup()`/`whenIdle()` 可由 HarnessExecutor 映射为受控 turn 边界，并已接入 JSONL checkpoint/Fork；`ctx.subagents.start()` 的锁定 spawn provider 是 one-shot，只适合 worker 内边界清晰的一次性委派，不作为 Phase 9 顶层长跑 worker 构造器。
6. **`ctx.compaction`**：内置单 Agent 历史压缩引擎，省去自研。
7. **TypeScript 原生**：整个 Harness 是大型 TypeScript 代码库。
8. **社区活跃**：发布后在 GitHub 上星数迅速增长。

**约束**：
- 当前为 Developer Preview 阶段，后续迭代中可能出现破坏兼容性的修改。
- **[2026-09-08 选型同步] D2：** 所有阶段、所有角色统一使用基于 DeepSeek Harness 的自研 Agent/HarnessExecutor，取消外部编码 Agent 与薄/厚切换路线。复用 Harness 的 loop、事件溯源、官方 JSONL persistence、inbox 与压缩；自研角色、投影、轻编排及并发/抢占控制。旧 `external`/`externalCmd` 仅是兼容字段，不代表外部命令可执行；本次文档同步不修改源码。D11 外部 Benchmark adapter 仅适配任务、环境与 Outcome Grader，不接管产品 Agent 执行。

> **[2026-09-03 选型同步] D4 Harness 会话持久化：** Harness core `SessionStore` 本身是进程内事件源，仅有 `sessionId` 不能在 context dispose 后恢复。Phase 8 直接采用与 Harness 同版本的 `@deepseek-ai/dsh-session-persistence-jsonl` `0.1.1-rc.2`，不自研 session codec；它按配置 root/规范化 cwd/session id 写持久 header + append-only events。`saveSafePoint()` 必须 await `ctx.sessions.flush()` 且确认持久 listener 参与；`loadSafePoint()` 在全新 context 通过 `ctx.sessionPersistence.load()` 读取经校验的 source log，截取 completed-turn prefix，再调用 `ctx.agents.create()` 以新 sessionId、seed 和 `parentSession/seedLength` lineage 原子创建 child Agent + Session。直接 `ctx.sessions.fork()` 只创建 live child Session，公开 Agent API 不能再把它原子接入 loop，因此不选；`ctx.agents.resume()` 复用旧 sessionId，也不满足新 lineage。该引入是 D4 真恢复所需的 Harness 官方配套插件，不替代 TaskStateStore，不将原始群聊注入 agent，也不改变 D8 单实例部署边界。

> **[2026-09-05 选型同步] D17 顶层 worker 构造：** 本地锁定 `@deepseek-ai/dsh-subagent-spawn-in-process@0.1.1-rc.2` 的官方类型与 README 显示 provider 只有 one-shot `start()`、没有 continuable creation；返回契约是最终 result/dispose，不提供 Agora 所需的逐 turn 控制、D4 持久 suspend/Fork 与 canonical step commit 接缝。因此 Phase 9 复用现有、已实测的 HarnessExecutor 工厂，为每个稳定 workerId 建独立 Context/Agent/session，再由 WorkerRuntime 并发调度；不新增库、不自研 agent loop，也不把 one-shot child 冒充可恢复 worker。

**备选方案（已排除）**：

| 框架                        | 排除理由                                                     |
| :-------------------------- | :----------------------------------------------------------- |
| **Agent Forge**             | 依赖装饰器（`experimentalDecorators`），与 Agora 的纯数据驱动角色设计理念不符；框架较重 |
| **BeeAI Framework**         | IBM 开源，Python/TS 双语言，但设计偏向企业级通用 Agent，与 Agora 的"编码协作"垂直场景匹配度低 |

| **AutoGen (Microsoft)**     | 群聊=全量历史广播、无角色投影（官方 issue #4648/#1006 自认缺陷）；人类是被动参与者、无否决权；MagenticOne 用 LLM 当 orchestrator。仅借鉴其 TerminationCondition/CodeExecutor/Ledger 模式，不引入框架（详见《框架调研与借鉴决策》） |

## 5. 编排层

### 5.1 自研轻量编排

**选型理由**：

1. **4 个通用节点**：编排拓扑极小（entry → coordinator → worker → integrate → humanGate → finalize），无需引入重量级框架。
2. **角色是数据，不是节点**：编排层不包含任何角色节点，路由由 Coordinator 数据驱动。增删角色不改代码。
3. **Harness 已提供底层能力**：事件溯源、checkpoint、inbox steering 已由 Harness 提供，编排层只需"粘合"这些能力。
4. **避免框架锁定**：自研层仅 ~500-800 行核心代码，未来替换成本极低。

**设计参考**：参考 LlamaIndex Workflows 的**轻量、事件驱动、100% 类型安全**的设计理念，但自研实现以确保完全可控。

## 7. 沙箱与隔离

### 7.1 Phase 0: LocalTempSandbox（真实临时目录）

**选型理由**（阶段 0 快速迭代策略）：

1. **零依赖**：使用 Node.js 原生 `fs.mkdtempSync` + `child_process.spawn`，无需安装 Docker。
2. **快速验证**：1 周内可跑通"状态流转 + Harness 接入 + 测试回环"完整链路。
3. **可替换性**：`SandboxManager` 接口抽象完善，Phase 1 可无缝切换至 Docker 实现，编排层零改动。

**接口定义**：

```typescript
interface SandboxManager {
  createWorktree(taskId: string, role: string): Promise<Worktree>;
  read(worktree: Worktree, path: string): Promise<string>;
  write(worktree: Worktree, path: string, content: string): Promise<void>;
  run(worktree: Worktree, cmd: string, timeout?: number): Promise<RunResult>;
  integrate(base: string, branches: string[]): Promise<IntegrationResult>;
  teardown(taskId: string): Promise<void>;
}
```

### 7.2 Phase 1+: Docker (dockerode)

> **[2026-09-08 选型同步] 安全保证范围：** 以下 Phase 1 参数是既有实现记录，不代表所有宿主 read/write/list 已抗并发路径替换。9.5 的正式入口、后台进程、目录祖先与恢复/归档矩阵见详细设计 §11.7。原生 helper/受审文件服务或静止窗口均只是待评审候选，当前没有自动批准的新依赖或安全豁免；容器执行退出、跨 worker 路径隔离和末级 no-follow 不能单独关闭 DEF-004。Node 文档说明预检查和实际文件操作之间可发生竞态；Linux 的 O_NOFOLLOW 只处理末级路径，与覆盖全部组件的解析约束不同。依据：[Node.js 文件访问说明](https://nodejs.org/docs/latest-v24.x/api/fs.html#fspromisesaccesspath-mode)、[Linux openat2 路径解析说明](https://man7.org/linux/man-pages/man2/openat2.2.html)；Linux 接口不能直接假设在 macOS 宿主或现有 Node API 中可用。

**选型理由**：

1. **生产级隔离**：每任务一容器，限网络与资源。
2. **生态成熟**：dockerode 是 Node.js 操作 Docker 的事实标准。
3. **接口隔离**：SandboxManager 保持可替换接缝；当前仅使用本地 Docker，不承诺 E2B/远程沙箱或新的虚拟化运行时。

**[2026-08-27 架构决策更新] `DockerSandbox`（阶段 1 实现类）落地参数**（`packages/runtime/sandbox/src/docker-sandbox.ts`）：

- **一任务一容器**：首次 `createWorktree(taskId, key)` 惰性创建容器，同 taskId 复用；任务 host 根目录 bind mount 至容器 `/workspace`。Phase 0–8 的顺序退化可令 key=role；Phase 9 真并行必须令 key=稳定 workerId，使同 role 多 worker 位于不同子目录。
- **Worktree.path 语义不变**：仍返回 host 绝对路径（组合根/模型零改动，R9）；`read/write` 走 host 侧 bind mount 共享文件，`run` 经 `docker exec`（`/bin/sh -c`，WorkingDir 映射容器路径）。
- **限网络与资源**（默认值，均可配置）：`NetworkMode: 'none'`（默认禁网，可选 `bridge`）；`Memory: 512MiB`（MemorySwap 同量禁 swap）；`CpuShares: 512`；`SecurityOpt: ['no-new-privileges:true']`；`Cmd: ['sleep','infinity']` 保活。
- **默认镜像**：`node:20-slim`（对齐 Node 20 LTS 运行时），可经配置替换；容器创建前检查镜像存在性，缺失自动 pull。
- **run 超时**：默认 30s（R7）；Docker API 无 `POST /exec/{id}/kill`（实测 404），改为容器内 coreutils `timeout -s KILL` 包装命令（`Cmd: ['timeout','-s','KILL',sec,'/bin/sh','-c',cmd]`，argv 数组免二次 shell 解析），超时仅杀 exec 进程组、容器存活可复用；JS 侧 timer 兜底（超时 +10s 强杀整容器，防无 coreutils 镜像挂死）。
- **integrate**：显式 not-implemented（Git 语义归 `packages/tools/git`，Phase 9 集成检查点实现），不静默。
- **teardown**：stop + remove(force) 容器，host 根目录移动至 `agora-sandbox-trash`（移动而非删除，对齐文件保护）。

**配置切换**：`packages/runtime/sandbox/src/factory.ts` 提供 `createSandbox(config)`：

```ts
SandboxConfig = { kind: 'local' } | { kind: 'docker', image?, networkMode?, memoryBytes?, cpuShares?, docker?, baseDir? }
```

默认 `{ kind: 'local' }`（Phase 0 行为不变，R9 向后兼容）；Phase 1 出口测试（1.6）用 `{ kind: 'docker' }` 验证双模式切换。

> [2026-09-01 选型同步] 宿主侧 `simple-git` 与文件 API 只负责 Git 元数据和 artifact 快照管理，不是代码执行后门。Agent 生成的源码/测试/脚本，包括从 `.data/.../artifacts/` 恢复后的独立复验，一律进入新的 DockerSandbox/等价隔离容器后再运行；验收必须检查真实 `RunResult`，不得以宿主 `node --test` 或确定性 adapter 硬编码的通过结果替代。

> **[2026-09-07 选型同步] D17 复合 workspace adapter：** Phase 1 的 `DockerSandbox` 子目录行为保留为历史退化实现；Phase 9 生产组合根不允许它与 `WorktreeGitService` 各自创建不同目录。一个复合 adapter 对外继续实现六个冻结 `SandboxManager` 方法，内部先从 `.data` 内 task-owned canonical repository 创建真实 Git linked worktree，再把**同一 host 规范路径**挂载/重挂载到 Docker。第二个字符串参数是逻辑 workerId isolation key，适配器须做确定性 Git-safe 防碰撞编码；canonical workerId 不因 Git 限制而改名。增加内部 bind-existing-worktree companion capability 不改变冻结端口。DEF-004 仍保持 open：跨 worker 独立目录不能证明同一 worktree 内宿主 fs 与并发进程间的 TOCTOU 已消失，9.5 前必须实测修复或明确后续安全边界。

**[2026-08-27 架构决策更新] 路径防护统一**：抽共享 `path-guard.ts`（`assertInside`，realpath 加固防 symlink 逃逸，含 dangling symlink 拒绝），`LocalTempSandbox` 与 `DockerSandbox` 共用，解决 DEF-001；`dirnameOf/basenameOf` 手写拆分替换为 `node:path`，解决 DEF-002。


## 8. 版本控制

### 8.1 simple-git (3.36.x)

**选型理由**：

1. **轻量**：纯 Node.js 实现，无需额外 CLI 依赖。
2. **TypeScript 支持**：原生类型定义。
3. **功能完备**：支持 clone、branch、checkout、merge、diff 等所有 Phase 0-9 所需操作。

**用途**：
- 每个稳定 `workerId` 绑定独立 git worktree/分支；同一 role 的并行 Worker 不复用目录
- 集成检查点时顺序合并分支
- 冲突检测与升级

## 9. 前端与实时通信

### 9.1 Next.js (15.x) + React (19.x)

**选型理由**：

1. **全栈同构**：与后端（Node.js + TypeScript）共享类型定义和工具函数。
2. **App Router**：Next.js 15 的 App Router 支持 Server Components 和 Streaming，适合群聊消息的实时渲染。
3. **本地运行**：Next.js 界面与状态/实时后端运行在同一台用户电脑，浏览器访问本机服务；当前不提供云端托管（D8，2026-09-09）。

### 9.2 SSE + HTTP POST（混合模式）

**选型理由**：

1. **HTTP 协议友好**：本机浏览器通过 SSE + HTTP POST 连接本机后端，无需 WebSocket 长连升级；协议选择不包含云端部署承诺。
2. **场景匹配**：群聊场景下，接收消息（服务器推送）是主要负载 → SSE；发送消息（用户发言）是低频操作 → HTTP POST。
3. **实现简单**：无需维护独立的 WebSocket 服务。

**协议设计**：
- `GET /api/stream?projectId={projectId}&taskId={taskId}&channelId={id}` → SSE 连接，接收实时展示信封
- `POST /api/messages` → Leader 发送消息或指令（含 `projectId`, `taskId`, `channelId`, 稳定 `msgId`, `display`；浏览器提交的 `msgId` 必须满足 `[A-Za-z0-9][A-Za-z0-9._:-]*`，受信任单用户边界内发送者由服务端固定为 `leader`，结构化意图与 agent `payload` 由服务端生成）
- `POST /api/tasks` → 单实例生命周期入口（含 `projectId`, `taskId`, 稳定 `requestId`, `goal`），异步启动既有编排循环；同 scope 不同 goal 返回 `409`。Phase 5–8 另一 scope 已有活动 run 时返回容量冲突；Phase 9 起允许不同 scope 并发，但 executable composition admission 满载时在重资源初始化前返回可重试 `429`
- `GET /api/tasks?projectId={projectId}&taskId={taskId}` → 读取持久化任务摘要与进程内 run 状态；进程重启后未完成快照明确返回 `interrupted`

### 11.1 Vitest (3.x)

### 11.3 工程 Eval Suite（D11）

> **[2026-09-08 选型同步] 9.5 对照增量：** 复用既有 Eval runner 与 TS/Vitest/Harness/Git/Docker，不接入 Phase 10 的外部 Benchmark 工具。用相同 D17 DAG 配合 cap=1/2/3，真实 model 主任务每组至少 3 次独立 attempt；固定源码、任务、实际模型配置、预算、镜像身份和执行顺序，失败与 provisional 尝试均留台账。新增资源/分段计时放 Eval 层 observation artifact，不改生产端口或现有 EvalResult 字段签名。单任务宽 DAG、跨项目公平及顺序依赖控制分开报告；产物目录、计时与 DEF 处置规则以详细设计 §11.7 为准。

**选型原则**：

1. **复用任务生态**：优先复用 [SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/) 的真实仓库 Issue/测试判定，以及 [Terminal-Bench/Harbor](https://github.com/harbor-framework/terminal-bench) 的容器任务格式与 Outcome Grader；不从零采集通用 Coding Benchmark，也不为排行榜定制生产 Agent。
2. **保持运行时纯 TS**：Phase 6 的统一任务 schema、运行器、四类 Grader 与结果汇总使用仓库既有 TypeScript/Node/Vitest/Docker 能力，不新增产品运行时依赖。
3. **外部适配而非侵入**：公开 Benchmark 通过独立 adapter 调用 Agora；Harbor/Python/`uv` 等只可作为 Phase 10 的可选开发评测工具，实施时必须重新核对版本、许可证、网络/镜像成本与技术选型，禁止进入 L1/L2 或默认产品部署。
4. **固定版本可审计**：记录数据集名称、release/commit、任务 ID/version/canonical fingerprint、runner/adapter 版本、模型 provider/model/参数、预算、环境指纹与 attempt；公开数据不复制入仓库，原始运行产物默认 gitignored。
5. **四维结果与 fail-closed**：Outcome（测试/补丁）、Process（协作不变量）、Efficiency（token/费用/时延/调用/编排轮次与返工）、Safety（沙箱/权限/泄漏/回收）。统一 check 状态为 `pass | fail | unknown` 并附证据引用；Outcome/Process/Safety 未观测不得通过，Efficiency 缺失才可显式 `unknown`。`maxIterations` 对应编排轮次，不混同返工。LLM-as-judge 只补充主观 rubric，确定性结果仍用测试和结构化不变量。
6. **隔离、生命周期与 profile**：每次运行使用经真实路径校验的 `.data/evals/<runId>/` 独立 data root/workspace，允许生产组合根写评测专用 State，但禁止访问用户 `.data/projects/` 与 KB。结果按 provisional→清理→final 两阶段原子留档，只有 final 可计入通过。Phase 6 同一任务目录提供分开汇总的 deterministic（脚本化 adapter）与 model（真实 provider）profile；前者不算模型能力，后者不承诺逐字节确定。
7. **配置与驱动同源**：实际模型/环境实例和结果元数据由同一冻结配置构造；禁止未记录环境覆写。任务 schema 必须完整运行时校验，未映射 driver 与缺凭据的专用 model 命令明确失败，不静默 skip 或回退。

Phase 6 先以 8–12 个小型内部版本化任务打通 Eval 基础设施；保持运行时纯 TypeScript，不新增产品依赖，指标通过 Eval wrapper/observer 和既有 trace 采集，无法可靠取得时写 `unknown`。Phase 10 再接公开 Benchmark 的小型固定子集并做重复对照。Eval 允许统计波动，不替代 Vitest、阶段出口集成测试和 G5 真实执行链路。
