## 0. 结论摘要（TL;DR）

Agora **不需要改用 AutoGen 或 AgentScope**，也不需要引入它们的编排层。但应**借鉴 8 个经过生产验证的模式**，并明确拒绝两者的共通弱点。本项目五大支柱（群聊单一原语、人类唯一权威、角色投影、配合式抢占、薄执行器）恰好是对这两个框架最弱层的正确否定。

| 框架 | 调研版本/提交 | 一句话结论 |
|---|---|---|
| **AutoGen (Microsoft)** | v0.7.5 @ `027ecf0a` | 群聊=全量广播无投影；人类无否决权；LLM 当 orchestrator。但 TerminationCondition / CodeExecutor / MagenticOne Ledger 值得借鉴 |
| **AgentScope (Alibaba)** | v0.1.7 `8775375a` / v1.0.9 `a0009548` / v2.0.7 `b2d60cc` | MsgHub 扁平广播、**v2.0 已删除**；定位非编码编排。但 reply/observe、写所有权不变量、interrupt() 值得借鉴 |

## 1. AutoGen 调研（Microsoft，v0.4+ / AgentChat / MagenticOne 时代）

源码基线：`microsoft/autogen` @ `027ecf0a379bcc1d09956d46d12d44a3ad9cee14`（main，v0.7.5，2026-08）。

> 版本注：独立 `autogen-magentic-one` 包已废弃，MagenticOne 迁入 `autogen-agentchat` 的 `MagenticOneGroupChat`。

### 1.1 群聊架构：全量历史广播（无投影）—— 拒绝

每个参与者被包装成 `ChatAgentContainer`，其 `_message_buffer` **累积全部广播消息**，被选中发言时把**整个缓冲**传给 agent：

```python
# python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_chat_agent_container.py L130-137
async for msg in self._agent.on_messages_stream(self._message_buffer, ctx.cancellation_token):
    ...
```

管理器 `BaseGroupChatManager` 同样持有全量 `_message_thread`；`SelectorGroupChat` 的 LLM 选发言人默认用 `UnboundedChatCompletionContext` 吃全量历史。**官方承认缺陷**：

- [issue #4648 "Chat History Reduction"](https://github.com/microsoft/autogen/issues/4648)：*"long running group chats can consume a significant number of tokens"*
- [issue #1006](https://github.com/microsoft/autogen/issues/1006)、[PR #6330](https://github.com/microsoft/autogen/pull/6330)：社区多次请求群聊内 summarization，官方未实现

缓解仅限 per-agent `model_context`（`Buffered` / `HeadAndTail` / `TokenLimited` 四种视图）——但只作用于 LLM prompt 层，消息投递层仍全量。**概念可借鉴（→ 角色投影），机制不可照搬。**

**Agora 对照**：支柱 2"角色投影、永不投原始群聊 log"正是对此模式的正面否定。

### 1.2 人类是被动参与者（无否决权）—— 拒绝

`UserProxyAgent` 是普通 `ChatAgent`，只在被选为发言人时阻塞读取用户输入；**协议内无否决/优先级/特权**。官方推荐"终止运行把控制权交回应用"（terminate-and-resume），而非在协议层给人类特权。

**Agora 对照**：支柱 1"人类 leader 唯一权威"是比 AutoGen 更强的模型（`humanGate` 即唯一裁决落点）。

### 1.3 值得借鉴的模式

**① TerminationCondition（增量可组合终止条件）—— 借鉴**

- 有状态、**增量式** callable：只检查自上次调用以来的新消息 delta，产出 `StopMessage`
- 可组合：`AndTerminationCondition` / `OrTerminationCondition`（`&` / `|`）
- 管理器的 `max_turns` 每轮 agent 响应后计数并检查（默认 `None`=无限——是坑；`MagenticOneGroupChat` 默认 20）
- → 对应 Agora 的 `iterationCount` 硬上限 + `humanGate`；**且 Agora 应默认开启**（不像 AutoGen 默认无限）

**② CodeExecutor 接口（代码执行器）—— 借鉴**

- `CodeBlock{code, language}` / `CodeResult{exit_code, output}`
- `CodeExecutor` 抽象：`execute_code_blocks(blocks, cancellation_token)` + `start()/stop()/restart()`（生命周期 = 沙箱会话开关）
- `LocalCommandLineCodeExecutor`：临时目录 + 子进程 + 60s 超时 + 危险命令过滤 + `CancellationToken.link_future`（取消即杀子进程）；官方警告本地不安全、推荐 Docker
- `DockerCommandLineCodeExecutor`：容器内 `exec_run`，取消时容器内 `pkill`
- → 完美映射 Agora 薄执行器 + 阶段 0 `LocalTempSandbox` / 阶段 1+ Docker

**③ MagenticOne Ledger 双循环（进度台账）—— 借鉴结构，拒绝 LLM 裁决** ⭐

- 外层 **Task Ledger**：orchestrator 的 LLM 产出 facts（已确认事实/猜测）+ plan，广播给全员
- 内层 **Progress Ledger**：每步用严格 JSON schema 评估：

```json
{ "is_request_satisfied":    {"reason": "...", "answer": bool},
  "is_in_loop":              {"reason": "...", "answer": bool},
  "is_progress_being_made":  {"reason": "...", "answer": bool},
  "next_speaker":            {"reason": "...", "answer": "<name>"},
  "instruction_or_question": {"reason": "...", "answer": "..."} }
```

- 停滞检测：`is_progress_being_made=false` 或 `is_in_loop=true` 计一次 stall；`>= max_stalls(3)` → 更新 facts+plan、重进外层循环
- `is_request_satisfied=true` → orchestrator 汇总最终答案
- → 这就是"orchestrator 维护结构化状态切片、在安全点显式评估进度"——与 Agora 支柱 2/4 同构。**关键改造**：台账裁决者应是**人类 leader（humanGate = is_request_satisfied）**而非 LLM；台账按角色投影切片，而非当纯文本广播

> **[2026-08-31 实装校准]** 任务 4.4 已按上述“借鉴结构、拒绝 LLM 裁决”落地：字段改为项目 camelCase schema；Coordinator 纯函数从结构化 State/Route 生成事实、计划与进度，不读取自然语言作裁决；普通完成只产生 `completionCandidate`，`isRequestSatisfied` 仍由 leader authority 持有，Phase 4 不抢跑 Phase 8 humanGate 完成流。连续 loop/no-progress 的 stall 上限为 3，触发外层 facts/plan revision；Ledger 作为结构化 Coordinator chat message append-only 持久化，并经 `coordinationContext` 对 Coordinator/worker 分片，不做全员广播。

**④ Handoff-as-tool（结构化交接）—— 借鉴协议**

- `Handoff{target, description, name}` → 生成 `transfer_to_<target>` 工具
- `HandoffMessage{target, context}`：`context` = 交接时打包的工具调用+结果（LLMMessage 列表），目标 agent 收到后 splice 进自己的 model context——**这是 AutoGen 唯一一处"选择性上下文传递"**
- `Swarm` 团队完全基于 handoff（发言人 = 最后一条 `HandoffMessage.target`）
- → Agora 借鉴"交接 = 带路由目标 + 结构化载荷的消息"（对应 `handoffPackets`），但载荷应写入共享状态切片（支柱 2），**拒绝** splice 进无界对话流

### 1.4 运行时：事件驱动演员模型 —— 借鉴概念

`autogen-core` 是 actor 框架：`send_message`（1:1 RPC）vs `publish_message`（话题广播）；`@rpc` / `@event` 装饰器；`SingleThreadedAgentRuntime` 保证每 agent 串行；`CancellationToken` 贯穿模型调用与子进程。

→ Agora 借鉴：单 Channel = 一个 topic；per-agent 串行化；rpc/event 区分（命令 vs 广播）；CancellationToken 传播。**拒绝**：为 4 个通用节点引入通用 actor 运行时 + 订阅图（支柱 5：编排保持小）。

## 2. AgentScope 调研（Alibaba）

源码基线：v0.1.7 `8775375a8aa6e87939195f64c92fac2344199b59`（经典分布式）/ v1.0.9 `a00095481062cbe04c4ef27036ddb871f7d41476`（异步重构）/ v2.0.7 `b2d60ccab81b2772dbbf1562845a9c5d5be4fd79`（当前 HEAD）。

### 2.1 v2.0 删除了 MsgHub —— 对 Agora 支柱 1 的独立背书 ⭐

HEAD（v2.0.7）源码中 `MsgHub`、`pipeline`、`ChatRoom` **全部移除**；多智能体协作改为 **Agent Team（leader–worker）+ 事件总线**（`src/agentscope/app/`：`_team_create.py`、`_team_say.py`、`_team_member_middleware.py`）。**阿里自己从"扁平广播群聊"转向 leader 制**——与 Agora"人类 leader 指挥"方向一致。

### 2.2 "same/different origin" 不存在

在 v0.0.4 / v0.1.7 / v1.0.9 源码与两篇论文（arXiv 2402.14034 / 2508.16279）中均无此术语。疑似来源是论文 "actor-based distributed framework" 中异步回复的**占位消息**（placeholder message），并非消息寻址字段。`Msg` 字段为 `id`（uuid4 hex）/ `name` / `role` / `content` / `metadata` / `timestamp`。

### 2.3 MsgHub 实际机制：扁平广播 —— 拒绝

v0.1.7 `MsgHubManager`：进 hub 时把每个参与者设为其他所有人的 audience；发言经 `__call__` → `_broadcast_to_audience` → 每人 `observe()`。v1.0.9 `MsgHub` 同理（subscriber 注册表）。**无层级、无 per-member 过滤**；源码 TODO 自认："we leave the consideration of nested msghub for future"。

### 2.4 值得借鉴的模式

**⑤ reply/observe/print 演员接口 —— 借鉴**

- `reply`（回应）、`observe`（收到但不回应、只入自己记忆）、`print`（UI 输出）
- → 单 Channel 群聊语义：observe = 非 turn-taking 投递；发言自动广播给成员

**⑥ 每 agent 独享内存的写所有权不变量 —— 借鉴** ⭐

- 核心框架**没有共享可写内存**：`AgentBase.__init__` 每个 agent 建自己的 memory（v0.1.7 `self.memory = TemporaryMemory()`）
- 唯一跨 agent 写路径是 `observe()`——单向拷贝进观察者自己的存储；`InMemoryMemory` = 有序列表 + 按 id 去重（单写者 append，无并发交错）
- 共享知识只以**只读 RAG knowledge bank** 形式存在
- 维护者官方推荐 per-customer/per-agent 隔离内存（[Discussion #1393](https://github.com/agentscope-ai/agentscope/discussions/1393)）；高级记忆被定位为 "time-series RAG problem"（[Issue #637](https://github.com/modelscope/agentscope/issues/637)，建议 `MemoryBase` + Graphiti）
- → 写-写冲突**靠构造消除**；验证 Agora"结构化切片**只读投影**、agent 只写自己私有区"的思路

**⑦ _reasoning/_acting 拆分 + interrupt()/handle_interrupt —— 借鉴**

- `ReActAgentBase`：`_reasoning` / `_acting` 两阶段 + pre/post hooks；`reply` 跑 `max_iters`（默认 10）循环，`finish_function_name="generate_response"` 退出；默认顺序执行工具，`parallel_tool_calls=True` 才 `asyncio.gather`
- `interrupt()` 取消当前 asyncio 任务，agent 在 `handle_interrupt` 驻留恢复——**这就是配合式抢占的正确实现**
- v2.0 事件总线将其形式化为 `RequireUserConfirmEvent` / `UserInterruptEvent`
- → 与 Agora 的 `agent/turn-stopping` 抢占落点同构；Harness 的 hook 扩展点 = 这里的 pre/post hooks

**⑧ 存储与上下文分离 + marks —— 借鉴**

- memory（存储源）与 context（进 prompt 的窗口）是**两层**；消息带 `marks` 标签用于过滤/压缩
- → 角色投影的具体化：投影 = 从存储层为每个角色派生"该看的视图"

### 2.5 要拒绝的

- `MsgHub` 扁平广播：无投影，规模受限（星型拓扑约饱和于 N = W/m 个 agent）
- `MultiAgentFormatter`：全量历史加名字前缀喂给每个 agent（= 最典型的无投影反模式）
- **人类 = 普通广播参与者**：`UserAgent` 阻塞读输入但不停止循环，循环停止完全靠代码编排——HITL 不是一等公民
- v0.1.x gRPC 演员网格：阶段 0 过早（保持"同代码本地/分布式"属性即可，不引入网格）
- 无 durable execution / checkpointer（对比 LangGraph 的弱点）；定位是角色扮演/仿真（狼人杀/辩论/社交模拟），**非编码编排**

## 4. 对五大支柱的校验结论

| 支柱 | 调研校验 |
|---|---|
| **1** 群聊单一原语 + 人类唯一权威 | AgentScope v2.0 移除 MsgHub、转向 leader–worker，独立印证方向；两者的 HITL 都弱于 Agora |
| **2** 角色投影（永不投原始 log） | AutoGen 全量广播 + issue #4648/#1006 证实缺陷；AgentScope `MultiAgentFormatter` 同病——Agora 方向正确 |
| **3** leader 唯一裁决 | AutoGen `UserProxyAgent` 无否决权、MagenticOne 用 LLM 裁决——Agora `humanGate` 更强 |
| **4** 配合式抢占 | AgentScope `interrupt()`/`handle_interrupt` 是同构的正确实现；AutoGen `CancellationToken` 是协作机制 |
| **5** 薄执行器 + 自研轻编排 | `CodeExecutor` 接口可直接映射；两者的编排层（actor 运行时/管线）均超出 Agora 4 节点所需 |

## 6. 后续动作

- **TerminationCondition 语义**由详细设计第 3 节已有 `iterationCount` 硬上限 + 确定性 humanGate 路由具体化。**[2026-09-03 架构决策更新]** 8.1 不再为借鉴模式单独新建一套隐藏进程内状态的通用 `TerminationCondition` 框架；如后续出现两种以上不能由 State 确定性表达的终止源，再以可持久游标为前提立项，不将其与 D4 生命周期绑死。
- **Coordinator 进度台账**（借鉴 MagenticOne Ledger）在阶段 4"自适应编排"实现时纳入：由人类 leader 持有裁决（`humanGate` = `is_request_satisfied`），台账按角色投影切片
- **写所有权不变量**：KnowledgeBase 阶段 0–N 只读（Write-Block）即该原则在 Agora 的具体化；Librarian 蒸馏（未来启用时）走"写入前双重门控"
- 本文为**带日期快照**；AutoGen/AgentScope 版本演进后如需复核，重跑调研并更新本文，决策同步到蓝图 §21。

#### 7.1.1 目标及当前判断

用户已明确希望 Agora 尽可能模拟真实软件开发团队。助手对这一方向的理解是：分工、主动沟通、交接、责任和经验积累应体现在实际行为中；用户既能让团队自行推进，也能进入讨论、调整方向。是否以及如何减少重复汇报、无效讨论和管理负担，需要继续设计。

**当前判断：** Agora 已具备多项真实执行机制，分工、并行、返工、需求调整和完成验收已有实现基础；长期成员记忆与自主协作还不完整。Phase 10 的 61 项任务完成，代表此前定义范围的完成，不代表本节产品愿景已经全部实现。

以下结论来自本轮源码与规格核对，以及既有验收用例；本轮没有重新运行产品场景，也不以“存在测试”推断模型在任意实际任务中都能稳定表现。当前证据主要针对既有 Docker/worktree 执行路径，迁移到本机直接开发后须重新验证。

<a id="future-3-2"></a>
#### 7.1.2 六项特征对照

| 真实团队特征 | 已有能力 | 当前缺口或边界 |
| --- | --- | --- |
| 成员有持续职责 | 六类角色、职责与工具权限；项目成员持久化、离职交接和任务接手 | 保留角色身份不等于保留跨任务经验；项目长期知识积累尚未启用 |
| 成员主动协作 | 开关小群、成员范围、群内上下文和结论回传已有机制；存在 worker 开群请求的处理入口 | 并行 worker 明确禁止 `channelAction`；不能宣称已完整支持“发现问题→主动找同事→同事响应→讨论后继续开发” |
| 工作并非固定流水线 | 复杂度分级、不同路由、依赖图并行、测试/评审反馈后的返工 | 自动调度仍围绕既定角色和规则；任意自定义角色自主路由尚未实现，不等于成员能够自由组织工作 |
| 成员能提出不同意见 | 结构化异议区分阻塞冲突与一般建议；Leader 裁决后形成可验证的事实并向角色传播 | 模型能否及时识别问题、提出有依据的异议，还需按真实场景验证，不能由机制存在推断意见质量 |
| 团队接受中途调整 | 需求、决策、优先级更新与安全点处理；自然语言需求有待确认草案；相关执行读取更新后的结构化事实 | 用户对影响范围、生效时机和返工范围的理解仍需改善；不代表所有自然语言都能直接执行 |
| 工作结果有责任归属 | 子任务责任、独立工作区、测试与评审记录、累计版本验证、Leader 完成确认 | 需要更清晰的面向用户的贡献、验收依据和剩余问题视图；测试通过不代表没有未覆盖缺陷 |

<a id="future-3-3"></a>
#### 7.1.3 关键证据与容易误解的边界

**主动开群受并行边界限制。** [MessageRuntime.handleWorkerOutput](../apps/web/src/server/message-runtime.ts) 会处理结构化 `open_sub_channel` 和关闭请求，但 [WorkerRuntime.validateParallelOutput](../packages/core/orchestration/src/worker-runtime.ts) 对并行输出中的 `channelAction` 明确拒绝，错误原文为：

```text
parallel worker "${handle.id}" cannot mutate project collaboration state
```

因此，“已有 Channel 基础”与“并行成员能随时自主拉群”必须分别表述。[Phase 6 验收用例](../tests/integration/phase6/phase6-exit.test.ts)覆盖通道隔离、结论回传和恢复，不足以单独证明后一种完整行为已经实现。后续应设计经过串行控制面校验的协作动作，而不是简单移除这项写入保护。

**跨任务经验尚未形成。** [详细设计 §8](详细设计方案.md)明确规定：“KnowledgeBase 写入功能被全局禁用（Write-Block）”，且“Librarian 仅作为空桩”。因此不能把已有 session 持久化、任务内交接或角色注册，解释为成员已经具备跨任务持续学习能力。若后续选择建设项目记忆，需要先定稿知识来源、适用范围、失效和更正机制，再按 D3 同步启用条件；本节不解除写入锁。

**自适应存在，但组织方式仍有边界。** [复杂度判断](../packages/core/orchestration/src/complexity.ts)和 [Coordinator](../packages/core/orchestration/src/coordinator.ts)已有按规则选择的执行路径；[延期项 DEF-016](deferred-items.json)明确记录任意自定义角色的自主路由尚未落地。项目可注册角色、Leader 可显式指派，不等于 Coordinator 能自动理解任意新增职责并合理安排工作。

**调整与交付有真实链路验收依据。** [Phase 9 并行流程用例](../tests/integration/phase9/phase9-parallel-flow.test.ts)覆盖需求调整后使旧证据失效并重新验证、定向返工保留无关工作，以及 A/B 并行后 C 接续、最终批准和归档。异议、完成裁决及累计产物约束的完整定义仍以 [项目蓝图 §21](项目蓝图.md)的 D9/D14/D16/D17 和详细设计对应章节为准。

<a id="future-3-4"></a>
#### 7.1.4 值得继续讨论的三个主要缺口

1. **成员如何积累项目经验。** 希望同一项目中的 Architect、Coder 等能接续过去工作；用户进一步提出共享项目知识库及专门维护角色，见 [§22.8](项目蓝图.md#future-10)。需要明确记住什么、由谁确认、如何引用来源、代码变化后如何更新或撤销旧认识。不能以无限保留全部聊天作为记忆方案。
2. **成员如何主动找同事协作。** 需要把发现问题、发起小群、参与者调度、上下文准入、作答、收尾与继续执行连接起来；特别要解决并行 worker 的协作动作如何进入受控写入路径。还需避免为了拉群而拉群。
3. **团队如何按工作需要组织执行。** 在已有复杂度、依赖和返工规则上讨论更灵活的责任分配、协作时机与角色参与方式；明确哪些取舍可自行推进，哪些必须交给 Leader。任意角色扩展与现有六角色优化是否同一阶段实施，尚未决定。

这三项是持续关注的产品缺口，不是已经批准的新任务。它们与原五个方向的实现依赖统一见 [§22.2](项目蓝图.md#future-4)，后续讨论按 [§18.4](开发计划安排.md#future-13) 接续。

#### 7.2.3 差异化验证与优先级说明
