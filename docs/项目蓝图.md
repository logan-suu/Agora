## 多 Agent 代码协作系统 · 项目蓝图

版本 v1.0（蓝图阶段，不含实现代码）· 日期 2026-08-20 目标场景：多个 agent 分工协作完成一个编码任务的完整闭环（需求理解 → 架构规划 → 编码 → 测试 → 代码评审 → 修复迭代）。 交互形态：**群聊式（一切皆群聊）**——界面是一列群聊：默认一个含全体成员的大群，agent 可按需新开只含相关成员的小群（即"私聊/临时小群"）；**leader 恒在每个群中**，随时观察、插话、指派、审批、拍板，全面模仿真实人类团队的协作。 执行形态：**真并行**——被激活的 agent 各自作为独立异步 worker 同时推进，配合式抢占 + git worktree 隔离 + 集成合并检查点，像真实团队一样多人同时干活。 权威形态：**leader 唯一裁决**——用户作为 leader 是最终决策者；agent 可以给出反馈、可以"顶嘴"提出异议，但最终由 leader 拍板，不做 agent 之间的自动共识。 技术栈：**纯 TypeScript 全栈**——薄 agent 内循环复用 **DeepSeek Harness**（可替换 loop + 事件溯源会话日志 + inbox steering + `ctx.subagents` 起隔离子 agent 作 worker 构建/作用域 + `ctx.compaction` 自动做单 agent 历史压缩），其上**自研轻量编排与并发/抢占层**；厚 agent 包裹 opencode / Harness+编码插件；工具走 MCP（TS SDK）；沙箱 Docker + git worktree；前端 Next.js/React 与后端同栈。 项目性质：**产品优先**——目标是做出一款完整、好用、像真实团队协作的群聊式代码协作产品，作为简历/作品集项目长期打磨；以渐进式工程 Eval 验证产品能力与架构取舍，但不追求论文级排行榜或大规模学术复现。 说明：本文为项目唯一主文档，已收拢前期竞品调研与框架选型的结论。标注「【假设】」处为默认设定，待确认后定稿。v1.0 相对 v0.9 的变化：在"任务"之上新增**项目/多租户层**（新增第二十节）——项目作为长期存在的顶层容器（项目 ⊃ 任务 ⊃ worker），采用"独立世界 + 全局调度器"隔离模型、每项目两层知识库（精炼层注入 + 归档层 RAG）由 Librarian 蒸馏回灌、跨项目默认拒绝 + 受控导入、leader 收件箱混合式（存储分项目 / 呈现全局聚合阻塞项）；并相应把 `AppState` 定位为任务级、澄清与第三节"不做账号级多租户"的区分（原第二十节"已定决策"顺延为第二十一节）。v0.9 相对 v0.8 的变化：更深地复用 DeepSeek Harness 现成能力——worker 的构建与作用域改骑 `ctx.subagents`（隔离子 agent，capabilities 映射角色规格），单 agent 历史压缩改委托 `ctx.compaction`；但 subagent 只做进程内上下文隔离、不替代 Docker+worktree 的文件隔离，且逐步驱动仍自行控制以支持配合式抢占（详见详细设计第 0、6、7 节）。v0.8 相对 v0.7 的变化：通信统一为单一 Channel 原语（一切皆群聊、leader 恒为成员），取代"广播/私聊/小群"三类通道的说法（详见第十、十一节）；并顺带清理若干残留的旧框架/字段命名。v0.7 相对 v0.6：技术栈从 Python/LangGraph 切换为纯 TypeScript + DeepSeek Harness + 自研轻编排（详见第四、十六节）。

### 一、项目定位与目标

这个项目要做的不是"再造一个 agent"，而是构建一套**多 agent 协作编排系统，并以群聊为产品形态呈现**：底层单 agent 的运行时（调 LLM、工具调用、推理循环）复用成熟框架，核心工作聚焦在协作层——如何把一个软件开发任务拆给多个有明确职责的 agent，如何让它们像真实团队一样在群里**并行**协作，如何在关键节点让人以 leader 身份介入指挥并**裁决冲突**，以及如何安全地执行 agent 产出的代码。

因为是产品优先，成功标准围绕"做出一款能用、好看、像真实团队"的完整产品：

一是**能跑通闭环**，给定中小规模编码任务，系统能自主完成"需求 → 设计 → 写-测-修 → 评审"并产出可运行代码与测试。二是**产品形态完整且生动**，以群聊界面为主形态实时呈现多 agent 协作，agent 之间能广播、私聊、拉小群、**同时并行干活**，用户作为 leader 可随时指挥并对分歧拍板；配可观测（trace/日志）、可一键部署、能直接演示。三是**协作可控**，每个 agent 职责边界清晰，流程可断点、可人工干预、可在中途插入新决策让全员响应。四是**工程质量稳**，上下文不因多 agent 而退化崩溃（见第八节），并行不因共享状态而写乱（见第十三节），系统行为连贯可预期。五是**可扩展**，新增角色或替换模型/工具、甚至把某个角色换成外部现成 agent，改动都局限在局部。

### 二、背景与竞品格局（产品设计的立足点）

「多角色 agent 分工写软件」不是新概念。开源侧，**ChatDev**（虚拟软件公司，CEO/CTO/程序员/测试等角色，34k stars，2026 年 2.0 已转型为通用多 agent 编排平台）、**MetaGPT**（把 SOP 编码进多 agent 协作）、**OpenHands**（开源自主编码 agent，可自托管）都做过类似实现。商业侧则相反——**Devin、Claude Code、Codex CLI** 等主流编码 agent **大多回归"单个强 agent"路线**，不做角色拆分。但另一侧的信号是：**Cursor 等已开始做"多 worktree 并行 agent"**——同一任务开多个 git worktree 让多个 agent 分头干、最后择优或合并，验证了"并行 + 隔离 + 集成"这条工程路线的现实价值。

最关键的行业信号：Devin 母公司 Cognition 发过影响很大的《Don't Build Multi-Agents》，论点是把编码拆给多个子 agent 常"适得其反"——**子 agent 之间上下文割裂、决策不一致、协调开销大**，不如一个握有完整上下文的强 agent。

对本项目的意义不是"这个方向错了"，而是给出两条硬性的**产品设计红线**。其一，多 agent 的价值在于分工带来的可控性、可审查性、以及"像真实团队"的生动协作体验；但**群聊绝不能被做成"所有 agent 都读群里全部消息"的全量广播总线**，否则就正好撞进上面批评的那个反模式。其二，**决策不一致必须有唯一权威来兜底**——本项目不做 agent 之间的自动共识（那正是"决策不一致、协调开销大"的温床），而是把 leader 设为唯一裁决者，agent 可反馈可异议、但最终由人拍板。因此本项目不做"又一个 ChatDev 复刻"，而是把"生动的群聊并行协作体验"和"底层受控的上下文工程 + 单一权威裁决"这两件看似矛盾的事同时做好（详见第八、十、十一、十四节）——这正是它作为产品的独特之处。

### 三、范围与边界（最关键的一节）

**我们要设计和实现的（项目主体）：** 协作编排拓扑（各角色如何串联、何时循环、何时分支）；角色职责划分与各自的 system prompt / 工具集；共享状态结构（state schema）与通信协议；**多形态通信（全员广播 / 私聊 / 临时小群）**；**真并行执行运行时（独立异步 worker + 配合式抢占 + worktree 隔离 + 集成检查点）**；**人工介入与 leader 冲突裁决（异议阻塞/建议双轨）**；**角色热插拔与团队动态编制（招募 / 离职 / 强制交接）**；**薄/厚 agent 执行器抽象（自研 llm 节点 vs 包裹外部 agent）**；**跨 agent 上下文工程机制**与**自适应编排机制**；工具经 MCP 的标准化接入；代码沙箱执行的接口与安全边界；**群聊式前端界面与可观测面板**（产品形态）。

**我们复用而不自研的（底层轮子）：** 单 agent 执行内核（**DeepSeek Harness** 提供的可替换 agent loop、Turn/Step 两层模型、工具三段流水线、事件溯源会话日志与 fork/resume/replay）；LLM 的 API 调用与重试（Harness 的 provider adapter）；MCP 协议的 client/server 实现（TS SDK）；沙箱底座（Docker，经 dockerode 驱动）；git worktree 的底层能力（simple-git）；可选的外部编码 agent（opencode / Harness+编码插件 / OpenHands，作为"厚 agent"执行器被包裹）；现成的聊天 UI 组件与流式通道（Next.js/React + SSE + HTTP POST）。

**明确不做的：** 自研模型或微调；**账号级多租户体系（SaaS 用户账号 / 权限 / 计费）**；生产级高可用与大规模并发；agent 之间的自动共识/投票机制（一律由 leader 裁决）；论文级大规模排行榜复现、为刷榜定制 Agent 或自建通用 Benchmark 任务生态。Agora **要做**面向工程验证的渐进式 Eval Suite：复用成熟 Coding Agent Benchmark 的任务/环境/Outcome Grader，自建少量 Agora 协作语义场景与 Process/Efficiency/Safety Grader，用于回归、架构取舍和秋招证据；它不替代各阶段集成测试或 G5 真实链路。（注意：这里排除的是"账号级多租户"；本项目**确实要做**单用户下的**多项目隔离**——同一 leader 可同时开多个项目、各自独立的团队/沙箱/知识库/群聊，见新增第二十节，二者不是一回事。）

### 四、总体架构

系统自上而下分四层。

**编排与并发层（Orchestration & Concurrency，自研）**：**不上重量级编排框架**，而是在 Harness 的事件流之上自研一层轻量编排——只有几个通用节点（coordinator / worker / integrate / humanGate）加一个 coordinator 路由函数，配一个全局共享 State。这一层决定"谁在什么条件下做什么、下一步交给谁"，并把"被激活的角色"实例化为**独立异步 worker** 同时运行，负责配合式抢占、worktree 分配与集成合并（见第十三节），也是自适应编排、leader 指令与冲突裁决的落点。之所以自研而非套框架：其一，编排图本身很小（4 个通用节点，角色是数据不进图）；其二，Harness 已自带事件溯源、checkpoint/fork/resume、inbox/steering，把"重框架"该给的 checkpoint 与人在环打断能力大半提供了，再叠一个 LangGraph 只会功能重叠。Node 的事件循环 + Promise 天然适配"多 worker 各自长跑、到边界让出"的并发模型。

**角色 Agent 层（Agents）**：每个 agent 有独立职责、system prompt 和工具集，但**执行器可薄可厚**——薄 agent 直接用 **Harness 的可替换 agent loop**（默认 `ReactLoopAgent`）作为内循环，我们通过其扩展点（`agent/pre-step`、`agent/request`、`agent/turn-stopping`）实现投影注入、抢占与路由，可被抢占、可细粒度介入；厚 agent 把 opencode / Harness+编码插件 / OpenHands 等外部编码 agent 包成一个"黑盒 worker"，只适合边界清晰的重编码子任务。我们只定义角色设定、能力边界与它读到的上下文投影。

**工具与执行层（Tools & Execution）**：所有对外部世界的操作（文件、git、测试、静态检查、执行代码）都封装成 MCP server（TS SDK），agent 通过统一协议调用（薄 agent 经 Harness 的工具三段流水线 `pre-execute → execute → post-execute` 调用）。代码执行隔离在沙箱中（Docker，dockerode 驱动），并行 worker 各自绑定一个 git worktree/分支（simple-git），agent 只提交代码、拿回结果，永不直接触碰宿主机。

**基础设施层（Infra）**：LLM provider（经 Harness adapter）、沙箱运行时、git worktree 池、持久化（Harness 事件溯源会话日志即天然 checkpoint/replay 源，另加产物存储）、可观测（从同一条事件流派生 trace / 日志）、以及驱动群聊界面的流式消息总线。

数据流：任务进入 → 编排层按图调度并选定并发档位（拓扑随复杂度自适应）→ 并发层把选中角色拉起为并行 worker，各读结构化上下文投影、在各自 worktree 内经 MCP 与沙箱交互、按协议在大群/小群中交接 → leader 可随时插话指挥、注入新决策、裁决异议（触发配合式抢占与重规划）→ 到集成检查点合并各 worker 产出 → 循环直到收敛 → 产出代码与产物。

### 五、角色划分【假设：6 个角色，可增减】

按软件团队隐喻划分六个角色，每个只对共享 State 的特定部分负责，职责单一。这 6 个是**默认在编阵容**——角色以数据（role spec）定义、可热插拔，leader 能招募新角色或让现有角色"离职"（详见第十二节），唯 Coordinator 作为调度内核不可移除。每个角色标注默认执行器类型（薄/厚，见第十六节）。

**Coordinator（协调者 / 调度大脑）【薄】**：不写代码也不定义需求，只做纯调度——根据任务复杂度与运行时反馈决定激活哪些角色、如何并行、判断是否收敛或升级给人。是编排、自适应、并发生命周期与通信路由的中枢。

**Product Manager（产品经理）【薄】**：把含糊的 `goal` 转成结构化需求（用户故事、验收标准、非目标），定义"做什么"，也是 Tester 客观验收判据的来源。当 leader 的新决策与既有需求矛盾时，PM 是提出反馈/异议的主要角色（最终仍由 leader 裁决）。【假设】由 Coordinator **条件触发**：需求含糊才走、明确规格则跳过。

**Architect（架构师）【薄】**：在需求之上定义"怎么做"——模块划分、接口约定、关键数据结构、技术选型，产出结构化设计写入 State。

**Coder（编码者）【薄或厚】**：依据架构与待办产出/修改代码补丁并提交沙箱，读取测试与评审反馈迭代。循环中最活跃，也是并行的主力。边界清晰的重编码子任务可切换为厚执行器（包裹外部 agent）。

**Tester（测试者）【薄或厚】**：编写并在沙箱运行测试，把编译错误、测试结果、覆盖率回填 State。测试不过就把控制权推回 Coder，是回环触发者。

**Reviewer（评审者）【薄】**：做质量、规范、安全审查，产出评审意见，也是人工卡点的载体。【假设】通过与否需人确认才进入收尾。

### 六、共享状态设计（State Schema）

所有协作信息集中在一个可序列化 State 对象里，是多 agent 唯一的"真相源"。初步字段（最终以代码定稿）：

任务层：`taskId`、`goal`、`requirements`（结构化需求）、`subtasks`、`phase`（clarifying / planning / coding / testing / review / done）、`complexity`（复杂度评估信号，供自适应编排用）。

设计层：`architecture`、`conventions`。

代码层：`repoSnapshot`（引用而非全量）、`pendingPatch`、`appliedHistory`。

反馈层：`testResults`、`reviewComments`、`iterationCount`（防死循环上限）。

并发层：`workers`（当前活跃的并行 worker：角色、状态 running/paused/done、绑定的 worktree/分支、当前安全点、执行器类型）、`integration`（集成检查点状态：待合并分支、合并结果、冲突项）。

协作层：`messages`（任务级消息事实，含所属群 `channelId` 与 `threadId`，见第十一节）、`roster`（当前在编角注册表：每个角色的定义、执行器类型与启用状态，支撑第十二节的热插拔）、`nextRole`、`humanGate`、`objections`（未决异议队列，见第十四节）、`handoffPackets`（结构化交接包，见第八节；也承载离职交接文档）、`decisionLedger`（决策+理由+**权威级别**台账，leader 决策为最高权威，见第十四节）。Channel 注册表属项目级 `Project.channels`，不在 `AppState` 复制（D7）。

并发写入用 State 合并函数（reducer 语义）明确各字段合并语义（如 `messages`/`decisionLedger`/`objections` 追加、`testResults` 覆盖、`workers` 按 workerId 归并），避免多 worker 并行写冲突（并发一致性详见第十三节）。

### 七、编排流程（协作拓扑）

主流程是一个带回环、**拓扑可随复杂度伸缩**、且**可并行推进**的有向图：

入口进 **Coordinator**，它评估任务复杂度并选择起始拓扑与并发档位（见第九、十三节）。含糊需求先经 **Product Manager** 产出验收标准再回来；随后视需要进 **Architect**；进入 coding 阶段后，Coordinator 可把多个可独立推进的子任务**同时**派给多个 Coder（各占一个 worktree）并行开工，Tester 可与之并行准备测试。

**核心回环**：Tester 失败则写回结果，Coordinator 判断——未超迭代上限回相应 Coder 续修（coding↔testing），超限则升级 `humanGate`。测试通过、且各并行分支到达**集成检查点**后合并；有需改项回 Coder（review↔coding），通过则触发人工确认卡点，确认后 `phase` 置 done，输出最终代码 + 测试 + 评审报告。

**问答与升级链**：任一 worker 卡住可发 `question`（带 `threadId`）定向问某角色→被问方挂起该线程作答→发起方 resume；答不了则沿 `threadId` 级联升级（Coder→PM→Leader），最终落到 `humanGate`。

**抢占与重规划**：leader 中途注入新决策或裁决异议时，Coordinator 广播暂停信号→各 worker 跑到安全点存 checkpoint→协调层改写共享 State→worker 带新上下文 resume（详见第十三、十四节）。

关键控制：`iterationCount` 硬上限（【假设】默认 8 轮）；任何角色遇不可解阻塞可主动置 `humanGate`；并行度上限由 Coordinator 按 worktree 池与成本约束控制。

### 八、亮点一：跨 Agent 上下文工程（产品稳定的地基）

**要解决的问题。** 多 agent 的头号死穴是上下文割裂：naive 做法要么把完整对话史全丢给下游（token 爆炸、关键信息被稀释），要么只传最终产物（下游看不到"为什么"，重复劳动甚至与上游矛盾）。尤其做成群聊后，最容易犯的错就是"让每个 agent 都读群里所有消息"——这会直接把产品拖垮。所以本项目把上下文当成**需显式设计的工程对象**，而非消息流的副产品。这是产品能稳定运行、不随对话变长而崩坏的地基。

**机制（四个抓手）。** 其一，**共享黑板作唯一真相源**：agent 间不流转原始对话 log，只读写结构化 State。其二，**角色投影视图**：每个 agent 只拿到与其角色相关的 State 切片（Coder 需要架构约定 + 当前失败测试 + 相关文件引用，不需要 PM 的完整讨论），省 token 又减干扰。其三，**结构化交接包（handoff packet）**：交接时生成紧凑结构——做了什么 / 关键决策及**理由** / 遗留问题 / 相关文件路径；理由入 `decisionLedger`，防止下游推翻上游。其四，**以产物为锚、按需检索**：代码真相在沙箱/仓库，agent 间传文件路径+行号引用而非贴代码（避免版本漂移），长历史做摘要压缩并保留检索入口。

**与执行器类型的关系。** 薄 agent 消费的是上述精细投影；厚 agent（外部 agent）是黑盒，只喂给它一份自包含的任务简报（目标 + 约束 + 相关文件入口 + 验收标准），拿回产物与摘要，不指望它遵守内部投影纪律——因此厚 agent 只用于边界清晰、上下文可打包的子任务。

**与群聊的关系。** 群里的消息是"给人看的展示层"；agent 真正消费的是上述结构化上下文（详见第十、十一节的双层分离）。小群天然就是"范围化上下文"——只有该群成员读到，正好把这条纪律变成产品自带的机制。

**待权衡点：** "每个角色到底需要哪些上下文"本身是设计难题，切太少丢信息、切太多退化回 naive；投影视图的划分规则需在实做中反复调。

### 九、亮点二：自适应编排

**要解决的问题。** 固定流水线对简单任务是浪费（给"加个缓存"也走完整 PM→架构→编码→测试→评审），而多 agent 协调开销只有过了复杂度阈值才回本。所以拓扑不写死，随任务复杂度动态伸缩，让产品对简单任务反应快、对复杂任务够稳。

**机制（两条路线结合）。** 路线一 **前置分类 + 分层拓扑**：入口用轻量路由估算复杂度，选档位——Tier 0 单 agent 直接上 / Tier 1 编码↔测试小循环 / Tier 2 完整团队（并可开并行）。路线二 **反馈式升级（escalation）**：默认走最便宜路径，失败再逐级加人（单 agent 不行→加 Reviewer→再拉 Architect 重设计），不依赖前置分类准确性、更鲁棒。二者结合：前置分类定起点，反馈升级兜底。（这也是"PM 条件触发"的推广——整个团队按需激活。）

**如何实现。** 即自研轻编排里 Coordinator 节点的**条件路由函数**：读 `complexity` 与上一轮结果决定 `nextRole` 与并发档位，而非走固定图；这就是 supervisor 模式运行时动态 dispatch。落到产品体验上，就是"简单需求几步就搞定、复杂需求才拉齐全队并行推进"，群里的参与人数与讨论深度随任务自然变化，更像真实团队。

**[2026-08-31 架构决策更新] Coordinator 双层进度台账的 Agora 落法。** MagenticOne 的 Task Ledger（已确认事实/假设/结构化计划）+ Progress Ledger（请求满足、回环、进展、下一角色、指令）只借结构，不引入 LLM orchestrator：Coordinator 在每个安全点用纯函数从 State + 已选 Route 确定性生成严格 JSON，并以 `messages.payload.kind='coordination_ledger'` 的结构化事件追加持久化（不扩 `AppState`/`Mutation` 接口）。`isInLoop=true` 或无结构化进展记一次 stall，连续 3 次重建外层 facts/plan 并递增 revision；`iterationCount=8` 仍是最终人工升级上限，两者分工不变。机器只能置 `completionCandidate`，`isRequestSatisfied` 始终由 leader 权威持有；Phase 4 只落该裁决接缝，普通完成路径的完整 humanGate Terminate & Fork 循环仍按路线留 Phase 8，避免阶段抢跑。台账不是原始群聊广播：COORDINATOR 读完整台账，业务角色只读自己的 plan step + confirmed facts + 当前 instruction。Coordinator 同一接缝在所有真实 worker→worker 角色切换时追加 `handoffPackets`，使进度、路由和交接保持同一结构化真相。

### 十、亮点三：群聊式协作界面（人作为 Leader 指挥）

**产品形态。** 最终交互是一个**群聊**：每个 agent 是群成员，PM/架构/编码/测试/评审的发言、交接、进度、产出链接都以人类可读的消息实时流在群里；用户作为 team leader 在群里发号施令——@某 agent 指派或追问、中途插入新需求、否决或批准评审、调整优先级、让某 agent 解释其决策、**对 agent 之间的分歧拍板**。相比"流水线跑完暂停等确认"，这种形态更生动、更可控、更像真实带团队，是本产品的灵魂。

**像真实团队一样通信（一切皆群聊）。** 界面上就是一列群聊：默认有一个包含全体角色的**大群**，agent 想和某人私下对齐时就**新开一个只含相关成员的小群**——本质仍是群聊，只是成员更少。所谓"全员广播"就是在大群发言，"私聊"就是 {A, B} 的小群，"临时小群"就是 {A, B, C} 的小群，它们不是三种不同的东西，而是**同一个原语（群聊 = 参与者集合）在不同成员规模下的用法**（详见第十一节）。**关键不变量：leader 恒是每个群的成员**——无论 agent 之间怎么私聊、拉群，leader 都在场、都看得到、随时能插话，不存在瞒着 leader 的对话。agent 可以自己发起小群，leader 也可以，小群收尾把结论冒泡回大群。并行状态下，多个 worker 会**同时**在各群里冒出消息，前端如实呈现"多人同时在干活"的热闹感。

**关键设计张力（产品能不能跑稳的分水岭）：群聊是展示与指挥层，不是 agent 的内部上下文总线。** 一个群的成员名单只决定"谁看得到这条消息"，不等于 agent 把看到的一切都塞进自己的工作上下文。每个 agent 纳入上下文的，仍是它的角色投影 + **它所属的那些群**的局部上下文（第八节）。这样大群发言不会淹没所有人，小群天然把上下文限定在参与者范围内。这条"展示层与 context 层解耦"的设计，正是让产品既生动又不崩的关键——群聊看起来热闹，底层每个 agent 的上下文却始终干净、聚焦。

**[2026-08-31 架构决策更新]消息事实与实时投递分离。** `AppState.messages` 是任务级消息事实源；消息必须先经应用服务调用 `applyMutations()` 提交并持久化，成功后才发布 `MessageCommitted` 事件。`MessageBus` 只负责已提交事件的投递，不直接修改 State。浏览器只接收 `{msgId, channelId, fromRole, type, display, ts}` 展示信封，永不接收面向 agent 的 `payload`；SSE 是可重连的实时提示层，不是第二份事实源。

**[2026-08-31 架构决策更新]Leader 指令的阶段化落地（D9）。** Leader 的普通发言与指令统一从 `POST /api/messages` 进入；浏览器只提交 `display` 与稳定 `msgId`，服务端从 `display` 生成结构化意图，不信任客户端自报的 `payload.intent`，也不保留绕过 State 的独立临时 command 投递面。Leader 消息与本阶段可执行的动作 mutations 必须在同一任务串行区内经一次 `TaskStateStore.commit()` 原子、幂等提交，成功后才按 D6 发布展示事件。

**[2026-09-01 架构决策更新]D9 单主消息边界。** 一次 `commitPlannedMessage` 只承载一个由服务端构造并单独校验的主消息；planner 返回的动作 mutations 只能修改非 `messages` 字段，禁止追加第二条消息。需要一次提交多条消息的编排路径必须走会校验并投递每条新增消息的批量 mutation 服务，避免附加消息绕过 Channel 策略或成为未发布事实。

**[2026-09-01 架构决策更新]D9 Phase 6 Channel 生命周期例外。** sub 群属于项目级 `Project.channels`，不能伪装成任务级 State mutation，也无法与 `TaskStateStore` 做跨文件原子提交。Leader 仍只从 `POST /api/messages` 发起；服务端先验证任务、可信 actor、roster 与命令，再按稳定 `msgId/actionId` 幂等提交 `ProjectChannelStore`，随后把原 Leader 消息或生命周期 `announce` 经 D6 写入任务 State 并投递。后一步失败不回滚已提交 Channel，重试必须补齐消息且不得重复开/关群。AppState 内动作继续遵守“主消息 + 非消息 mutations 一次提交”；Channel 生命周期不得借临时 command 总线绕过同一入口。

阶段 5 只承诺可真实闭环的最小指令：消息开头的单一 `@ROLE` 表示定向激活，目标必须是已启用角色，任务不得处于 `done` 或待裁决 `humanGate`；有效指令随消息原子写入 `nextRole`，普通文本只作为 `chat` 持久化。Coordinator 在下一次决策时只消费**最新且尚未确认**的 applied assignment，追加带 `sourceMsgId` 的控制事件并把 instruction 写入本轮 Coordination Ledger 后定向派发；该确认事件防止同一指令重复激活，更早的未消费 assignment 视为已被最新指令覆盖。未知/禁用角色、非法状态，以及尚未到阶段的新需求重规划、正式决策覆盖、humanGate 裁决、优先级改写、objection 关闭、sub 群创建均不得静默假装成功，而须返回结构化 `rejected` 或 `deferred`（含目标阶段与原因），同时保留 Leader 原始消息事实。动态 sub 群归阶段 6，humanGate/objection 裁决归阶段 8，需要安全点暂停与重跑的新需求/决策/优先级变更归阶段 9 的完整配合式抢占。识别与执行分层，后续阶段扩展动作执行器而不重写 Leader 输入入口。

**[2026-09-01 架构决策更新]Phase 5 Web 编排执行桥接（D10）。** 创建并启动一个全新任务属于任务生命周期操作，不属于 D9 所指的“既有任务内 Leader 发言/指令”；任务启动后，所有群聊输入仍统一遵守 D9。受信任单用户、单实例自托管后端的组合根必须复用既有 `runOrchestration()`、HarnessExecutor、沙箱和 L3 端口，不复制第二套编排循环。Phase 5 仍处于“项目内初期退化单任务、Phase 9 才升级真并行”的阶段，因此整个后端实例最多一个活动 run；不同任务的持久终态可共存，但另一活动任务存在时新启动必须明确拒绝，禁止在 GlobalScheduler 落地前绕过并行配额。Coordinator/Worker 的展示消息与状态变化必须先提交并持久化到任务 State，再经 MessageBus→SSE 投递；静态种子消息不得充当执行证据。终态 State/消息与产物引用必须可刷新恢复；产物先归档到任务耐久目录，再释放 Harness、MCP/Git client 与 Docker 容器，刷新不得依赖活执行资源。活动 run 因进程退出而中断时不得误报“仍在运行”；进程重启自动续跑不在本阶段承诺内。

### 十一、通信形态与协议（一切皆群聊：单一 Channel 原语）

agent 间不直接互相调用，而是**通过共享 State + 群聊消息**间接协作，耦合最低、最可控。**这里只有一个通信原语——群聊（Channel = 一个参与者集合），且 leader 恒为其成员。** 过去常说的"广播 / 私聊 / 小群"不是三种不同的通道类型，而是同一个原语在不同成员规模下的用法：

**全员大群（main）**：participants 覆盖全体在编角色 + leader。在这里发言即"全员广播"，用于阶段公告、目标发布、评审终审结论等需要全员周知的信息。全员"可见"但不等于全员"消费"——是否纳入某 agent 的工作上下文仍由其角色投影决定。

**子集小群（sub）**：participants 是若干成员 + leader（leader 强制并入），且每个 sub 群必须绑定创建它的 `taskId`、稳定 `threadId`、非空 `topic` 与可信 `createdBy`，不允许任务 A 借用任务 B 的小群。两人时就是过去说的"私聊"，多人时就是"临时小群"（如 Coder+Tester 合力攻 bug、Architect+Coder 对齐方案）。小群拥有自己的**局部上下文**，只有群成员能读到；讨论结束后把结论摘要 + 关键决策及理由冒泡回大群并写回共享黑板，防止形成信息孤岛。这也正好是自适应编排里 Tier-1/Tier-2 局部拓扑的可视化呈现。

因为 leader 是每个群的成员，所以**任何 agent 之间的对话对 leader 都是透明的、可随时介入的**——这是"leader 唯一裁决"权威形态在通信层的自然落点，也让"瞒着 leader 私下商量"这种情况在结构上不可能发生。

**消息结构**（初步，TS 字段）：`{ msgId, threadId（问答/升级/异议的会话链标识，用于挂起-作答-resume 与级联升级）, channelId（所属群聊；大群=main，"私聊/小群"=对应 sub 群）, fromRole, to?（群内 @定向，仅影响 inbox 优先级，不改变可见范围）, type（handoff / feedback / question / escalation / objection / chat / announce）, payload（面向 agent 的结构化内容）, display（面向人的可读摘要，用于群聊呈现）, ts }`。`payload` 与 `display` 分离，正是第十节双层设计的落点；`threadId` 支撑第七节的问答链与第十四节的异议/升级链；消息的可见范围只由它所属 Channel 的 participants 决定。

**[2026-09-01 架构决策更新]作用域、所有权与恢复边界。** `Project.channels` 是 Channel 注册表的唯一真相源，`AppState.messages` 保存任务级消息事实；`AppState` 不再复制 `channels`。跨边界投递使用 `{projectId, taskId, message}` 信封，API/SSE 也必须带项目与任务作用域，避免不同项目的 `main` 群碰撞。阶段 6 的注册表必须经项目级原子 JSON 快照持久化，并可在进程重启后恢复；不得以进程内 Map 充当真相源。项目只有一个 `channelId='main'` 的项目级大群；sub 群的 `channelId` 在项目内唯一且必须绑定 `taskId`。角色 inbox 属 `channels` 的可重建读模型，从持久 Channel 注册表 + 任务 `AppState.messages` 派生，不属于 `MessageBus` 端口，不保存第二份消息事实。阶段 5 退化为每个活动任务从项目 main 群派生视图；阶段 6 启用持久 Channel、participants、任务绑定 sub 群与局部上下文。

**[2026-09-01 架构决策更新]D7 升级恢复与语义稳定性。** Phase 6 首次读取已有任务时，若任务 `state.json` 存在而项目 `channels.json` 缺失，服务端必须以当前已启用 roster 幂等补建唯一 main，保证 Phase 5 持久任务升级后仍可访问；仅“文件缺失”允许 backfill，损坏或违反不变量的快照必须明确失败，不得覆盖。已启用角色必须非空、唯一且不得使用保留身份 `leader`。Channel JSON 对象的属性排列不构成语义变化；participants 在领域上是集合，写入前必须标准化为 `leader` 在前、其余角色按当前 enabled roster 顺序排列，成员相同而输入顺序不同属于 no-op。Channel 注册表顺序与 `localContext` 消息引用顺序仍保留，语义相同的 commit 不得写盘或递增 revision。

**[2026-09-01 架构决策更新]发起权与生命周期【已定：以 agent 自发为主】。** 小群（含"私聊"）**主要由 agent 自己按需发起**，leader 同样可随时发起。agent 只能在最终回复末尾输出至多一个严格 `<agora-channel-action>{...}</agora-channel-action>` 控制块；薄执行器校验并从人类 display 中剥离该块，以同一步 assistant message 的 `msgId` 绑定 actionId，再通过现有通用 `StepResult.output` 在安全边界交给编排层。它不是 AppState mutation，也不是可由模型伪造 actor 的普通 MCP 参数；组合根必须把当前 RoleSpec 身份绑定为可信 actor，畸形/未知控制块令 Step 明确失败而非降级成普通文本。控制块可以为 open 显式携带安全、稳定的 `threadId`，但不得携带 actor/actionId；纯控制回复仍保存审计 Message，并生成不含原控制块的确定性非空 display，避免展示空白消息。Leader 使用 `/channel open ROLE[,ROLE...] <topic>` 与 `/channel close <channelId>`，仍经 `POST /api/messages`，由服务端绑定为 `leader`。

每个动作携带安全、稳定的 `actionId`；Leader 路径复用 `msgId`，agent 路径由执行器生成并在重试时复用。新群采用可逆长度前缀 `channelId='sub-'+taskId.length+'-'+taskId+'-'+actionId`，消除 taskId/actionId 均允许连字符时的拼接碰撞；`threadId=actionId`（agent 可显式提供另一个稳定 threadId）。participants 自动取 `{leader, actor（若非 leader）, requestedRoles}` 并按 roster 标准化。相同 `taskId+threadId` 的同语义 open 返回既有 Channel；participants/topic 不同则明确冲突；不同 thread 若仍产生 channelId 冲突必须作为业务拒绝而非存储异常；关闭后重开同一 thread 也不得静默复活。只有 leader 或该 sub 的 participant 可关闭；main 永不关闭；重复 close 为 no-op。所有生命周期写经一个按项目串行的应用服务提交既有 `ProjectChannelStore`，不修改其冻结签名。

Coordinator 不再是群的主要创建者，而退为轻量治理：用 `taskId+threadId` 防重复议题群、观察数量并保证收尾回流。6.2 的 close 只原子置 `closed=true`、阻止后续 sub 发言并向 main 写稳定幂等的生命周期公告；6.3 再处理 `closed && bubbledSummary===undefined`，以稳定 msgId 把结论冒泡到 main 后写入 `bubbledSummary`。因此 `threadId` 在 6.2 只提供持久会话链与路由，真正的异议挂起、humanGate 裁决和 resume 仍归 Phase 8。工具调用侧继续一律走 MCP；Channel 生命周期属于编排控制动作，不新增绕过 MCP 的代码执行工具。

前端不得继续把 main 写死为唯一群。Phase 6 增加只读 `GET /api/channels?projectId&taskId`，从持久 `ProjectChannelSnapshot` 以字段白名单派生 leader 可见的 main + 当前 task sub 元数据（不返回 `localContext`、`bubbledSummary` 原文或消息 payload）；UI 在任务初始化、生命周期动作完成时刷新一次，仅在 active run 中持续短轮询，成功恢复后清除独立的 Channel 刷新错误；切群后用所选 `channelId` 重建既有 SSE/POST 作用域。Channel 列表不是新事实源，不新增 Channel 事件总线；agent 开群即使 lifecycle announce 暂时投递失败，也可由持久快照恢复发现。

### 十二、角色热插拔与团队动态编制（入职 · 离职 · 交接）

**能力概述。** leader 可以像管理真实团队一样动态调整成员编制：**招募新 agent（入职）**、**移除某个 agent（离职）**；被移除的 agent 在离开前**必须先交出一份交接文档**，新加入的 agent 入职时自动读取交接文档与当前状态投影来接手工作。这把第八节的"结构化交接"从看不见的内部机制，升级成看得见、可操作的产品能力。

**前提：角色是数据，不是代码。** 每个角色由一份**角色定义（RoleSpec）描述——名称、职责说明、system prompt、工具集（MCP 权限）、负责的 State 切片（投影规则）、执行器类型（薄 harness / 厚 external）、可被路由的条件。系统维护一个运行时角色注册表（roster）**，当前"在编"成员即注册表里的启用项。增删角色 = 改注册表数据，无需改代码。实现上用"**通用 worker 节点 + coordinator 路由**"：Coordinator 决定交给角色 X，通用执行节点按注册表加载 X 的 prompt/工具/投影/执行器类型来运行；新增或删除角色都不改编排结构——这正是自研轻编排（而非静态图框架）带来的灵活性。

**三个生命周期动作。** 其一，**入职（招募）**：leader 从**角色模板库**选一个，或自定义 spec（名字 + 职责 + prompt + 工具 + 执行器类型）；系统注册进 roster 并在群里发"入职公告"；新 agent 的初始上下文 = 相关交接文档 + 当前 State 的角色投影（只读它该读的，而非全部历史）。其二，**离职（移除）**：leader @某 agent 下"离职"指令 → 触发**强制交接流程**——该 agent 被移出前必须产出一份**交接文档**（我负责的部分现状 / 关键决策及理由 / 未完成事项 / 相关文件与产物入口 / 给接手人的建议），写回共享黑板（复用 `handoffPackets` + `decisionLedger` 结构）；交接完成、责任转移后才把该角色从 roster 停用。其三，**责任转移（handover）**：离职会留下"孤儿职责"，由 leader 在离职指令里指定接手人——转给某个在编 agent，或招募一个替补 agent 继承（它入职时读那份交接文档）；若暂时无人接手，Coordinator 把该职责标记为空缺、需要时升级 `humanGate`，绝不静默丢责任。

**护栏。** 其一，Coordinator 不可删除——它是调度内核，删了就没有编排；其余 5 个角色均可插拔。其二，任务进行中删角色要优雅：先触发配合式抢占让该 worker 跑到安全点暂停 → 交接 → 转移 → resume，不允许某角色正干活时硬拔导致状态半截（并发下的安全点机制见第十三节）。其三，自适应编排只在**当前在编 roster** 内路由；某类工作对应的角色被删且无人接手时，该能力暂时缺失，Coordinator 显式提示 leader，而不是假装能做。

**产品与讲点价值。** "我把 agent 团队做成一个活的、可编辑的组织——leader 能招人、能让成员'离职'，而离职必须先交接、新人入职自动读交接文档接手。"它同时是极具冲击力的演示点，和对"多 agent 的上下文如何传承"这一深问题的正面回答。

### 十三、真并行执行与配合式抢占

**要解决的问题。** 要"像真实团队"，就不能只是轮流发言的回合制——多个成员应能**同时**干活。但真并行带来两个新难题：一是并发访问共享黑板会写乱；二是 LLM 一旦开始生成就无法"硬中断"，leader 中途改主意时没法瞬间叫停所有人。本节给出应对。

**独立异步 worker。** 被 Coordinator 激活的每个角色实例化为一个**独立异步 worker**，拥有自己的推理循环（薄 agent 即经 Harness `ctx.subagents` 起的隔离子 agent，零父上下文、独立 session，其可用工具/人格由角色规格作用域化）、事件溯源会话日志（天然 checkpoint/replay 源）和绑定的 git worktree/分支，彼此并行推进。**隔离是两层：subagent 负责进程内上下文隔离，git worktree 负责文件系统隔离，二者互补。** Node 的事件循环 + Promise 让"多 worker 各自长跑、到边界让出"表达得很自然——这正是真实团队"各自干活、随时可被打断改计划"的并发形态。

**为何自研这层。** 单 agent 的运行时（loop、工具流水线、事件溯源、resume）复用 Harness；但"多个长跑 worker 的生命周期 + 抢占编排 + worktree 分配 + 集成合并"是 Harness（单 agent 运行时）之上、需要我们自己写的协作层：它拉起/回收 worker、广播控制信号、协调对共享 State 的写入（走合并函数归并 + 按 workerId 分区，避免互相覆盖）。这层轻——因为 Harness 已经把每个 worker 内部最难的事件溯源与安全打断能力给了，我们只做"多 worker 之上的调度"。

**配合式抢占（cooperative preemption）。** 既然不能硬中断 LLM，就用"协作式"：协调层广播一个**暂停信号** → 每个 worker 跑到**安全点**（当前这次 LLM 调用或工具调用自然结束）才停 → 存 checkpoint → 协调层改写共享 State（写入 leader 新决策/裁决结果）→ worker 带**新上下文** resume。代价是有一个"到安全点"的延迟（秒级），但换来状态一致、不撕裂，符合"改主意后全员响应新计划"的产品诉求。

**worktree 隔离与集成检查点。** 并行的 Coder 各占一个 git worktree/分支，互不踩踏文件（呼应第二节 Cursor 的多 worktree 实践）；到**集成检查点**时，协调层按顺序合并各分支，冲突则交给一个集成步骤（或升级 leader）解决，再跑一遍整体测试。这样"并行提速"与"最终一致"兼得。

**一致性兜底。** 其一，写共享 State 一律经 reducer，字段级明确合并语义（追加/覆盖/按 id 归并）。其二，代码产物以 worktree 为准、State 只存引用（路径+分支+commit），避免贴代码导致的版本漂移。其三，任何跨 worker 的强依赖（B 必须等 A 的接口）由 Coordinator 建**依赖序**，不满足则该 worker 暂不激活或先给桩。

**分阶段落地。** 真并行是进阶能力，不在第一版。**先做回合制（round-robin）跑通全链路**（阶段 0–8），把状态、上下文、通信、裁决都验稳，**再在阶段 9 升级为真并行**——底层预留 worker 抽象与 worktree 接口，但初期用"单 worker 顺序执行"退化实现，降低早期复杂度与调试成本。

### 十四、人工介入与冲突裁决（Leader 唯一权威）

**核心原则：leader 是唯一裁决者，不做 agent 自动共识。** agent 可以给出专业反馈、可以"顶嘴"提出异议，但最终决策权始终在人。这既是产品设定（用户是团队 leader），也是对《Don't Build Multi-Agents》"决策不一致"批评的正面回答——用单一权威兜底，避免 agent 互相扯皮或达成错误共识。

**三类人工介入。** 借 Harness 的事件溯源会话日志（天然 checkpoint）+ turn-stopping/inbox steering（安全点打断与注入）实现。其一是**被动卡点**：Reviewer 通过后的终审确认（放行/打回/直接改）、迭代超限或角色主动升级时的兜底决策。其二是**主动指挥**（承接第十节群聊）：leader 随时在群里发指令——指派、追问、插入新需求/新决策、否决/批准、调优先级、拉小群；各动作严格按 D9 的 Phase 5/6/8/9 边界逐步解锁，只有需要重规划/重跑的动作在 Phase 9 进入完整安全点抢占。其三是**冲突裁决**：对 agent 之间或 agent 与既有决策之间的分歧拍板。完整形态以"（配合式）暂停并保存完整状态 → 人给指令 → 从断点 resume"的统一机制落地。

**异议双轨（agent 如何"顶嘴"）。** agent 发现问题时发 `objection` 类型消息，分两轨处理：

- **阻塞型（blocking）**：当 leader 的新决策与既有需求/设计**矛盾**（典型：leader 临时改需求，PM 认为与已定验收标准冲突）。此时受影响的相关工作**暂停**（走配合式抢占到安全点），异议进 `objections` 队列并在群里高亮，等 leader 拍板后才继续。理由：方向性矛盾若不先解决，继续干只会产出废码。
- **建议型（advisory）**：小范围的技术异议（如 Coder 觉得某接口命名不佳、建议换个库）。此时**工作照常继续**，异议作为一条记录挂在 `objections` 里、在群里可见，leader 有空再看、可采纳可忽略，不打断节奏。

判定谁阻塞谁建议，由 Coordinator 按"是否与 `decisionLedger` 里已定决策/需求相矛盾"来分类；拿不准时从宽按 advisory，避免动辄卡住全队。

**决策台账与权威级别。** `decisionLedger` 每条决策带**权威级别**：leader 决策为最高权威，可覆盖 agent 此前的任何约定；agent 之间的约定为普通级别。下游想推翻某决策时，只能推翻同级或更低级别的；碰到 leader 级决策只能走异议 → 由 leader 自己改。这样"leader 新决策与 PM 旧需求矛盾"就有明确的解法：PM 发 blocking objection → 相关工作暂停 → leader 裁决（改需求或收回新决策）→ 结果以最高权威写回台账 → 全员按新台账 resume。

**卡点粒度待定。** 具体保留哪些被动卡点、粒度多细（每阶段确认 vs 仅终审确认），待确认。

### 十五、代码执行与安全

agent 产出的代码一律在**沙箱**中执行，绝不碰宿主机。[2026-08-24 选型同步]【假设】阶段 1 起使用本地 Docker（每任务一隔离容器，限网络与资源），阶段 0 先以本地临时目录 Mock 沙箱替代（决策 5），后续可平滑切 E2B / Firecracker microVM。并行执行时，每个 worker 绑定独立的 **git worktree/分支**（可映射到各自的容器工作目录），互不踩踏，集成检查点再合并。沙箱经 MCP 暴露三类能力：应用补丁、运行命令（编译/测试）、读取输出。所有文件操作限定容器内工作目录，遵守文件保护原则。厚 agent（外部编码 agent）同样只在沙箱内运行、只经受控接口拿产物，不给宿主机直接权限。

**[2026-09-01 架构决策更新] 归档产物的独立复验同样属于 Agent 代码执行。** 宿主进程可管理 Git 元数据、持久化 State、复制/归档文件快照，但不得用宿主 Node、shell 或其他运行时直接执行 Agent 生成的源码、测试或脚本。终态 artifact 需要独立验收时，必须把耐久快照复制或只读挂载到一个**新的隔离沙箱/容器**后再执行，以同时证明归档可恢复性与 G7 隔离边界；“宿主 Git”不等于“宿主执行”。

### 十六、技术栈选型（含框架对比结论）

**语言与全栈基线：纯 TypeScript。** 前端（群聊界面）本就是 Web，编码 agent 生态（Harness、opencode、Claude Code、Codex CLI、多数 MCP server）也以 TS/Node 为主，纯 TS 让前后端 + agent 运行时统一成一套工具链，对单人长期打磨的作品集项目省心；Node 事件循环也天然适配"多 worker 各自长跑、到边界让出"的并发模型。

**薄 agent 内循环：DeepSeek Harness。** 复用它的可替换 agent loop（默认 `ReactLoopAgent`）、Turn/Step 两层模型、工具三段流水线、事件溯源会话日志（`deriveMessages()` 从日志投影历史、从不单独存储——正好落实我们"共享黑板 + 角色投影"的上下文纪律）、以及 fork/resume/replay。我们通过它的扩展点接入自己的逻辑：`agent/pre-step`（注入角色投影、拦截本步）、`agent/request`（按角色路由不同模型/推理档位）、`agent/turn-stopping` + inbox 的 `steer`/`inject`（实现配合式抢占——中途注入 leader 新指令，agent 跑到边界重读 inbox 再开一步）。

**编排与并发：自研轻量层（TypeScript）。** 不上重量级编排框架（对比：LangGraph.js/Mastra 虽 2026 已生产可用，但我们的编排图只有 4 个通用节点、角色是数据不进图，且 Harness 已自带事件溯源/resume/inbox，再叠一个重框架只会功能重叠）。自研层负责：4 个通用节点（coordinator/worker/integrate/humanGate）+ coordinator 条件路由、独立 worker 生命周期、配合式抢占的信号广播与安全点、worktree 分配与集成合并（见第十三节）。

工具接入统一走 **MCP（TS SDK）**（git / 文件 / 测试 / 静态检查各封装为 server）。代码执行用 **Docker 沙箱**（dockerode 驱动，云端可升级 E2B），并行隔离用 **git worktree**（simple-git）。模型按角色差异化：规划/评审用强推理模型，编码用代码专精模型（经 Harness `agent/request` 扩展点做模型路由）。前端做**群聊式界面**（消息流 + @指令 + 私聊/小群会话 + 并行进度 + 异议高亮 + 产出/trace 侧栏），用 **Next.js/React + SSE + HTTP POST**（[2026-08-24 选型同步]取代原 WebSocket/SSE，详见《技术选型文档》§9.2）；可观测直接从 Harness 的事件流派生 trace + 结构化日志。

**厚 agent 候选：** opencode、Harness+编码插件、OpenHands 等外部编码 agent，经统一的 `ExternalAgentExecutor` 接口包裹，仅用于边界清晰的重编码子任务。

### 十七、分阶段实施路线（按产品打磨节奏）

**总原则：先回合制跑稳全链路，再升级真并行。** 早期用"单 worker 顺序执行"退化实现，把状态/上下文/通信/裁决验稳，避免一上来就扛并发复杂度。

**阶段 0 · 骨架**：搭 TS 工程 + Harness 单 agent 跑通，[2026-08-24 架构决策更新：Phase 0 采纳三角色闭环（对齐《开发计划安排》）]自研轻编排仅 Coordinator + Coder + Tester 三个角色跑最简单任务（Coder 写码 → Tester 跑测 → 失败回 Coder），验证 State 传递、worker 节点与 Harness loop 接入。底层预留 worker 抽象接口（初期退化为单 worker 顺序执行）。[2026-08-23 架构决策更新] 产出：最小闭环 demo（基于本地临时目录，不依赖容器与真实 Git 分支）。

**阶段 1 · 沙箱与工具**：接 Docker 沙箱 + 核心 MCP 工具（文件/运行命令/git），Coder 能真正写代码进沙箱并执行。产出：agent 能产出并运行代码。

**阶段 2 · 完整角色与回环**：补齐 PM / Architect / Tester / Reviewer，实现 coding↔testing↔review 回环与迭代上限。角色从一开始就用**数据驱动的注册表 + 通用 worker 节点 + 执行器类型字段**实现（为阶段 7/9 的热插拔与厚 agent 铺路，避免后期返工）。产出：完整协作闭环。

**阶段 3 · 上下文工程**：实现结构化交接包、角色投影视图、决策台账（含权威级别），把"上下文不随对话变长而崩"的地基打牢。产出：稳定的上下文机制。

**阶段 4 · 自适应编排**：实现复杂度路由 + 反馈式升级，让参与规模随任务自然伸缩。产出：对简单任务快、对复杂任务稳的编排。

**阶段 5 · 群聊界面（MVP）**：做群聊式界面（agent 成员实时消息流 + leader @指令 + 产出/trace 侧栏），落地"展示层与内部上下文双层分离"；消息先写任务 State 的 JSON 快照、再经 MessageBus→SSE 推送展示信封，SSE 建连必须在持久快照与实时尾流之间无缝衔接；阶段内只支持带 `projectId/taskId` 作用域的固定 `main` 群，并只承诺受信任边界内的单实例自托管运行；按 D9 接通服务端解释、原子持久化且可验证生效的 leader `@ROLE` 定向激活，完整 interrupt/resume 留阶段 9。产出：可演示且刷新后可恢复的群聊协作产品雏形。

**阶段 6 · 多形态通信 + Eval 骨架**：在阶段 5 已定稿的消息提交/投递端口之上，实现可持久恢复的项目级 Channel 注册表——一个全员 main 群 + 可动态新建且绑定任务的 sub 群（"私聊/小群"，participants 自动含 leader），带 `threadId/topic/createdBy` 生命周期元数据；增加 participants 路由、可从持久真相重建的角色 inbox、agent/leader 幂等发起与关闭 sub 群，以及关闭后的结论冒泡，不改写 MessageBus 的 State 所有权。Channel 生命周期按项目串行，Channel 事实先提交、D6 消息后补齐；participants 按集合标准化。与此同时按 D11 定稿统一 Eval 任务/结果契约、可重复运行器与 Phase 0–6 基线任务。产出：像真实团队一样通信的群聊 + 可增量演进的工程 Eval 地基。

**阶段 7 · 角色热插拔**：实现 leader 招募/移除角色、离职强制交接文档、新人入职读交接接手、责任转移与护栏（Coordinator 不可删、运行中先暂停再交接）。产出：可增删成员的"活团队"。

**阶段 8 · 人工卡点与冲突裁决**：human-in-the-loop 卡点、checkpoint 续跑、异议双轨（阻塞/建议）、决策权威级别、结构化 trace 面板。产出：可控、可裁决、可观测的系统。

**阶段 9 · 真并行升级**：把退化的单 worker 顺序执行升级为**独立异步 worker 真并行** + 配合式抢占 + worktree 隔离 + 集成检查点；前端呈现"多人同时干活"。产出：真正并行的团队协作。

**阶段 10 · 厚 agent 接入、最终 Benchmark 与产品化打磨**：把 Coder/Tester 可选接入外部 agent（opencode/pi/OpenHands）作为厚执行器；错误恢复、模型调优、界面细节与体验、一键部署，扩展可处理的任务类型；经外部 adapter 接成熟 Coding Agent Benchmark 小型固定子集，完成系统变体重复对照、方差/失败分类和可审计报告，再据实写 README 与产品介绍。产出：可直接演示且有工程证据的完整产品。[2026-08-23 架构决策更新] **厚 Agent 接入延后至此阶段，此前（阶段 0–9）不进行薄/厚动态切换**，所有 Worker 统一为薄 Harness 执行器。

每阶段结束继续以确定性集成测试与 G5 真实链路作为阻断门禁；自阶段 6 起并行维护一组固定 Eval 任务，逐阶段追加 Channel、热插拔、humanGate、抢占与真并行场景。Eval 的模型运行允许方差并输出结构化结果，不能用一次跑分替代门禁或宣称统计结论。

### 十八、简历/面试视角（把产品讲出深度）

虽然定位是纯产品，但它作为简历项目仍有强讲点：**编排层**="能手写多 agent 状态流转与回环控制"；**真并行 + 配合式抢占**="知道 LLM 不能硬中断，用协作式抢占 + 安全点 + checkpoint 做到'改主意后全员响应新计划'，并用 git worktree 隔离并行、集成检查点合并，兼顾提速与一致"；**上下文工程**="知道多 agent 头号病灶是上下文割裂，并用共享黑板 + 角色投影 + 结构化交接把它治住，保证产品不随对话变长而崩"；**自适应编排**="不盲从多 agent，让协作规模随任务复杂度伸缩"；**群聊 + 多形态通信**="把人机协作做成可指挥的控制面，agent 能广播/私聊/拉小群像真实团队，同时用展示层/上下文层双层分离保证群聊不污染 agent 内部上下文"；**Leader 唯一裁决 + 异议双轨**="用单一权威兜底决策不一致，正面回应《Don't Build Multi-Agents》，agent 能顶嘴但阻塞/建议分轨、最终由人拍板"；**角色热插拔**="把 agent 团队做成可编辑的活组织——角色是数据不是代码（注册表 + 通用 worker 节点），离职强制交接、新人入职读交接接手"；**薄/厚执行器抽象**="想清楚了什么该自研、什么该包外部 agent——薄 agent 换可控性、厚 agent 换现成能力，同接口可切换"；**工程 Eval**="不靠架构自述证明效果，复用成熟任务评最终产物、自建协作语义 Grader 验证投影/抢占/Leader/并行，并报告成功率、成本、时延与方差"；**沙箱安全**="考虑了 agent 执行代码的隔离"；**MCP 工具层**="用业界标准协议解耦"。

高频追问需提前备答（开发过程中就记录，别临时编）：为何选纯 TS 全栈、为何复用 DeepSeek Harness 当薄 agent 内循环、为何不上 LangGraph.js/Mastra 而自研轻编排；群聊会不会让上下文爆炸、你怎么防（双层分离，且 Harness 的 `deriveMessages` 从事件流投影天然契合）；私聊/小群的上下文怎么隔离与回流；LLM 不能硬中断你怎么做抢占（Harness 的 turn-stopping + inbox steering + 安全点）；并行 worker 的状态怎么保证一致；leader 决策和 PM 需求矛盾时系统怎么走；自适应误分类怎么兜底；如何防死循环和控成本；哪些自己写、哪些复用 Harness、哪些包外部 agent。

### 十九、主要风险与应对

**群聊退化成全量广播（本项目最大的技术坑）**：严格执行"通道决定可见性、投影决定消费"的双层分离，agent 永不直接吃群里的原始消息流。**并行写乱共享状态**：一切写走 reducer + 字段级合并语义 + 代码以 worktree 为准 State 只存引用。**抢占延迟与撕裂**：配合式抢占接受秒级"到安全点"延迟以换一致性，绝不硬杀 LLM 造成半截状态。**厚 agent 不可控**：外部 agent 只接边界清晰、上下文可打包的子任务，只在沙箱内运行、只经受控接口拿产物，且只能在任务边界处介入、不能细粒度抢占。**死循环/不收敛**：`iterationCount` 硬上限 + 超限人工兜底。**沙箱安全**：严格网络/资源限制，文件限工作目录，不执行危险脚本。**中途删角色留下孤儿职责**：离职走"先暂停 → 强制交接文档 → 指定接手/招替补 → 才停用"的流程，无人接手则标记空缺并升级人工，绝不静默丢责任；Coordinator 不可删。**决策不一致/扯皮**：leader 唯一裁决 + 异议双轨 + 决策权威级别，不做 agent 自动共识。**成本失控**：分角色用不同档位模型、长上下文压缩、并行度上限。**框架锁定**：工具走 MCP、并发与业务逻辑与框架 API 解耦。**范围膨胀（长期打磨最大的坑）**：严格按阶段推进、先回合制后并行，每阶段有可演示产出才进下一阶段，避免无限加功能却始终不能演示。

### 二十、项目与多租户层（单用户 · 多项目隔离）

**为什么需要这一层。** 前面十九节都在讲"一个任务如何被一个 agent 团队协作完成"，但真实使用中，同一个用户（leader）往往**同时在推进多个项目**——上午调项目 A 的后端、下午起个项目 B 的原型。这两个项目的团队、代码库、沉淀的约定、群聊历史必须**互不串味**：项目 A 的架构决策不该污染项目 B 的 agent 上下文，项目 B 的实验代码也不该被 A 的 worker 看到。所以在"任务"之上再抽出一层**项目（Project）**作为长期存在的租户边界。层级关系是：**项目（Project）⊃ 任务（AppState）⊃ Worker**——项目是持久的世界，任务是项目里的一次协作，worker 是任务里的一个执行体。**注意与第三节的区分：这里做的是"单用户下的多项目隔离"，不是"账号级多租户/权限/计费"（那才是明确不做的）。**

**隔离模型：独立世界 + 全局调度器。** 每个项目是一个**自包含的 ProjectRuntime**——拥有各自独立的编排器、沙箱根目录、角色注册表、知识库、群聊集合、成本账本，彼此**默认全隔离**（互不可见）。项目之上只有一个很薄的**全局调度器（GlobalScheduler）**，它不介入任何项目内部逻辑，只做两件全局的事：其一，**并行配额分配**——所有项目共享一个全局并行上限（【假设】默认 3 个 worker 同时跑），并保证**每个活跃项目至少保底 1 个**槽位，避免某项目饿死；[2026-08-23 架构决策更新] 某项目卡在 humanGate 等 leader 时会**终止（Terminate）该项目 Harness 进程、释放资源**（名额自动交还全局池），leader 裁决后再按 `safePoint` 事件游标重 Fork 恢复（终止并分叉，详见详细设计第 8 节；阶段 0 简化为"任务即进程，结束即销毁"）。其二，**成本统一核算**——各项目的 token/费用汇总到全局账本，便于 leader 总览。这样"多项目"不是把系统改复杂，而是"多个独立世界 + 一个调度总管"。

**多任务但初期退化单任务。** 项目内**允许多个任务并存**（`activeTaskIds`），但初期**退化为单任务**——一个项目同时只跑一个任务，把复杂度后置。为此 `AppState` 从"全局唯一状态"降级为**任务级状态**，并带一个 `projectId` 回指所属项目；跨任务/跨项目的持久内容（约定、架构、术语、决策）不放在 `AppState` 里，而是上移到项目的**知识库**。

**[2026-09-01 架构决策更新]通信所有权随层级对齐。** Channel 是项目团队的长期通信空间，因此注册表只存在于 `Project.channels`，并由项目级持久化端口以原子 JSON 快照维护；任务只在 `AppState.messages` 保存本任务产生的消息事实。传输层用 `projectId/taskId` 绑定两者：main 是项目级唯一大群，sub 在项目注册表中必须绑定创建它的 `taskId`。局部上下文引用使用 `{taskId,msgId}` 而非裸 `msgId`，避免跨任务歧义；角色 inbox 从注册表与任务消息派生，不持有第二份事实。

**团队知识库（两层结构）。** 每个项目有自己的知识库，分两层，对应"要不要长期喂给 agent"：

- **精炼层（refined，小、注入投影）**：项目的稳定共识——编码约定、架构总览、术语表、代码地图（文件→职责）、长期决策台账、角色默认配置。它很小，**随角色投影一起注入**每个 worker 的上下文，让新任务/新 agent 一上来就"懂这个项目的规矩"，无需重新摸索。
- **归档层（archive，大、按需检索）**：历史任务摘要、完整群聊消息、旧补丁等。它很大，**不进上下文**，只在需要时经 RAG 检索命中片段——呼应第八节"以产物为锚、按需检索"的纪律。

**知识库靠谁维护——Librarian 蒸馏回灌。** 知识库不会自己长出来。引入一个 **Librarian（图书管理员）职责**：在**每个任务收尾**时，把这次任务里产生的、值得沉淀的东西（新确立的约定、被推翻/新增的架构决策、复用性高的代码片段位置）**蒸馏**进精炼层，把原始过程**归档**进归档层。Librarian **默认由 Coordinator 代管**（不单设角色、省编制），但因为角色是数据可热插拔，项目大了可由 leader**按需招募**一个专职 Librarian。这样知识库是"任务跑完自动增厚"的，而非人工维护。

**跨项目：默认拒绝 + 受控导入。** 项目间**默认零共享**（连"项目 A 有个好用的缓存实现"这种事，项目 B 的 agent 也看不到）。确需复用时走**受控导入**流程，而非打通实时引用：leader 显式发起导入 → 把源项目的目标内容（一段约定 / 一份代码 / 一条决策 / 一条知识库条目）**快照拷贝**进目标项目 → 落一条**导入台账（ImportRecord，需 leader 批准、留审计痕迹）**。导入的是**副本不是链接**——源项目此后怎么改都不影响已导入的副本，避免跨项目的隐式耦合。这既满足"想复用"的现实需求，又守住"默认隔离"的边界。

**Leader 收件箱：混合式（存储分项目 + 呈现全局）。** 多项目并行时，leader 需要处理各项目冒上来的 humanGate（卡点/裁决/升级）。采用**混合式**：**存储上分项目**——每个项目维护自己的 humanGate 队列，建议型异议(advisory)只留在项目内、不打扰全局；**呈现上全局聚合**——一个**全局收件箱（GlobalInbox）只把各项目的阻塞型(blocking)待办**汇总到一处，让 leader 一眼看到"哪些项目正卡着等我"。点进某条待办即**带 leader 进入该项目的上下文**去处理。配合前面"[2026-08-23 架构决策更新]卡在 humanGate 的项目终止进程交还槽位、裁决后按安全点重 Fork（终止并分叉）"，就实现了"leader 不必盯着单个项目、被真正需要决策的事牵引着走"的多项目指挥体验。

**产品与讲点价值。** "我的产品不是只能做一个项目的玩具——它是一个能同时托管多个独立项目世界的工作台：每个项目有自己会随任务自动增厚的团队知识库，项目间默认隔离、要复用得走带审计的受控导入，而 leader 用一个全局收件箱统一指挥、被真正需要拍板的事牵引。"这把"多 agent 协作"从单任务演示升级为**可长期驻留使用的产品**。

### 二十一、已定的设计决策（蓝图定稿）

蓝图阶段的开放问题已全部收口，进入详细设计。以下为已拍板、直接落地的决策：

通信统一为单一原语——一切皆群聊（Channel = 参与者集合），"广播/私聊/小群"只是成员规模不同的用法，且 leader 恒为每个群成员（对任意对话透明、可随时介入）；小群以 agent 自发为主、Coordinator 只做轻量治理；执行采用真并行（独立异步 worker + 配合式抢占 + worktree 隔离 + 集成检查点），但先回合制跑稳、阶段 9 再升级；leader 为唯一裁决者、不做 agent 自动共识；agent 可提异议、分阻塞/建议双轨；决策台账带权威级别、leader 最高；角色可热插拔、离职强制交接；执行器分薄/厚，薄为主、厚（包 opencode/pi/OpenHands）用于边界清晰的重编码；首批验证任务=单文件小工具/算法（阶段 0 用此类任务跑通状态流转与写-测-修回环）；运行环境[2026-08-24 选型同步]阶段 0 用本地临时目录 Mock、阶段 1 起用本地 Docker（每任务一隔离容器，后续可平滑切 E2B）；人工卡点粒度=每阶段确认（需求→设计→编码→测试→评审每个阶段切换都过 leader 确认）；**角色沿用这 6 个（Coordinator/PM/Architect/Coder/Tester/Reviewer），PM 按"条件触发、清晰规格跳过"设计；不预置 Debugger/Doc——角色是数据可热插拔，需要时由 leader 招募**；**真并行的并行度上限默认 3 个 worker/worktree 同时跑（演示画面清晰、成本可控），集成合并冲突默认升级 leader 裁决（贴合唯一裁决设定，后续可加自动合并选项）**；**在任务之上新增项目层：项目=独立世界（各自编排器/沙箱/角色注册表/知识库/群聊/成本账本），其上一个薄的全局调度器统一分配并行槽位（默认上限 3、每活跃项目保底 1、卡在 humanGate 时终止进程交还名额、裁决后按安全点重 Fork（[2026-08-23 架构决策更新]终止并分叉））与成本核算；项目内允许多任务但初期退化单任务，**`AppState` **降为任务级并带** `projectId`**；每项目两层知识库（精炼层注入投影 + 归档层 RAG），由 Librarian（默认 Coordinator 代管、可按需招募）在任务收尾蒸馏回灌；跨项目默认零共享、复用走受控导入（快照拷贝进目标 + 带审计的导入台账 + leader 批准，导入副本非链接）；leader 收件箱混合式——存储分项目、呈现上全局聚合各项目的阻塞型待办**。

确认后进入下一份文档——**详细设计方案**（State 精确 schema、各角色 prompt 与工具清单、编排节点/路由定义、并发 worker 与配合式抢占协议、通信模型（单一 Channel 原语）、执行器类型接口、MCP server 接口签名、沙箱与 worktree 接口、上下文投影与自适应路由的具体规则），再据此开始阶段 0。（该文档已完成，见 v2.0）

**[2026-08-31 架构决策更新]D6——消息提交与投递分离：** 应用服务先通过 `applyMutations()` 把消息提交并持久化到任务 State，成功后再发布 `MessageCommitted`；L3 `MessageBus` 只投递已提交事件，不直接修改 State。SSE/UI 只接收不含 `payload` 的展示信封，实时流不是事实源。SSE 建连必须无缝衔接持久快照与实时尾流，允许因竞态重复但不允许漏消息，消费端按 `msgId` 去重；同一次逻辑发送的网络重试必须复用原 `msgId`。

**[2026-09-01 架构决策更新]D7——Channel 与消息作用域：** `Project.channels` 是 Channel 注册表唯一真相源，必须经项目级原子 JSON 快照持久化且可重启恢复；`AppState.messages` 保存任务级消息，传输信封显式携带 `projectId/taskId`。项目只有一个 main 群；sub 群在项目内唯一且必须绑定 `taskId`，局部上下文以 `{taskId,msgId}` 引用任务消息。角色 inbox 归 `comm/channels` 的可重建读模型，从 Channel 注册表 + 任务 State 派生，保留消息原始因果顺序；`to` 只产生定向优先级元数据，不改可见性或重排事实。MessageBus 仍只投递已提交事件，不保存 inbox。阶段 5 只派生 main 视图，阶段 6 启用上述持久注册表、participants 校验与任务绑定 sub 群。

**[2026-09-01 架构决策更新]D7 升级恢复补充：** 已有任务 State 与项目 Channel 快照必须成对可恢复；仅在 `state.json` 存在且 `channels.json` 缺失时，以当前合法 roster create-if-absent 补建 main。损坏/非法 Channel 快照不自动修复。角色列表排除保留身份 `leader` 且不得重复；对象属性顺序不构成 Channel 变更；Channel 注册表与 localContext 数组顺序保留，participants 顺序按下述 Phase 6 集合规则处理。

**[2026-09-01 架构决策更新]D7 Phase 6 生命周期补充：** participants 是集合而非有序业务数据，必须标准化为 leader 在前、其余角色按 enabled roster 顺序；仅输入顺序不同不得触发 revision。新建 sub 必须持久化 `taskId/threadId/topic/createdBy`，同一 `taskId+threadId` 只允许一个生命周期实例。6.1 期间已持久化且缺少这三项的 legacy sub 不是损坏快照：6.2 首次初始化时在项目串行区内一次性补为 `threadId='legacy-'+channelId`、`topic='Legacy channel '+channelId`、`createdBy='leader'`，通过正常 revision commit 写回；三项部分缺失仍视为损坏并 fail-fast。open/close 由按项目串行的应用服务通过既有 `ProjectChannelStore` 完成，稳定 `actionId` 提供幂等，actor 由组合根绑定；main 不可关闭，sub 仅 leader/participant 可关闭，重复 close 为 no-op。

**[2026-09-01 架构决策更新]D8——阶段化部署边界：** 阶段 5–9 的 `.data` TaskStateStore/ProjectChannelStore + 进程内 MessageBus/SSE 只承诺受信任单用户边界内的单实例自托管后端；Vercel 在此期间只可承载前端，后端仍自托管。完整 Serverless/水平扩展后端必须先同时提供外部耐久 `TaskStateStore`、`ProjectChannelStore` 与跨实例事件传输，由阶段 10 部署任务根据实际需求裁决，不得将本地 `.data` 或进程内订阅宣称为 Vercel 后端持久化。

**[2026-08-31 架构决策更新]D9——Leader Intent 单入口与阶段化执行：** Leader 发言与指令统一经 `POST /api/messages`；服务端从 `display` 解析意图并生成 agent `payload`，不信任浏览器自报意图。消息与本阶段可执行动作在同一任务串行区内原子、幂等提交后才投递。Phase 5 只执行经校验的开头单一 `@ROLE` 定向激活（写 `nextRole`）与普通 chat；Coordinator 只消费最新 applied assignment 一次，以 `sourceMsgId` 控制事件确认并把 instruction 带入 Coordination Ledger。其余动作必须显式 `rejected/deferred`，sub 群归 Phase 6，humanGate/objection 裁决归 Phase 8，需要抢占的新需求/决策/优先级变更归 Phase 9，禁止临时 command 总线绕过 State 或静默宣称成功。

**[2026-09-01 架构决策更新]D9 Phase 6 Channel 生命周期补充：** Leader 的 `/channel open ROLE[,ROLE...] <topic>` 与 `/channel close <channelId>` 仍从 `POST /api/messages` 解析，复用稳定 `msgId` 为 actionId；agent 在 Step 安全边界从既有通用 output 产出同构动作，actor 由运行时绑定。因 Channel 与任务消息分属两个持久真相源，执行采用可重试 saga：先幂等提交 Channel，再经 D6 提交原消息/稳定 lifecycle announce；后一步失败不回滚 Channel，重试补齐且不重复操作。此例外不改变 ProjectChannelStore/TaskStateStore/MessageBus/Executor 签名，也不授权临时 command 旁路。

**[2026-09-01 架构决策更新]D10——Phase 5 Web 编排执行桥接、串行退化与真实性门禁：** 新任务创建/启动是生命周期操作，不复用或绕过 D9 的任务内消息语义；启动后的 Leader 发言仍只走 `POST /api/messages`。单实例组合根复用既有 `runOrchestration()`/Harness/沙箱与端口；Phase 5 全实例最多一个活动 run，不同任务终态可共存，GlobalScheduler/多任务并行不得抢跑 Phase 9。每个可展示的 Coordinator/Worker 进展必须先持久化 State 再投递 SSE。终态产物须归档到 `.data/projects/{projectId}/tasks/{taskId}/artifacts/` 并持久化引用，然后释放 Harness、MCP/Git client 与 Docker 容器；最终 State/消息/产物可刷新恢复但不依赖活执行资源，活动 run 的进程重启自动恢复延期。静态种子消息或彼此分离的编排测试与 UI 演示不得冒充 Web 触发的真实闭环。
