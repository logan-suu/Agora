### 一、项目定位与目标

这个项目要做的不是"再造一个 agent"，而是构建一套**多 agent 协作编排系统，并以群聊为产品形态呈现**：底层单 agent 的运行时（调 LLM、工具调用、推理循环）复用成熟框架，核心工作聚焦在协作层——如何把一个软件开发任务拆给多个有明确职责的 agent，如何让它们像真实团队一样在群里**并行**协作，如何在关键节点让人以 leader 身份介入指挥并**裁决冲突**，以及如何安全地执行 agent 产出的代码。

因为是产品优先，成功标准围绕"做出一款能用、好看、像真实团队"的完整产品：

一是**能跑通闭环**，给定中小规模编码任务，系统能自主完成"需求 → 设计 → 写-测-修 → 评审"并产出可运行代码与测试。二是**产品形态完整且生动**，以群聊界面为主形态实时呈现多 agent 协作，agent 之间能广播、私聊、拉小群、**同时并行干活**，用户作为 leader 可随时指挥并对分歧拍板；配可观测（trace/日志）、可在本机一键启动、能直接演示。三是**协作可控**，每个 agent 职责边界清晰，流程可断点、可人工干预、可在中途插入新决策让全员响应。四是**工程质量稳**，上下文不因多 agent 而退化崩溃（见第八节），并行不因共享状态而写乱（见第十三节），系统行为连贯可预期。五是**可扩展**，新增角色或替换模型/工具，改动局限在 RoleSpec、Harness 扩展点与 MCP 适配层；任意自定义角色的自主路由仍按 DEF-016 验收。

### 二、背景与竞品格局（产品设计的立足点）

「多角色 agent 分工写软件」不是新概念。开源侧，**ChatDev**（虚拟软件公司，CEO/CTO/程序员/测试等角色，34k stars，2026 年 2.0 已转型为通用多 agent 编排平台）、**MetaGPT**（把 SOP 编码进多 agent 协作）、**OpenHands**（开源自主编码 agent，可自托管）都做过类似实现。商业侧则相反——**Devin、Claude Code、Codex CLI** 等主流编码 agent **大多回归"单个强 agent"路线**，不做角色拆分。但另一侧的信号是：**Cursor 等已开始做"多 worktree 并行 agent"**——同一任务开多个 git worktree 让多个 agent 分头干、最后择优或合并，验证了"并行 + 隔离 + 集成"这条工程路线的现实价值。

最关键的行业信号：Devin 母公司 Cognition 发过影响很大的《Don't Build Multi-Agents》，论点是把编码拆给多个子 agent 常"适得其反"——**子 agent 之间上下文割裂、决策不一致、协调开销大**，不如一个握有完整上下文的强 agent。

对本项目的意义不是"这个方向错了"，而是给出两条硬性的**产品设计红线**。其一，多 agent 的价值在于分工带来的可控性、可审查性、以及"像真实团队"的生动协作体验；但**群聊绝不能被做成"所有 agent 都读群里全部消息"的全量广播总线**，否则就正好撞进上面批评的那个反模式。其二，**决策不一致必须有唯一权威来兜底**——本项目不做 agent 之间的自动共识（那正是"决策不一致、协调开销大"的温床），而是把 leader 设为唯一裁决者，agent 可反馈可异议、但最终由人拍板。因此本项目不做"又一个 ChatDev 复刻"，而是把"生动的群聊并行协作体验"和"底层受控的上下文工程 + 单一权威裁决"这两件看似矛盾的事同时做好（详见第八、十、十一、十四节）——这正是它作为产品的独特之处。

### 三、范围与边界（最关键的一节）

**我们要设计和实现的（项目主体）：** 协作编排拓扑（各角色如何串联、何时循环、何时分支）；角色职责划分与各自的 system prompt / 工具集；共享状态结构（state schema）与通信协议；**多形态通信（全员广播 / 私聊 / 临时小群）**；**真并行执行运行时（独立异步 worker + 配合式抢占 + worktree 隔离 + 集成检查点）**；**人工介入与 leader 冲突裁决（异议阻塞/建议双轨）**；**角色热插拔与团队动态编制（招募 / 离职 / 强制交接）**；**基于 DeepSeek Harness 的统一执行器适配（复用单 agent 内核，自研协作控制）**；**跨 agent 上下文工程机制**与**自适应编排机制**；工具经 MCP 的标准化接入；代码沙箱执行的接口与安全边界；**群聊式前端界面与可观测面板**（产品形态）。

**我们复用而不自研的（底层轮子）：** 单 agent 执行内核（**DeepSeek Harness** 提供的可替换 agent loop、Turn/Step 两层模型、工具三段流水线、事件溯源会话日志与 fork/resume/replay）；LLM 的 API 调用与重试（Harness 的 provider adapter）；MCP 协议的 client/server 实现（TS SDK）；沙箱底座（Docker，经 dockerode 驱动）；git worktree 的底层能力（simple-git）；现成的聊天 UI 组件与流式通道（Next.js/React + SSE + HTTP POST）。

**明确不做的：** 自研模型或微调；**账号级多租户体系（SaaS 用户账号 / 权限 / 计费）**；生产级高可用与大规模并发；agent 之间的自动共识/投票机制（一律由 leader 裁决）；论文级大规模排行榜复现、为刷榜定制 Agent 或自建通用 Benchmark 任务生态。Agora **要做**面向工程验证的渐进式 Eval Suite：复用成熟 Coding Agent Benchmark 的任务/环境/Outcome Grader，自建少量 Agora 协作语义场景与 Process/Efficiency/Safety Grader，用于回归、架构取舍和秋招证据；它不替代各阶段集成测试或 G5 真实链路。（注意：这里排除的是"账号级多租户"；本项目**确实要做**单用户下的**多项目隔离**——同一 leader 可同时开多个项目、各自独立的团队/沙箱/知识库/群聊，见新增第二十节，二者不是一回事。）

### 四、总体架构

系统自上而下分四层。

**编排与并发层（Orchestration & Concurrency，自研）**：**不上重量级编排框架**，而是在 Harness 的事件流之上自研一层轻量编排——只有几个通用节点（coordinator / worker / integrate / humanGate）加一个 coordinator 路由函数，配一个全局共享 State。这一层决定"谁在什么条件下做什么、下一步交给谁"，并把"被激活的角色"实例化为**独立异步 worker** 同时运行，负责配合式抢占、worktree 分配与集成合并（见第十三节），也是自适应编排、leader 指令与冲突裁决的落点。之所以自研而非套框架：其一，编排图本身很小（4 个通用节点，角色是数据不进图）；其二，Harness 已自带事件溯源、checkpoint/fork/resume、inbox/steering，把"重框架"该给的 checkpoint 与人在环打断能力大半提供了，再叠一个 LangGraph 只会功能重叠。Node 的事件循环 + Promise 天然适配"多 worker 各自长跑、到边界让出"的并发模型。

**角色 Agent 层（Agents）**：每个 agent 有独立职责、system prompt 和工具集，统一以 **DeepSeek Harness** 的官方 agent loop 为内核。Agora 通过 `HarnessExecutor` 和扩展点（`agent/pre-step`、`agent/request`、`agent/turn-stopping`）实现角色投影、模型路由与配合式抢占；每个顶层 worker 有独立 Context/Agent/session。角色、上下文和协作控制由 Agora 自研，loop、事件溯源、会话持久化与单 agent 压缩复用 Harness。

**工具与执行层（Tools & Execution）**：所有对外部世界的操作（文件、git、测试、静态检查、执行代码）都封装成 MCP server（TS SDK），agent 通过统一协议调用（薄 agent 经 Harness 的工具三段流水线 `pre-execute → execute → post-execute` 调用）。代码执行隔离在沙箱中（Docker，dockerode 驱动），并行 worker 各自绑定一个 git worktree/分支（simple-git），agent 只提交代码、拿回结果，永不直接触碰宿主机。

**基础设施层（Infra）**：LLM provider（经 Harness adapter）、沙箱运行时、git worktree 池、持久化（Harness 事件溯源会话日志即天然 checkpoint/replay 源，另加产物存储）、可观测（从同一条事件流派生 trace / 日志）、以及驱动群聊界面的流式消息总线。

数据流：任务进入 → 编排层按图调度并选定并发档位（拓扑随复杂度自适应）→ 并发层把选中角色拉起为并行 worker，各读结构化上下文投影、在各自 worktree 内经 MCP 与沙箱交互、按协议在大群/小群中交接 → leader 可随时插话指挥、注入新决策、裁决异议（触发配合式抢占与重规划）→ 到集成检查点合并各 worker 产出 → 循环直到收敛 → 产出代码与产物。

### 五、角色划分【假设：6 个角色，可增减】

按软件团队隐喻划分六个角色，每个只对共享 State 的特定部分负责，职责单一。这 6 个是**默认在编阵容**——角色以数据（role spec）定义、可热插拔，leader 能招募新角色或让现有角色"离职"（详见第十二节），唯 Coordinator 作为调度内核不可移除。所有角色统一使用 HarnessExecutor（见第十六节），角色差异由 RoleSpec、模型路由和工具白名单表达。

**Coordinator（协调者 / 调度大脑）【薄】**：不写代码也不定义需求，只做纯调度——根据任务复杂度与运行时反馈决定激活哪些角色、如何并行、判断是否收敛或升级给人。是编排、自适应、并发生命周期与通信路由的中枢。

**Product Manager（产品经理）【薄】**：把含糊的 `goal` 转成结构化需求（用户故事、验收标准、非目标），定义"做什么"，也是 Tester 客观验收判据的来源。当 leader 的新决策与既有需求矛盾时，PM 是提出反馈/异议的主要角色（最终仍由 leader 裁决）。【假设】由 Coordinator **条件触发**：需求含糊才走、明确规格则跳过。

**Architect（架构师）【薄】**：在需求之上定义"怎么做"——模块划分、接口约定、关键数据结构、技术选型，产出结构化设计写入 State。

**Coder（编码者）【Harness】**：依据架构与待办产出/修改代码补丁并提交沙箱，读取测试与评审反馈迭代。循环中最活跃，也是并行的主力。重编码子任务仍由独立 Harness worker 在规范 worktree 内完成。

**Tester（测试者）【Harness】**：编写并在沙箱运行测试，把编译错误、测试结果、覆盖率回填 State。测试不过就把控制权推回 Coder，是回环触发者。

**Reviewer（评审者）【薄】**：做质量、规范、安全审查，产出评审意见，也是人工卡点的载体。【假设】通过与否需人确认才进入收尾。

### 六、共享状态设计（State Schema）

所有协作信息集中在一个可序列化 State 对象里，是多 agent 唯一的"真相源"。初步字段（最终以代码定稿）：

任务层：`taskId`、`goal`、`requirements`（结构化需求）、`subtasks`、`phase`（clarifying / planning / coding / testing / review / done）、`complexity`（复杂度评估信号，供自适应编排用）。

设计层：`architecture`、`conventions`。

代码层：`repoSnapshot`（引用而非全量）、`appliedHistory`；当前代码事实只经结构化 `WorktreeRef`（path/branch/baseCommit/headCommit）与 `integration` 传递，不保留无消费者的全局 `pendingPatch`。

反馈层：`testResults`、`reviewComments`、`iterationCount`（防死循环上限）。

并发层：`workers`（当前活跃的并行 worker：角色、状态 running/paused/done、绑定的 worktree/分支、当前安全点、执行器类型）、`integration`（集成检查点状态：待合并分支、合并结果、冲突项）。

协作层：`messages`（任务级消息事实，含所属群 `channelId` 与 `threadId`，见第十一节）、`nextRole`、`humanGate`（Phase 8 起仅表示当前活动卡点，必须含稳定 `gateId`、打开时间与持久 `safePointRefs`；已裁决历史留在规范 Leader 消息而不堆在活动字段）、`objections`（不可变异议事实；未决视图由异议事实与规范 Leader 裁决消息读时派生，见第十四节）、`handoffPackets`（结构化交接包，见第八节；也承载离职交接文档）、`decisionLedger`（决策+理由+**权威级别**台账，leader 决策为最高权威，见第十四节）。`roster` 与 Channel 注册表都属项目级协作事实，按 D12 存于同一原子快照，不在 `AppState` 复制。

并发写入用 State 合并函数（reducer 语义）明确各字段合并语义（如 `messages`/`decisionLedger`/`objections` 追加、`testResults` 覆盖、`workers` 按 workerId 归并），避免多 worker 并行写冲突（并发一致性详见第十三节）。

### 七、编排流程（协作拓扑）

主流程是一个带回环、**拓扑可随复杂度伸缩**、且**可并行推进**的有向图：

入口进 **Coordinator**，它评估任务复杂度并选择起始拓扑与并发档位（见第九、十三节）。含糊需求先经 **Product Manager** 产出验收标准再回来；随后视需要进 **Architect**；进入 coding 阶段后，Coordinator 可把多个可独立推进的子任务**同时**派给多个 Coder（各占一个 worktree）并行开工，9.4 的 Tester preparation 固定关闭；测试由集成后的 validation Tester 负责，未来只读准备模式需独立验收后启用。

**核心回环**：Phase 9 每个拓扑波次先等待全部 Coder 收敛，再合并到专用 integration worktree；单一 Tester 从该精确结果创建独立验证 worktree，编写并执行测试。通过的验证提交成为下一波共同基线，失败按有界返工路径处理；全部波次通过后，Reviewer 只读评审最终累计验证提交，Leader 经 D16 终审后才能置 done。禁止先测试分散分支、再把未经整体测试的合并结果当最终产物。Phase 0–8 保留顺序小环的历史回归路径。

**问答与升级链**：任一 worker 卡住可发 `question`（带 `threadId`）定向问某角色→被问方挂起该线程作答→发起方 resume；答不了则沿 `threadId` 级联升级（Coder→PM→Leader），最终落到 `humanGate`。

**抢占与重规划**：leader 中途注入新决策或裁决异议时，Coordinator 广播暂停信号→各 worker 跑到安全点存 checkpoint→协调层改写共享 State→worker 带新上下文 resume（详见第十三、十四节）。

关键控制：`iterationCount` 硬上限（【假设】默认 8 轮）；任何角色遇不可解阻塞可主动置 `humanGate`；并行度上限由 Coordinator 按 worktree 池与成本约束控制。

### 八、亮点一：跨 Agent 上下文工程（产品稳定的地基）

**要解决的问题。** 多 agent 的头号死穴是上下文割裂：naive 做法要么把完整对话史全丢给下游（token 爆炸、关键信息被稀释），要么只传最终产物（下游看不到"为什么"，重复劳动甚至与上游矛盾）。尤其做成群聊后，最容易犯的错就是"让每个 agent 都读群里所有消息"——这会直接把产品拖垮。所以本项目把上下文当成**需显式设计的工程对象**，而非消息流的副产品。这是产品能稳定运行、不随对话变长而崩坏的地基。

**机制（四个抓手）。** 其一，**共享黑板作唯一真相源**：agent 间不流转原始对话 log，只读写结构化 State。其二，**角色投影视图**：每个 agent 只拿到与其角色相关的 State 切片（Coder 需要架构约定 + 当前失败测试 + 相关文件引用，不需要 PM 的完整讨论），省 token 又减干扰。其三，**结构化交接包（handoff packet）**：交接时生成紧凑结构——做了什么 / 关键决策及**理由** / 遗留问题 / 相关文件路径；理由入 `decisionLedger`，防止下游推翻上游。其四，**以产物为锚、按需检索**：代码真相在沙箱/仓库，agent 间传文件路径+行号引用而非贴代码（避免版本漂移），长历史做摘要压缩并保留检索入口。

**统一执行与投影。** 所有角色均由 HarnessExecutor 消费精细投影，并遵守 D1、D4、D15、D17；初始 Step、reproject 与 Fork resume 走同一路径，没有外部黑盒简报或投影例外。代码通过文件引用与受控 MCP 工具读取。

### 九、亮点二：自适应编排

**要解决的问题。** 固定流水线对简单任务是浪费（给"加个缓存"也走完整 PM→架构→编码→测试→评审），而多 agent 协调开销只有过了复杂度阈值才回本。所以拓扑不写死，随任务复杂度动态伸缩，让产品对简单任务反应快、对复杂任务够稳。

**机制（两条路线结合）。** 路线一 **前置分类 + 分层拓扑**：入口用轻量路由估算复杂度，选档位——Tier 0 单 agent 直接上 / Tier 1 编码↔测试小循环 / Tier 2 完整团队（并可开并行）。路线二 **反馈式升级（escalation）**：默认走最便宜路径，失败再逐级加人（单 agent 不行→加 Reviewer→再拉 Architect 重设计），不依赖前置分类准确性、更鲁棒。二者结合：前置分类定起点，反馈升级兜底。（这也是"PM 条件触发"的推广——整个团队按需激活。）

**如何实现。** 即自研轻编排里 Coordinator 节点的**条件路由函数**：读 `complexity` 与上一轮结果决定 `nextRole` 与并发档位，而非走固定图；这就是 supervisor 模式运行时动态 dispatch。落到产品体验上，就是"简单需求几步就搞定、复杂需求才拉齐全队并行推进"，群里的参与人数与讨论深度随任务自然变化，更像真实团队。

**[2026-08-31 架构决策更新] Coordinator 双层进度台账的 Agora 落法。** MagenticOne 的 Task Ledger（已确认事实/假设/结构化计划）+ Progress Ledger（请求满足、回环、进展、下一角色、指令）只借结构，不引入 LLM orchestrator：Coordinator 在每个安全点用纯函数从 State + 已选 Route 确定性生成严格 JSON，并以 `messages.payload.kind='coordination_ledger'` 的结构化事件追加持久化（不扩 `AppState`/`Mutation` 接口）。`isInLoop=true` 或无结构化进展记一次 stall，连续 3 次重建外层 facts/plan 并递增 revision；`iterationCount=8` 仍是最终人工升级上限，两者分工不变。机器只能置 `completionCandidate`，`isRequestSatisfied` 始终由 leader 权威持有；Phase 4 只落该裁决接缝，普通完成路径的完整 humanGate Terminate & Fork 循环仍按路线留 Phase 8，避免阶段抢跑。台账不是原始群聊广播：COORDINATOR 读完整台账，业务角色只读自己的 plan step + confirmed facts + 当前 instruction。Coordinator 同一接缝在所有真实 worker→worker 角色切换时追加 `handoffPackets`，使进度、路由和交接保持同一结构化真相。

**[2026-09-05 架构决策更新] D16——任务完成权威闭环。** TESTER 通过与 REVIEWER `approved` 只产生 `completionCandidate`，不得直接把请求判定为已满足或进入 `done`。Coordinator 以该轮 REVIEWER dispatch 后唯一、且满足 `[A-Za-z0-9][A-Za-z0-9._:-]*` 的稳定 verdict id 产生 `reason='completion_confirmation:<reviewId>'`、`options=['approve_completion','request_changes']` 的 D4 humanGate；Leader 仍经 D9 `/resolve-gate` 单入口裁决。`approve_completion` 可省略理由并由服务端写入规范默认 rationale，`request_changes` 必须携带非空自由文本理由；同一次 Task State commit 写规范 Leader 消息、`id='task-completion-resolution:'+actionId` 且 `authority='leader'` 的 Decision、resolution receipt 与 clear gate。恢复后 Coordinator 只从经消息/Decision/receipt 交叉验证的同一 review 裁决派生结果：approve 令 `isRequestSatisfied=true` 并 finalize，request changes 令其保持 false、按现有保守策略重开待修改 subtasks 并路由 CODER；新一轮 REVIEWER verdict 使用新 gate，旧裁决不得越轮复用。两条路径都遵守 D4 全新 context、稳定 resumed 事实与幂等重放；缺失、冲突或跨 review 引用 fail-closed。

### 十、亮点三：群聊式协作界面（人作为 Leader 指挥）

**产品形态。** 最终交互是一个**群聊**：每个 agent 是群成员，PM/架构/编码/测试/评审的发言、交接、进度、产出链接都以人类可读的消息实时流在群里；用户作为 team leader 在群里发号施令——@某 agent 指派或追问、中途插入新需求、否决或批准评审、调整优先级、让某 agent 解释其决策、**对 agent 之间的分歧拍板**。相比"流水线跑完暂停等确认"，这种形态更生动、更可控、更像真实带团队，是本产品的灵魂。

**像真实团队一样通信（一切皆群聊）。** 界面上就是一列群聊：默认有一个包含全体角色的**大群**，agent 想和某人私下对齐时就**新开一个只含相关成员的小群**——本质仍是群聊，只是成员更少。所谓"全员广播"就是在大群发言，"私聊"就是 {A, B} 的小群，"临时小群"就是 {A, B, C} 的小群，它们不是三种不同的东西，而是**同一个原语（群聊 = 参与者集合）在不同成员规模下的用法**（详见第十一节）。**关键不变量：leader 恒是每个群的成员**——无论 agent 之间怎么私聊、拉群，leader 都在场、都看得到、随时能插话，不存在瞒着 leader 的对话。agent 可以自己发起小群，leader 也可以，小群收尾把结论冒泡回大群。并行状态下，多个 worker 会**同时**在各群里冒出消息，前端如实呈现"多人同时在干活"的热闹感。

**关键设计张力（产品能不能跑稳的分水岭）：群聊是展示与指挥层，不是 agent 的内部上下文总线。** 一个群的成员名单只决定"谁看得到这条消息"，不等于 agent 把看到的一切都塞进自己的工作上下文。每个 agent 纳入上下文的，仍是它的角色投影 + **它所属的那些群**的局部上下文（第八节）。这样大群发言不会淹没所有人，小群天然把上下文限定在参与者范围内。这条"展示层与 context 层解耦"的设计，正是让产品既生动又不崩的关键——群聊看起来热闹，底层每个 agent 的上下文却始终干净、聚焦。

**[2026-08-31 架构决策更新]消息事实与实时投递分离。** `AppState.messages` 是任务级消息事实源；消息必须先经应用服务调用 `applyMutations()` 提交并持久化，成功后才发布 `MessageCommitted` 事件。`MessageBus` 只负责已提交事件的投递，不直接修改 State。浏览器只接收 `{msgId, channelId, fromRole, type, display, ts}` 展示信封，永不接收面向 agent 的 `payload`；SSE 是可重连的实时提示层，不是第二份事实源。

**[2026-08-31 架构决策更新]Leader 指令的阶段化落地（D9）。** Leader 的普通发言与指令统一从 `POST /api/messages` 进入；浏览器只提交 `display` 与稳定 `msgId`，服务端从 `display` 生成结构化意图，不信任客户端自报的 `payload.intent`，也不保留绕过 State 的独立临时 command 投递面。Leader 消息与本阶段可执行的动作 mutations 必须在同一任务串行区内经一次 `TaskStateStore.commit()` 原子、幂等提交，成功后才按 D6 发布展示事件。

**[2026-09-01 架构决策更新]D9 单主消息边界。** 一次 `commitPlannedMessage` 只承载一个由服务端构造并单独校验的主消息；planner 返回的动作 mutations 只能修改非 `messages` 字段，禁止追加第二条消息。需要一次提交多条消息的编排路径必须走会校验并投递每条新增消息的批量 mutation 服务，避免附加消息绕过 Channel 策略或成为未发布事实。

**[2026-09-01 架构决策更新]D9 Phase 6 Channel 生命周期例外。** sub 群属于项目级 `Project.channels`，不能伪装成任务级 State mutation，也无法与 `TaskStateStore` 做跨文件原子提交。Leader 仍只从 `POST /api/messages` 发起；服务端先验证任务、可信 actor、roster 与命令，再按稳定 `msgId/actionId` 幂等提交 `ProjectChannelStore`，随后把原 Leader 消息或生命周期 `announce` 经 D6 写入任务 State 并投递。后一步失败不回滚已提交 Channel，重试必须补齐消息且不得重复开/关群。AppState 内动作继续遵守“主消息 + 非消息 mutations 一次提交”；Channel 生命周期不得借临时 command 总线绕过同一入口。

**[2026-09-03 架构决策更新]D9 Phase 7 角色离职例外。** Leader 使用同一入口发 `/role remove <ROLE> [to <SUCCESSOR>]`，稳定 `msgId` 作为 actionId；离职服务把 action/task/接任者/阶段持久化进目标 `RosterEntry.departure`，按 D12 可恢复 saga 跨 collaboration 与 Task State 推进。原消息已存在不代表 saga 完成，重复 msgId 必须从持久阶段继续。`awaiting_replacement` 是可展示的 blocking 结果而非 applied；Phase 8 裁决恢复与 Phase 9 完整抢占仍不得抢跑。

**[2026-09-03 架构决策更新]D9 Phase 8 humanGate 裁决。** Leader 仍使用同一 `POST /api/messages`，以 `/resolve-gate <gateId> <option> [argument]` 显式绑定当前 gate，稳定 `msgId` 作为 actionId。旧 `/approve`/`/reject` 不含 gateId，不得在 Phase 8 继续作为可执行快捷命令，以避免延迟/重放请求裁决了新 gate。服务绑定 actor=`leader`，必须重读持久 gate 并校验 ID/option/argument 及 reason-specific 后置条件；规范 Leader 消息、裁决变更与 active gate 清除在一次 Task State commit 中原子落盘，成功后才按 D6 投递。该消息必须保存 `{gateId,option,argument?,safePointRefs,resumeSessionId}` resolution receipt，`resumeSessionId` 从 actionId 确定性派生，作为清 gate 后 composition/fork 重试与后端重启恢复的锚点；lineage child Agent 创建后还必须提交稳定 `human-gate-resumed:<actionId>` 控制事实，完成前 run 仍为 `needs_attention`，不得伪造 running。

**[2026-09-03 架构决策更新]D13 Phase 7 任务入职例外。** Leader 使用同一入口发 `/role onboard <ROLE> [from <HANDOFF_MSG_ID>[,<HANDOFF_MSG_ID>...]]`，稳定 `msgId` 作为 actionId。该动作只读取项目 enabled roster，不修改 collaboration；Leader 主消息、`nextRole` 与规范 handoff refs 在一个 Task State commit 中提交。它与项目 `addRole` 明确分离，避免伪造跨文件原子事务；精确选择、认领与投影规则见第十二节。

阶段 5 只承诺可真实闭环的最小指令：消息开头的单一 `@ROLE` 表示定向激活，目标必须是已启用角色，任务不得处于 `done` 或待裁决 `humanGate`；有效指令随消息原子写入 `nextRole`，普通文本只作为 `chat` 持久化。Coordinator 在下一次决策时只消费**最新且尚未确认**的 applied assignment，追加带 `sourceMsgId` 的控制事件并把 instruction 写入本轮 Coordination Ledger 后定向派发；该确认事件防止同一指令重复激活，更早的未消费 assignment 视为已被最新指令覆盖。未知/禁用角色、非法状态，以及尚未到阶段的新需求重规划、正式决策覆盖、humanGate 裁决、优先级改写、objection 关闭、sub 群创建均不得静默假装成功，而须返回结构化 `rejected` 或 `deferred`（含目标阶段与原因），同时保留 Leader 原始消息事实。动态 sub 群归阶段 6，humanGate/objection 裁决归阶段 8，需要安全点暂停与重跑的新需求/决策/优先级变更归阶段 9 的完整配合式抢占。识别与执行分层，后续阶段扩展动作执行器而不重写 Leader 输入入口。

**[2026-09-01 架构决策更新]Phase 5 Web 编排执行桥接（D10）。** 创建并启动一个全新任务属于任务生命周期操作，不属于 D9 所指的“既有任务内 Leader 发言/指令”；任务启动后，所有群聊输入仍统一遵守 D9。受信任单用户、单实例自托管后端的组合根必须复用既有 `runOrchestration()`、HarnessExecutor、沙箱和 L3 端口，不复制第二套编排循环。Phase 5 仍处于“项目内初期退化单任务、Phase 9 才升级真并行”的阶段，因此整个后端实例最多一个活动 run；不同任务的持久终态可共存，但另一活动任务存在时新启动必须明确拒绝，禁止在 GlobalScheduler 落地前绕过并行配额。Coordinator/Worker 的展示消息与状态变化必须先提交并持久化到任务 State，再经 MessageBus→SSE 投递；静态种子消息不得充当执行证据。终态 State/消息与产物引用必须可刷新恢复；产物先归档到任务耐久目录，再释放 Harness、MCP/Git client 与 Docker 容器，刷新不得依赖活执行资源。活动 run 因进程退出而中断时不得误报“仍在运行”；进程重启自动续跑不在本阶段承诺内。

### 十一、通信形态与协议（一切皆群聊：单一 Channel 原语）

agent 间不直接互相调用，而是**通过共享 State + 群聊消息**间接协作，耦合最低、最可控。**这里只有一个通信原语——群聊（Channel = 一个参与者集合），且 leader 恒为其成员。** 过去常说的"广播 / 私聊 / 小群"不是三种不同的通道类型，而是同一个原语在不同成员规模下的用法：

**全员大群（main）**：participants 覆盖全体在编角色 + leader。在这里发言即"全员广播"，用于阶段公告、目标发布、评审终审结论等需要全员周知的信息。全员"可见"但不等于全员"消费"——是否纳入某 agent 的工作上下文仍由其角色投影决定。

**子集小群（sub）**：participants 是若干成员 + leader（leader 强制并入），且每个 sub 群必须绑定创建它的 `taskId`、稳定 `threadId`、非空 `topic` 与可信 `createdBy`，不允许任务 A 借用任务 B 的小群。两人时就是过去说的"私聊"，多人时就是"临时小群"（如 Coder+Tester 合力攻 bug、Architect+Coder 对齐方案）。小群拥有自己的**局部上下文**，只有群成员能读到；讨论结束后把结论摘要 + 关键决策及理由冒泡回大群并写回共享黑板，防止形成信息孤岛。这也正好是自适应编排里 Tier-1/Tier-2 局部拓扑的可视化呈现。

因为 leader 是每个群的成员，所以**任何 agent 之间的对话对 leader 都是透明的、可随时介入的**——这是"leader 唯一裁决"权威形态在通信层的自然落点，也让"瞒着 leader 私下商量"这种情况在结构上不可能发生。

**消息结构**（初步，TS 字段）：`{ msgId, threadId（问答/升级/异议的会话链标识，用于挂起-作答-resume 与级联升级）, channelId（所属群聊；大群=main，"私聊/小群"=对应 sub 群）, fromRole, to?（群内 @定向，仅影响 inbox 优先级，不改变可见范围）, type（handoff / feedback / question / escalation / objection / chat / announce）, payload（面向 agent 的结构化内容）, display（面向人的可读摘要，用于群聊呈现）, ts }`。`payload` 与 `display` 分离，正是第十节双层设计的落点；`threadId` 支撑第七节的问答链与第十四节的异议/升级链；消息的可见范围只由它所属 Channel 的 participants 决定。

**[2026-09-01 架构决策更新]作用域、所有权与恢复边界。** `Project.channels` 是 Channel 注册表的唯一真相源，`AppState.messages` 保存任务级消息事实；`AppState` 不再复制 `channels`。跨边界投递使用 `{projectId, taskId, message}` 信封，API/SSE 也必须带项目与任务作用域，避免不同项目的 `main` 群碰撞。阶段 6 的注册表必须经项目级原子 JSON 快照持久化，并可在进程重启后恢复；不得以进程内 Map 充当真相源。项目只有一个 `channelId='main'` 的项目级大群；sub 群的 `channelId` 在项目内唯一且必须绑定 `taskId`。角色 inbox 与角色 `ChannelContext` 都属 `channels` 的可重建读模型，从持久 Channel 注册表 + 任务 `AppState.messages` 派生，不属于 `MessageBus` 端口，也不在 Channel 中保存第二份消息索引。阶段 5 退化为每个活动任务从项目 main 群派生视图；阶段 6 启用持久 Channel、participants、任务绑定 sub 群与结构化局部上下文。

**[2026-09-01 架构决策更新]D7 升级恢复与语义稳定性。** Phase 6 首次读取已有任务时，若任务 `state.json` 存在而项目 `channels.json` 缺失，服务端必须以当前已启用 roster 幂等补建唯一 main，保证 Phase 5 持久任务升级后仍可访问；仅“文件缺失”允许 backfill，损坏或违反不变量的快照必须明确失败，不得覆盖。已启用角色必须非空、唯一且不得使用保留身份 `leader`。Channel JSON 对象的属性排列不构成语义变化；participants 在领域上是集合，写入前必须标准化为 `leader` 在前、其余角色按当前 enabled roster 顺序排列，成员相同而输入顺序不同属于 no-op。Channel 注册表顺序保留，语义相同的 commit 不得写盘或递增 revision。

**[2026-09-01 架构决策更新]发起权与生命周期【已定：以 agent 自发为主】。** 小群（含"私聊"）**主要由 agent 自己按需发起**，leader 同样可随时发起。agent 只能在最终回复末尾输出至多一个严格 `<agora-channel-action>{...}</agora-channel-action>` 控制块；薄执行器校验并从人类 display 中剥离该块，以同一步 assistant message 的 `msgId` 绑定 actionId，再通过现有通用 `StepResult.output` 在安全边界交给编排层。它不是 AppState mutation，也不是可由模型伪造 actor 的普通 MCP 参数；组合根必须把当前 RoleSpec 身份绑定为可信 actor，畸形/未知控制块令 Step 明确失败而非降级成普通文本。控制块可以为 open 显式携带安全、稳定的 `threadId`，但不得携带 actor/actionId；纯控制回复仍保存审计 Message，并生成不含原控制块的确定性非空 display，避免展示空白消息。Leader 使用 `/channel open ROLE[,ROLE...] <topic>` 与 `/channel close <channelId>`，仍经 `POST /api/messages`，由服务端绑定为 `leader`。

每个动作携带安全、稳定的 `actionId`；Leader 路径复用 `msgId`，agent 路径由执行器生成并在重试时复用。新群采用可逆长度前缀 `channelId='sub-'+taskId.length+'-'+taskId+'-'+actionId`，消除 taskId/actionId 均允许连字符时的拼接碰撞；`threadId=actionId`（agent 可显式提供另一个稳定 threadId）。participants 自动取 `{leader, actor（若非 leader）, requestedRoles}` 并按 roster 标准化。相同 `taskId+threadId` 的同语义 open 返回既有 Channel；participants/topic 不同则明确冲突；不同 thread 若仍产生 channelId 冲突必须作为业务拒绝而非存储异常；关闭后重开同一 thread 也不得静默复活。只有 leader 或该 sub 的 participant 可关闭；main 永不关闭；重复 close 为 no-op。所有生命周期写经一个按项目串行的应用服务提交既有 `ProjectChannelStore`，不修改其冻结签名。

Coordinator 不再是群的主要创建者，而退为轻量治理：用 `taskId+threadId` 防重复议题群、观察数量并保证收尾回流。6.2 的 close 只原子置 `closed=true`、阻止后续 sub 发言并向 main 写稳定幂等的生命周期公告；6.3 再协调 `ChannelSummaryGenerator`，从该 sub 的结构化消息切片生成结论、关键决策及理由、未决问题与来源 msgId，以稳定 `msgId='channel-bubble:'+channelId` 先写入 main，随后只在 Channel 保存 `bubbledSummaryRef:{taskId,msgId}`。摘要消息是唯一内容真相，Channel 不复制摘要字符串；重试先复用已存在的稳定 main 消息，再补引用，因此任一步崩溃后均可收敛。`threadId` 在 6.2 只提供持久会话链与路由，真正的异议挂起、humanGate 裁决和 resume 仍归 Phase 8。工具调用侧继续一律走 MCP；Channel 生命周期属于编排控制动作，不新增绕过 MCP 的代码执行工具。

前端不得继续把 main 写死为唯一群。Phase 6 增加只读 `GET /api/channels?projectId&taskId`，从持久 `ProjectChannelSnapshot` 以字段白名单派生 leader 可见的 main + 当前 task sub 元数据（不返回 `bubbledSummaryRef` 指向的摘要内容或消息 payload）；UI 在任务初始化、生命周期动作完成时刷新一次，仅在 active run 中持续短轮询，成功恢复后清除独立的 Channel 刷新错误；切群后用所选 `channelId` 重建既有 SSE/POST 作用域。Channel 列表不是新事实源，不新增 Channel 事件总线；agent 开群即使 lifecycle announce 暂时投递失败，也可由持久快照恢复发现。

### 十二、角色热插拔与团队动态编制（入职 · 离职 · 交接）

**能力概述。** leader 可以像管理真实团队一样动态调整成员编制：**招募新 agent（加入项目）**、**移除某个 agent（离职）**，并把任一 enabled 成员**入职到具体任务接手工作**。项目成员登记与任务接手是两个不同作用域的动作：前者只改变项目 roster+Channel，后者只在选定任务中提交接手事实、交接引用与激活意图。被移除成员离开前，系统必须等其当前 Step 自然结束并从已提交 State 固化一份**可验证的结构化交接文档**；接手成员从持久 Task State 派生交接上下文与当前角色投影，不依赖进程内一次性注入。交接内容不依赖额外一次 LLM 自报成功：已有结构化产出可纳入，最终事实仍由 State、decisionLedger、subtask 与文件引用确定性生成。这把第八节的"结构化交接"从看不见的内部机制，升级成看得见、可操作且可恢复的产品能力。

**前提：角色是数据，不是代码。** 角色定义 `RoleSpec` 只描述名称、职责、system prompt、工具集（MCP 权限）、投影规则、执行器类型与路由条件；项目成员关系由 `RosterEntry` 单独描述，并以 `enabled | disabled | departing | departed` 表示生命周期。项目级 roster 是唯一真相源，不复制进任务级 `AppState`，也不由进程内 `DEFAULT_ROSTER` 充当运行事实。运行时通过"**通用 worker 节点 + coordinator 路由**"加载当前 `status='enabled'` 的成员；成员状态变化不增加角色节点。

**[2026-09-02 架构决策更新] D12——roster 与 Channel 原子同源。** roster 变化会同步改变 main participants，二者必须在同一个带 revision 的 `ProjectCollaborationSnapshot { projectId, revision, roster, channels }` 中原子提交并持久化到 `.data/projects/{projectId}/collaboration.json`。Phase 6 的 `ProjectChannelStore` 公开签名保持不变，作为该协作快照的 Channel 视图；Phase 7 首次落地 `ProjectCollaborationStore` 后冻结其接口。旧 `channels.json` 只允许在 `collaboration.json` 缺失时用六角色默认 roster 做一次确定性迁移；两文件并存且内容不一致、任一文件损坏或不变量失败均 fail-fast，迁移完成后不得保留第二份 Channel 真相。

**四个生命周期动作。** 其一，**加入项目（招募）**：受信任的项目管理面把已选择或自定义的 `RoleSpec` 交给 `addRole`；Phase 7 不虚构尚不存在的模板目录或任意 RoleSpec 编辑 UI。`addRole` 只接受规范化后唯一、非保留的 role id，并以 `enabled` 加入项目 roster；它不选择任务、不写任务消息，也不声称成员已经接手工作。其二，**入职具体任务（onboard）**：leader 在目标任务 main 群经 `POST /api/messages` 发 `/role onboard <ROLE> [from <HANDOFF_MSG_ID>[,<HANDOFF_MSG_ID>...]]`，稳定 `msgId=actionId`；目标必须是项目中 enabled 成员。该 Leader 主消息就是可见的入职/接手公告，并与 `nextRole=<ROLE>`、规范化交接引用在同一次 Task State commit 中原子落盘。其三，**临时停用/恢复**：`disableRole` 只把 `enabled→disabled`，`enableRole` 只把 `disabled→enabled`，重复同态操作为 no-op；`departing/departed` 不得被普通 enable 复活。其四，**离职（remove）与责任转移**：`removeRole` 不是底层数组删除，而是阶段 7.2 的可恢复状态机。Leader 通过 `POST /api/messages` 发 `/role remove <ROLE> [to <SUCCESSOR>]`，稳定 `msgId` 同时作为 `actionId`；服务先以 collaboration revision CAS 写入 `departing` 与离职操作元数据，从而立即禁止新指派、发言和普通执行，再等待已运行 Worker 完成当前 Step 并保存安全点。随后从已提交任务 State 确定性生成 `HandoffPacket`，并在一次 `TaskStateStore.commit()` 中写交接、展示消息与责任变更。仅当未完成责任已转给 enabled 接任者，或确认不存在未完成责任时，才以第二次 CAS 进入 `departed`。离职记录和最小角色身份永久保留供消息、Channel 与审计引用；需要重新加入项目时使用新的显式流程或新 role id，不静默覆写历史身份。

**[2026-09-03 架构决策更新] D13——项目招募与任务入职分离。** `addRole` 是 D12 的项目级成员登记，只提交 `ProjectCollaborationSnapshot`；`onboard` 是任务级 Leader Intent，只提交当前 `AppState`，二者不得包装成无恢复锚点的跨文件“原子入职”。onboard 自动选择当前任务内尚未被既有 applied onboarding 事实认领、且规范离职 handoff Message 的 `packet.toRole===ROLE` 的直接交接；`from` 只允许 Leader 显式列出同任务、`packet.toRole='leader'` 的托管离职 handoff Message。交接引用一律保存完整 `{taskId,msgId}`，只接受能同时命中规范 `Message{type:'handoff',payload.kind:'role_departure_handoff'}`、其内 packet、`AppState.handoffPackets` 与离职 `actionId` 的事实；未知、跨任务、重复认领或冲突引用 fail-closed。普通 Coordinator 角色切换生成但没有稳定 handoff Message 的 packet 不属于本接手协议，避免以数组位置或内容猜身份。

onboard 继续使用既有 Leader Intent 外壳 `payload={kind:'leader_intent',intent:{kind:'onboard_role',...},action,onboarding:{actionId,role,handoffRefs}}`，不得另造平行消息协议或复制原始群聊。`project(state,role,...)` 从最新 applied onboarding 事实与其规范引用读时派生系统级 `onboardingContext`，返回防御性拷贝的结构化 handoff；该切片不由自定义 `RoleSpec.projection` 关闭，也不依赖 Channel 4000 字符窗口或进程内 Map，因此刷新、重启和新建 Harness executor 后仍可恢复。它与角色声明切片、所属 ChannelContext 一起接受 D1 pre-step 覆写；同一任务以后再次显式 onboard 会产生新 action 并取代旧 onboardingContext，已认领交接不得分配给另一角色。onboard 提交后若角色在消费前失效，继续沿用 D12 的 `required_role_unavailable:<role>` humanGate，不伪造已接手成功。

**[2026-09-03 架构决策更新] D12 Phase 7 离职 drain 与恢复边界。** `RosterEntry` 的离职元数据持久保存 `actionId/taskId/requestedTs/successorRole?/stage/handoffRef?`，作为跨 `ProjectCollaborationStore` 与 `TaskStateStore` 可重试 saga 的项目级恢复锚点；阶段至少区分 `draining | handoff_committed | awaiting_replacement | completed`。执行顺序固定为 `departing CAS → 目标 Worker step/end drain → Task State 幂等提交交接/责任结果 → departed CAS`，每一步先重读两份事实并从已完成处继续。现有 `HandoffPacket` 结构保持不变：`done` 表示当前进展，`keyDecisions` 引用理由随行的决策，`openIssues` 承载未完成事项及带显式前缀的建议，`fileRefs` 只传路径行号；有接任者时 `toRole=SUCCESSOR`，无人接手时 `toRole=leader` 作为托管交接。稳定 handoff 展示消息 `msgId='role-departure:'+actionId` 由 `actionId` 派生并写入 `handoffRef`，使无 id 的旧 `HandoffPacket` 仍可幂等兼容；该内部 id 只能命中类型、角色、`actionId` 与 packet 全部匹配的规范 handoff 事实，被任意其他 Message 占用时必须 fail-closed，不得跳过 drain/责任提交或写入虚假 `handoffRef`。

role id 统一大写并匹配 `[A-Z][A-Z0-9_-]*`，按规范化值唯一，`leader` 为保留身份。`COORDINATOR` 不得 disable、depart 或 remove。`addRole` 对完全相同的现有 enabled 条目为幂等 no-op；同 id 不同 spec，或同 id 已处于 disabled/departing/departed，即使 spec 相同也明确冲突，调用方必须改走 enable 或阶段 7.2 离职状态机，不得借 add 隐式复职。所有更新使用快照 revision CAS，禁止 last-write-wins 覆盖并发管理动作。

**护栏。** 其一，Coordinator 不可删除或停用。其二，任务进行中让角色离职必须先进入 `departing` 阻断新工作，再等当前 Step 到安全点、固化交接并处理责任；目标成员不 resume，阶段 7 的其他顺序工作在事实提交后继续。`departing` 后唯一允许的目标角色写入是已登记活动 handle 当前在途 Step 的 mutation commit；该受限路径只为先落盘再停，不允许新 Step、普通发言或额外 Channel 副作用，并仅对目标已从 main participants 移除这一点放宽当前 Step 的 main Channel 校验。其三，只设置“无人接手” humanGate 不算完成责任转移：只要仍有未完成 subtask，角色必须保持 `departing`，相关 subtask 保留原 owner 并标 `blocked`，直到 Leader 指定 enabled 接任者；不得用 `departed` 制造孤儿职责。Phase 8 落回合制单任务的 D4 持久 suspend/resolve/真 Fork resume，Phase 9 才补全局多 worker 抢占与上下文注入。其四，Coordinator、Leader Intent、WorkerRuntime 与 Channel 发言入口都必须以同一持久 roster 判定普通工作仅允许 `status='enabled'`；`departing` 只可由离职服务执行受限 drain/交接协议，不能重新进入普通路由。该权威源缺失时 fail-closed。已持久化的 Leader 指派若在 Coordinator 消费前因角色停用而失效，必须进入 `required_role_unavailable:<role>` humanGate，不得抛出未处理异常中止编排。其五，main participants 精确等于 leader + enabled roster；sub 的参与者与 createdBy 只需是 leader 或**已知 roster 身份**，从而允许读取历史群。停用/离职不删除历史 sub 成员，也不使历史快照失效。

**Phase 7 的自定义角色边界。** 默认六角色继续由 Coordinator 的已定语义自动路由；自定义角色在 Phase 7 保证可持久注册、投影、工具作用域化，并可由 leader 通过显式 `@ROLE` 指派给通用 worker。仅凭 `routeWhen` 还不足以定义多个任意角色之间的优先级、产出契约与冲突处理，因此 Phase 7 不宣称任意自定义角色可被 Coordinator 自主调度；该能力按 `DEF-016` 延期，未落地前不得用“新增任意角色即可自动参与编排”对外宣传。

**产品与讲点价值。** "我把 agent 团队做成一个活的、可编辑的组织——leader 能招人、能让成员'离职'，而离职必须先交接、新人入职自动读交接文档接手。"它同时是极具冲击力的演示点，和对"多 agent 的上下文如何传承"这一深问题的正面回答。

### 十三、真并行执行与配合式抢占

**[2026-09-08 9.5 实装与安全验收]** 上述方案已落地：正式文件入口与独立进程竞态、真实逐 worktree 挂载及后台写入冻结、Git metadata 固定、暂停/Fork/恢复/归档和停止失败重试均有当前回归证据。支持 macOS/Linux 受信宿主；不把 LocalTemp.run 描述为任意代码的系统隔离。DEF-004/010/013 的最终状态与逐项依据只查 `deferred-items.json`；此前阶段的 open 记录保留为历史。构建部署命令与 capability 兼容约定见详细设计 §6、技术选型 §12。

**要解决的问题。** 要"像真实团队"，就不能只是轮流发言的回合制——多个成员应能**同时**干活。但真并行带来两个新难题：一是并发访问共享黑板会写乱；二是 LLM 一旦开始生成就无法"硬中断"，leader 中途改主意时没法瞬间叫停所有人。本节给出应对。

**独立异步 worker。** 被 Coordinator 激活的每个 assignment 实例化为一个**独立异步 worker**；其逻辑身份是 `{projectId,taskId,workerId}`，其中稳定 `workerId` 由本任务内的 `dispatch/index` 派生，并由 canonical `WorkerState.subtaskId` 绑定 subtask，不能用 role 充当唯一身份（同一批允许多个 CODER）。每个 worker 拥有自己的薄 Harness Executor、独立 session/事件日志与角色投影；任务 9.3 再把该身份绑定到独立 git worktree/分支。`workerId` 是逻辑身份而不是 Git ref：组合适配器必须对 `{projectId,taskId,workerId}` 做确定性、防碰撞的 Git-safe 编码，不得更改 canonical workerId 或依赖 role 命名。**隔离是两层：Harness context/session 负责进程内上下文隔离，git worktree 负责文件系统隔离，二者互补。** Node 的事件循环 + Promise 只并行模型/工具工作；共享 State 与 Channel 副作用仍在 step/end 边界进入任务级提交串行区。

**为何自研这层。** 单 agent 的运行时（loop、工具流水线、事件溯源、resume）复用 Harness；但"多个长跑 worker 的生命周期 + 抢占编排 + worktree 分配 + 集成合并"是 Harness（单 agent 运行时）之上、需要我们自己写的协作层。Phase 9 的并发层只负责 assignment 校验、全局槽位租约、worker 生命周期和任务级提交串行化；不复制 Harness loop，也不在 `Promise.all()` 后合并多个完整 `AppState` 快照。

**[2026-09-05 架构决策更新] D17——有界并行与提交一致性。** `runParallel(state,batch)` 是处理**全部**合法 assignment 的有界异步队列，不得用 `batch.slice(0,maxParallel)` 静默丢弃尾部；默认全局同时运行上限为 3。跨项目 worker 执行额度只由单实例 `GlobalScheduler` 的稳定 lease 统一分配，lease 身份为 `{projectId,taskId,workerId}`，`WorkerRuntime` 只设置不高于全局额度的本任务上限；调度器按项目轮转，容量足够时先给每个有等待工作的项目一个槽位，项目数超过容量时排队而不虚构“每项目同时保底 1”。同一进程内由 scheduler 返回的同一个 lease capability 重复释放为 no-op；克隆、伪造或错配 lease fail-closed，scheduler 不以永久强引用 tombstone 换取跨进程幂等。worker 完成、失败或持久 suspend 后必须释放 lease。锁定 Harness 的 spawn provider 只有 one-shot `ctx.subagents.start()`，不适合 D4 可恢复长跑 worker；顶层 worker 复用既有 HarnessExecutor 工厂，以独立 Context/`ctx.agents.create()`/session 实例化，one-shot subagent 只可作为 worker 内部委派。

模型/工具调用可并行，但每个 step 的输出处理、并行写权限校验与 `TaskStateStore.commit()` 必须按 task 串行：进入提交区后重读最新 canonical State，再原子提交该 step 的 mutations；join 等全部已启动 worker settled、提交队列排空后重新加载 canonical State 返回。并行 agent step 输出只允许 append 带稳定身份且通过生产者校验的事实，不得直接 merge `workers`；`WorkerState` 的注册、`status/safePoint` 等生命周期进展只由 `WorkerRuntime` 内部为当前 worker 提交，不接受模型伪造。当前 `Subtask` schema 的 `title/ownerRole/dependsOn/status/worktree/priority` 全是拓扑、所有权或集成控制面字段，不存在可授权给并行 worker 的“非控制面进展字段”，故任何并行 subtask merge、全局 `set`、他人 worker 分区与项目级 collaboration 写入一律拒绝，由 Coordinator/专用服务在串行控制面提交。`priority` 是可选的 0–100 整数，旧快照缺省按 `0`；依赖可执行性优先，同一拓扑波次的就绪 subtask 才按 `priority` 降序、再按稳定 `id` 排序。`Promise.all` fail-fast、选择某个 worker 返回的 State、或对多个完整 State 做未定义 `mergeStates()` 都不构成一致性方案。任一 worker 失败时不得硬杀同批 LLM；等待其余已启动 worker 到自然边界，保留成功提交，聚合失败并 fail-closed。

Web 运行注册表允许多个 task 并发登记，不等于允许在 lease 外无限预分配 Docker/worktree/MCP/Git/Harness 等重资源。单实例 `TaskOrchestrationRuntime` 对持有 executable `TaskComposition` 的活动任务设置独立生命周期 admission cap（默认 3）；它只限制组合根资源数量，不授予任何 worker 执行额度。容量已满时必须在调用 `TaskCompositionFactory` 前以可重试 `429` 拒绝，不能创建占位 State 或半成品 composition；实际 worker 仍须另行进入唯一 `GlobalScheduler` 公平队列取得 lease。

**配合式抢占（cooperative preemption）。** 既然不能硬中断 LLM，就用"协作式"：按 task 串行接受带稳定 `actionId` 的暂停请求，固定请求当时的 active worker cohort，阻止该 task 再启动新 Step；已进入模型/工具流的 worker 必须先自然到 `step/end`，经 per-task canonical queue 提交该 Step，再 flush checkpoint 并由 WorkerRuntime 写入自身 `WorkerState.safePoint/status`。没有取得 lease 的本 task 排队 assignment 取消等待但保持 `pending`，不记为 worker 失败。代价是有一个"到安全点"的延迟（秒级），但换来状态一致、不撕裂。

**[2026-09-06 架构决策更新] D4/D17——抢占分两种恢复模式。** 不需要等待人类的非阻塞重规划在 cohort 全部到安全点后，将已校验的 Leader 主消息与控制 mutations 一次提交到最新 canonical State，再向原 context 注入最新 D1 投影并恢复；该短临界区持有原 lease 和 composition admission，不做无意义的 dispose/Fork/重排队。需要 Leader 无界等待的 blocking/humanGate 则走 D4 耐久路径：全体 cohort checkpoint 与完整 gate 落盘后，先交还已静止 worker 的 scheduler lease，再 suspend executable composition；重资源清理失败会保留 composition admission 与 `needs_attention`，但不得继续占用已无执行活动的 worker lease。Leader resolve 后新 composition 为每个 `paused` worker 从 receipt 的稳定 per-worker 恢复计划创建/接管 lineage child，每个 worker 在再次执行前取得全新 lease；旧 lease capability 绝不跨 Fork 复用。

**worktree 隔离与集成检查点。** 并行的 Coder 各占一个真实 linked git worktree/分支，互不踩踏文件。Phase 9 组合根只允许一个对外 worktree 所有者：复合 workspace adapter 经冻结 `SandboxManager` 端口对编排层提供工作区，内部以 task-owned canonical repository 创建 Git linked worktree，并把**同一个规范路径**绑入 Docker 执行边界；不得让 Docker 目录与 Git worktree 各自创建一份事实。task-owned repository 从受信 seed/测试 fixture 在 `.data/projects/{projectId}/tasks/{taskId}/repository/` 物化，空任务则建空仓；Git 初始化必须确认指定目录本身是 repository root，不能把向上发现的用户仓库当成任务仓库（`.data` 嵌套场景需显式 git init）；绝不 checkout/merge 或写回用户正在使用的源仓工作区。

**[2026-09-07 架构决策更新] D17——可恢复集成与冲突裁决。** 每个新 Phase 9 worker 必须在 State 中持久化结构化 `WorktreeRef{path,branch,baseCommit,headCommit?}`；Phase 0–8 的字符串路径只作兼容读，进入 Phase 9 前必须通过 Git 实际查询升级，禁止猜 branch/commit。集成服务以稳定 `integrationId` 持久化 base branch/commit、按 `{topologicalRank,workerId}` 排好序的分支身份、已合并进度、冲突与结果 commit。合并只在从记录 base commit 创建的专用 integration worktree/分支中串行执行；每步前后校验 branch head，已合并重放通过 ancestry + 持久进度幂等确认，事实漂移则 fail-closed。冲突时必须收集路径后 `merge --abort`，持久化 `integration.status='conflict'` 并打开 `integration_conflict:<integrationId>` gate；Phase 9 最小裁决仅允许 `request_rework <workerId>`，且 workerId 必须命中冲突贡献者。裁决 commit 将该 worker 的 subtask 退回 `todo`，清除本轮集成中间态并从原 base 重建；其他复杂手工冲突提交能力未定义前不得伪装支持。

**[2026-09-07 架构决策更新] D17——集成恢复精确化。** `Integration.pendingBranches` 必须非空且身份唯一；`mergedBranches` 只能是它按完整 `{workerId,subtaskId,branch,headCommit}` 匹配的前缀，`conflict` 只能指向紧随此前缀的唯一分支，`done` 必须覆盖全部输入且 `resultCommit` 等于最后进度。所谓“Git 已成功但 State 回执遗失”只允许补记**当前下一分支的一个步骤**：integration HEAD 要么是该分支造成的合法 fast-forward，要么是父提交精确为 `{previousHead,branchHead}` 的单次 merge commit；若已包含后续分支、额外提交或父链不符，一律视为漂移。恢复除 task-root 路径、branch/head 与 common-dir 外，还必须在 canonical repo 的 `git worktree list --porcelain -z` 中找到唯一、精确匹配规范 path/branch/HEAD 的 linked-worktree 记录，并明确拒绝 canonical 主工作区；仅同仓库不足以证明持久身份。创建后取消、Docker bind 失败及终态回收都必须同时闭合 worktree admin metadata 与临时 branch；冲突 abort 未确认不得持久化普通 conflict/gate。并发产物选择不得依赖 Promise 完成顺序：9.3 以当前 Integration 波次作为分支审阅来源；9.4 最终累计审阅/主产物归档使用该结果派生的 accepted validation receipt，见下文；无 Integration 的顺序兼容只允许所有候选收敛到一个相同 WorktreeRef，否则必须保留全部分支的确定性归档或 fail-closed，不得静默挑一个 worker。首次物化终态 artifact 时必须持久化不可变的 source→archived path receipt；同一目标重试只能校验并复用该 receipt，禁止根据后来已改写的 State 重算映射。目标已存在但 receipt 缺失、损坏或引用不存在时保持 `needs_attention` 并保留源 worktree。

**一致性兜底。** 其一，写共享 State 一律经 reducer；只有满足 D17 身份分区的合法并行 mutation 才要求交换、幂等，覆盖型 `set` 留在串行控制面。其二，代码产物以 worktree 为准、State 只存引用（路径+分支+commit），避免贴代码导致的版本漂移。其三，任何跨 worker 的强依赖（B 必须等 A 的接口）由显式、已校验的任务 DAG 表达；每次只激活 `dependsOn` 全部完成的拓扑波次，同波次全部成功 settled 后才进入集成检查点。有未完成任务却没有就绪任务时不得进入评审或完成。

**分阶段落地。** 真并行是进阶能力，不在第一版。**先做回合制（round-robin）跑通全链路**（阶段 0–8），把状态、上下文、通信、裁决都验稳，**再在阶段 9 升级为真并行**：9.1 落 GlobalScheduler lease、稳定 worker 身份、全 batch 有界队列与任务级 canonical commit join；9.2 把多 worker 安全点与 D4 槽位释放/恢复接上；9.3 落 workerId worktree 与确定性集成；9.4 接 Coordinator 拓扑波次、集成后的独立验证分支及完整终审链；Tester 只读准备仅保留契约，当前固定关闭。9.4 已接生产编排与独立验收链；实现验证证据单独记录，不把 9.1–9.3 的局部能力追记为完整 E2E。

**[2026-09-07 架构决策更新] D17——9.4 波次闭合与验证身份。** `architecture.executionPlan` 给出版本化 subtask DAG，Coordinator 验证引用、唯一身份与无环后锁定计划；旧 `modules:string[]` 只能显式退化为按数组序的依赖链，不能猜各模块独立并发。每个 wave 在启动前持久化成员、共同 base、attempt 与稳定 dispatch/workerIds；恢复只消费该 wave 的 assignment，不能扫描历史全部 done/pending worker 猜当前批次。新波次从上一个通过测试的累计提交分支；同角色 worker 的投影和工具工作区必须绑定其 canonical assignment。

合并结果 `Integration.resultCommit` 保持不可变。为保留 TESTER 编写测试的职责，同时避免污染 merge 重放证明，集成后 TESTER 使用从 resultCommit 创建的独立 validation linked worktree，最终测试必须对应已提交且内容冻结的精确 HEAD。可信输出接缝将真实沙箱执行证据、当前验证 dispatch、integrationId、结果提交与当前需求/决策指纹绑定为不可变 validation receipt；仅有 `testResults.passed=true` 或复制来的旧结果文件不构成通过。通过后一次串行 commit 闭合波次 subtasks、登记 accepted receipt 并更新全局 testResults；后续波次、最终只读 REVIEWER、D16 与 artifact 均以这个已验证累计提交为准。`Integration.done` 仅表示分支合并完成，不表示测试、任务或 Leader 终审已完成。详细契约见详细设计 §3.1。9.4 的可信执行器固定使用 Node 内置测试运行器，对 Git 跟踪的 `*.test/spec.mjs/cjs/js` 全集执行 TAP 验证；测试必须提交且命令前后目录无未提交/忽略文件。TESTER preparation 在本版本保持关闭，不提供启用入口。

**[2026-09-07 架构决策更新] D17——累计复验不得回退测试。** 需求/裁决变化或旧结果指纹失效时，复验必须从上一份可信 validation receipt 的精确 HEAD 创建新分支，保留其代码和全部累计测试；不能退回尚未包含 TESTER 测试提交的 Integration.resultCommit。新 dispatch 显式绑定更早的 sourceReceiptId，校验同 wave/attempt/Integration 与测试证据，首次验证仍从冻结 Integration 开始。

**[2026-09-07 架构决策更新] D4/D9——原生安全点与控制边界。** WorkerRuntime 经可选 `SafePointExecutor.requestSafePoint()` 请求边界；Harness 等当前模型与工具 Step 自然结束，在下一次 `agent/pre-step` 拒绝新 Step proposal，官方 loop 闭合 turn 后才 flush/持久暂停，不取消 token 流或改写冻结 Executor 接口。冲突返工的历史 Integration 存入同一 Leader resolution receipt 的 `integrationRework`，裁决仍只有一条主消息。已采纳 parallelExecution 后，无 subtask/wave 绑定的 `@ROLE` 与 `/role onboard` 明确 rejected，避免仅写 nextRole 却未执行；Leader 使用绑定目标的 D9 需求/决策/优先级命令与 D4 gate。旧顺序任务沿用原指派/入职协议，任意并行角色派发不在本任务范围。

**[2026-09-07 架构决策更新] D16/D17——返工与审阅范围。** REVIEWER 的稳定 `subtaskIds` 只能引用本任务当前已验证计划；窄化返工必须重开所指任务及其**全部传递依赖后继，包括已 done 后继**，因为上游修改会使既有下游验收失效。无 refs 才允许显式 degraded 的全量重开，畸形、未知或过期 refs 不能当作缺省值。任务级最终评审必须看到累计产物与全计划的结构化任务引用，不能只看最后一波分支。Leader `request_changes` 仍以非空理由触发保守全量返工，不从自然语言猜 subtask。旧测试/评审/完成裁决不得越 attempt、commit 或需求/决策版本复用；D4 suspend/Fork 不等于返工，原 paused worker 恢复身份不变，真正返工用新的 workerId。

**[2026-09-03 架构决策更新] Phase 7 离职只落目标角色 drain。** 为满足离职“不硬拔”但不抢跑阶段 9，阶段 7 只提供一个可注入、可等待的目标角色 drain 端口：若该角色有活动 Worker，则允许当前 Step 自然完成、提交 mutations 并保存 safePoint 后返回；没有活动 Worker 则立即视为 quiescent。它不广播全局暂停、不启动额外 LLM 交接 Step、不向普通 Worker 注入新上下文，也不实现 terminate/fork。阶段 9 的 task-scoped pause epoch/cohort 协议在此接缝上升级为多 Worker 全局抢占。

**[2026-09-07 架构决策更新] D17——返工保留成员与验证重放。** root-cause 评审定向返工时，未被要求重写但尚未通过验证的同波成员保留实现贡献，并纳入修复波次的累计验收范围；只有新的可信通过回执才能将其置 done，不得遗留不可调度的 in_progress 或未经验证直接完成。CODER 派发集合与累计验证集合分别校验，后者从规范返工来源事实派生，不扩充无关 CODER 派发。单 CODER 与多 CODER 的执行失败都进入同一有界重试流程，持久化/额度释放等基础设施失败仍明确上报。验证证据已持久而 State 回执未提交时，重放必须校验并复用首次证据，不能再次执行测试或覆盖已有文件；身份、命令、报告或 HEAD 漂移一律拒绝。测试全集不按文件名语言或空格过滤，Node suite 包装失败不重复计入叶测试失败数。失败反馈只绑定当前返工身份，不能继续投给已修复后的新波次。architecture issueScope 属计划级重设计，显式全量重开并绑定原累计验证 HEAD，不按实现层 refs 猜局部架构迁移。

**[2026-09-07 架构决策更新] D4/D17——暂停撤销与失败资源收敛。** 原生 pre-step 消费暂停请求时必须清除该请求；Runtime abort 同时取消尚未消费的请求，不注入未提交指令。Executor 冻结接口不变，取消通过 SafePointExecutor companion 的可选 cancelSafePoint 完成。无 active gate/待恢复 gate 的并行基础设施错误在全部执行收敛后保持 needs_attention，保留 State、source worktree、Harness JSONL 与验证证据，通过 recoverable suspend 释放可执行资源和 composition admission，不终态归档或 teardown。suspend 失败保留 admission 与可重试清理记录；同任务 start 只续办清理，成功后释放 admission，仍不伪造业务完成或任意崩溃恢复。

**[2026-09-07 架构决策更新] D17——累计测试文件保留检查。** CODER 完成和 TESTER 可信验证都比较各自输入 Git commit 与当前 HEAD 的完整 tracked 路径，拒绝删除继承测试或将其改名移出原测试路径；不能用仅剩的 smoke 测试生成通过回执。该检查沿每波 accepted base 与 sourceReceiptId 复验链累计生效，当前没有模型自行删除继承测试的授权入口。CODER 完成检查包含 tracked 修改及 untracked 文件，忽略的本地依赖/缓存不进入 Git 集成输入，不阻挡其完成；TESTER 目录继续拒绝全部未跟踪/忽略文件。

**[2026-09-08 架构决策更新] D11/D17——Phase 9 出口与对照口径。** 9.5 分别交付确定性出口测试、真实生产链 G5、固定配置的串行/并发 2/3 Eval；三者不相互替代，9.4 的 A/B→C 正确性演示也不作为并发 3 的对照任务。串行基线仍运行相同多角色、相同 DAG、相同波次/集成/验证协议，只将唯一 GlobalScheduler cap 设为 1；另外两组 cap 为 2、3，不切换旧顺序编排或改任务拆分。至少一个对照任务具有 4 个独立就绪子任务及依赖它们的后继，同时检验 cap=3 的实际执行与排队尾部；有限队列的跨项目公平另设确定性争用场景，不混入单任务性能数字。

重复次数、配置、预算和轮换顺序在运行前冻结；真实模型每组至少 3 次独立 attempt，作为小样本探索结果，保留全部失败与清理记录，不宣称统计显著或通用加速。模型没有提速不阻断阶段完成；缺少规定实验、关键正确性/安全证据或用旧 G5 冒充对照则不能完成。具体矩阵、计时/指标定义、产出与完成判据统一见详细设计 §11.7，后续 Phase 10 才做更广的最终 Benchmark。

cap=3 限制持有 lease 的 worker 执行，生命周期 admission 限制 executable composition；两者都不是持久 worktree 数量或磁盘占用上限。集成、验证、返工与暂停恢复会保留额外工作区，资源报告须分别记录执行峰值、容器/工作区峰值和清理后的保留量。

DEF-004 的默认出口要求仍为修复并验证实际文件访问入口；若选择后续安全边界，必须由 Leader 另外明确接受具体的支持范围、执行限制、残余风险和复评条件，并同步延期台账，不能从本次规格评审或一个风险复现测试推导豁免。安全验收须包含同一 worktree 内的后台写进程、祖先目录替换、读/写/目录遍历与生命周期边界；单一 worker lease、工具调用串行化、路径预校验或末级 no-follow 都不能独自证明该竞态已消失。本次只冻结验收要求，不预选原生 helper 或新增依赖。

### 十四、人工介入与冲突裁决（Leader 唯一权威）

**核心原则：leader 是唯一裁决者，不做 agent 自动共识。** agent 可以给出专业反馈、可以"顶嘴"提出异议，但最终决策权始终在人。这既是产品设定（用户是团队 leader），也是对《Don't Build Multi-Agents》"决策不一致"批评的正面回答——用单一权威兜底，避免 agent 互相扯皮或达成错误共识。

**三类人工介入。** 借 Harness 的事件溯源会话日志（天然 checkpoint）+ turn-stopping/inbox steering（安全点打断与注入）实现。其一是**被动卡点**：Reviewer 通过后的 D16 终审确认（`approve_completion` / `request_changes`）、迭代超限或角色主动升级时的兜底决策。其二是**主动指挥**（承接第十节群聊）：leader 随时在群里发指令——指派、追问、插入新需求/新决策、否决/批准、调优先级、拉小群或发起角色离职；各动作严格按 D9 的 Phase 5/6/7/8/9 边界逐步解锁，Phase 7 离职只做目标角色 drain，只有需要全局重规划/重跑的动作在 Phase 9 进入完整安全点抢占。其三是**冲突裁决**：对 agent 之间或 agent 与既有决策之间的分歧拍板。完整形态以"（配合式）暂停并保存完整状态 → 人给指令 → 从断点 resume"的统一机制落地。

**[2026-09-03 架构决策更新] D4 恢复协议与阶段边界。** Phase 8 的 gate 生产者只产生瞬态请求；当前单任务到达已提交的 `step/end` 安全边界后，生命周期服务先 flush 项目/任务命名空间下的 Harness session JSONL，全部成功后才在同任务串行区一次持久化带稳定 `gateId` 与 opaque `safePointRefs` 的完整活动 gate，禁止写入缺 checkpoint 的半成品。随后销毁可执行 composition/Harness context（Harness 当前是进程内 context，不虚称子进程），保留 `TaskState`、worktree 与持久 session，且不走终态产物归档。Leader 裁决继续经 `POST /api/messages`，稳定 `msgId=actionId` 必须绑定当前 `gateId`；同一 Task State commit 追加含 `{gateId,option,argument?,safePointRefs}` resolution receipt 的规范裁决消息、应用原因特定状态变更并清除活动 gate。随后从 receipt + 持久 State/worktree 新建 composition，在全新 Harness context 中加载 source session，截取到已完成 turn boundary 的合法前缀，并经公开 Agent factory 以新 sessionId、seed 与 `parentSession/seedLength` lineage 原子创建 child Agent；D1 注入最新角色投影后继续编排。不得直接调用只生成 live child Session、却无法通过公开 API 再原子绑定 Agent 的 `ctx.sessions.fork()`。任一 gate/action/checkpoint 冲突、会话缺失、未 flush 或非安全 boundary 都 fail-closed；裁决前以 active gate、裁决后以 resolution receipt 保留恢复锚点，fork 成功前 run 始终为 `needs_attention`。Phase 8 只释放单实例本地运行注册表的容量；Phase 9 才将该 suspend/resolve/resume 生命周期接入 `GlobalScheduler` 槽位与多 worker 全局配合式抢占。

**[2026-09-03 架构决策更新] D4 部分失败与身份校验补充。** 活动 gate 可见不等于旧 composition 已完成 suspend；同一 task 的 resolve/resume 必须与 suspend 收尾线性化，若裁决先提交，resume 必须等待旧 run 完全停稳后再重读持久 State，禁止因旧 run 仍标记 running 而丢弃恢复。完整 gate 已提交后的 Executor/catalog/Git/沙箱释放失败不是任务终态失败：必须保留 `needs_attention`、checkpoint/worktree 与恢复锚点，禁止归档；重试从持久事实继续。稳定 actionId 是单一语义标识：已持久化为 gate resolution 后，只接受同一 resolve intent 的重放，chat/invalid/其他动作复用均冲突。已存在 lineage child 必须同时复核 header 与持久事件的完整 seed 前缀；恢复 worktree 必须证明属于当前 task 的规范 root，跨任务路径一律 fail-closed。跨存储离职 saga 若已提交规范 handoff、但尚无对应完整 gate，重试必须先重新驱动 D4 suspend，再校验并推进，不得把可恢复的部分提交变成永久损坏。

**[2026-09-06 架构决策更新] D4 Phase 9 多 worker 恢复计划。** `safePointRefs` 仍是不解释内容的耐久引用集，但完整 gate 必须与 canonical `WorkerState.safePoint` 一对一交叉验证。Phase 9 的 resolution receipt 在保留 Phase 8 单 worker `resumeSessionId` 兼容读的同时，增加按 `workerId` 稳定排序的 per-worker 恢复计划，每项绑定 `{workerId,sourceSafePointRef,resumeSessionId}`；child id 由 `actionId+workerId` 确定性派生。恢复只重建 gate 打开时属于 cohort 且持久状态仍为 `paused` 的 worker；已自然 `done` 或已 `failed` 的 worker 保留终态，未启动 assignment 保持 `pending`。已存在 child 仍须完整复核 source prefix，且恢复前必须以 WorkerState 绑定校验 scope/assignment/safePoint，不得仅凭 role 或 ref 顺序匹配。

**[2026-09-04 架构决策更新] D14——异议事实、确定性分类与阶段边界。** agent 在已提交的 Step 边界以同一个稳定 `id=msgId` 原子追加结构化 `Objection` 与 `type='objection'` Message；`objections` 是 append-only 事实集，不在原记录上改 `status`，未决视图由异议事实与后续规范 Leader 裁决消息读时派生。异议目标使用带种类的引用 `{kind:'decision'|'requirement',id}`，不得以无命名空间字符串混指两类事实。L1 `classifyObjection(draft, decisionLedger, requirements)` 不用关键词或另一次 LLM 调用猜语义：上游 Coordinator 只在有明确矛盾证据时声明 `claim='contradiction'`；函数验证引用存在，且 decision 仍是未被 supersede 的当前项，然后分类为 blocking。一般改进建议及语义不确定项声明 `claim='concern'` 并分类为 advisory；未知、错种类或已失效引用属于生产者错误，明确拒绝，不得伪装成 advisory。任务 8.2 只负责结构化记录、分类与分轨：advisory 提交后继续；blocking 提交后以 `reason='blocking_objection:<id>'`、`options=['accept_objection','reject_objection']` 交 D4 生命周期进入持久 gate。任务 8.3 再定稿并实现该 reason 的 Leader 裁决、最高权威 decisionLedger 写回及未决视图闭合；8.2 不得用一个尚无 resolver 的临时旁路清 gate，也不得提前实现 Phase 9 多 worker 广播抢占。

**[2026-09-04 架构决策更新] D14——Leader 裁决与控制事实闭合。** 每次 objection 裁决必须在一次 Task State commit 中追加规范 Leader 消息和确定性 `authority='leader'` 的 resolution Decision；该 Decision 以 `id='objection-resolution:'+actionId` 为身份，携带结构化 `{objectionId,outcome,target?}`，`decision` 固定为 `accept_objection|reject_objection`，`rationale` 取 Leader 必填的自由文本理由，禁止信任浏览器自报 authority/by/关联字段。blocking 仍只经 `/resolve-gate <gateId> <option> <rationale...>` 裁决并随后走 D4 真 Fork resume；accept decision-target 时 resolution Decision 必须 `supersedes=target.id`，accept requirement-target 时同 commit 将该 Requirement 标记 `withdrawnByDecisionId=resolutionDecision.id`，两者都表示撤回冲突控制事实；reject 保留原目标。advisory 不建 gate，由 `/resolve-objection <objectionId> <accept_objection|reject_objection> <rationale...>` 直接裁决，resolution Decision 仅记录 Leader 采纳/忽略意见，不自动撤回 target。未决视图由纯函数从 Objection、规范 Leader 消息、resolution Decision 与 target 后置事实派生；缺失、重复冲突或漂移一律 fail-closed。同 actionId 重放必须复核完整消息、receipt/关联 Decision 及 target effect 后才可返回 applied。Decision 只能 supersede 当前项，禁止从已失效历史项再分叉。旧 Requirement 无 `withdrawnByDecisionId` 视为 active；投影与路由只消费 active requirements。所有角色投影还必须携带经上述交叉校验的结构化 `objectionResolutions` 系统切片，使真 Fork 后的任一接手角色都能看到 Leader outcome/rationale/target，不读取原始群聊。Phase 9 仍负责普通 `/decision`、`/requirement` 变更与多 worker 广播抢占。

**[2026-09-05 架构决策更新] Decision supersedes 作用域。** `supersedes` 只允许指向同一 `topic` 的 current Decision；跨 topic 指针不能表达“替换同一事项”，会同时破坏每 topic 当前项与冲突集合语义，必须在 L1 写入边界 fail-fast。D14 接受 decision-target 异议时，resolution Decision 继承目标 Decision 的 topic，因此仍满足该约束；历史跨 topic fixture 只用于验证旧读侧不丢信息，不再是合法写入样例。

**[2026-09-05 架构决策更新] D16——终审确认不是自动共识。** REVIEWER `approved` 是完成候选事实而非 Leader 裁决；只有绑定该 review 的规范 `completion_confirmation` gate resolution 才能令 `isRequestSatisfied=true`。`approve_completion` 恢复后进入 finalize；`request_changes <rationale...>` 恢复后重开返工并路由 CODER。不得让 REVIEWER、Coordinator 或 Eval 脚本绕过 D9 冒充 Leader，也不得把旧 review 的裁决复用于新一轮候选。

**异议双轨（agent 如何"顶嘴"）。** agent 发现问题时发 `objection` 类型消息，分两轨处理：

- **阻塞型（blocking）**：结构化矛盾声明指向当前有效的 decision 或 requirement（典型：leader 临时改需求，PM 指出它与已定验收标准冲突）。异议事实与群聊消息先原子提交并高亮，再由 D4 在 Phase 8 的回合制单 worker 安全边界持久 suspend，等 leader 拍板后才继续；Phase 9 才对多 worker 广播暂停并等待全部到达安全点。理由：方向性矛盾若不先解决，继续干只会产出废码。
- **建议型（advisory）**：小范围的技术异议（如 Coder 觉得某接口命名不佳、建议换个库）或无法证明与当前控制事实矛盾的意见。此时**工作照常继续**，异议作为不可变事实留在 `objections` 并在群里可见，leader 有空再看、可采纳可忽略，不打断节奏。

Coordinator 负责把语义判断收敛成结构化 `claim` 与目标引用；L1 只做确定性引用校验和分轨。拿不准时上游必须选择 `concern`，从宽按 advisory，避免动辄卡住全队；明确声明 contradiction 却引用未知或已失效事实时 fail-fast，避免损坏事实悄悄进入 State。

**决策台账与权威级别。** `decisionLedger` 每条决策带**权威级别**：leader 决策为最高权威，可覆盖 agent 此前的任何约定；agent 之间的约定为普通级别。下游想推翻某决策时，只能推翻同级或更低级别的；碰到 leader 级决策只能走异议 → 由 leader 自己改。这样"leader 新决策与 PM 旧需求矛盾"就有明确的解法：PM 发 blocking objection → 相关工作暂停 → leader 裁决（改需求或收回新决策）→ 结果以最高权威写回台账 → 全员按新台账 resume。

**卡点粒度。** Phase 8 的被动卡点限定为迭代上限、必需角色不可用、离职无人接任、blocking objection 与 D16 终审确认；普通阶段切换不逐段审批。Phase 9 的新需求/决策/优先级抢占另按安全点协议处理。

### 十五、代码执行与安全

**[2026-09-08 架构决策更新] 执行与文件访问边界。** agent 产出的代码经**沙箱**执行。阶段 0 的 LocalTempSandbox 是真实临时目录/子进程实现，只用于已声明的受信开发测试，不具备容器隔离；Phase 9 生产执行使用 Docker。每个并行 worker 的 Git linked worktree 与 Docker bind mount 使用同一规范目录，集成后再由独立 validation worktree 验证。MCP 暴露文件、Git、测试与命令能力，角色权限和路径作用域必须逐项校验；当前部分文件操作实际经宿主访问 bind mount，不能描述为“全部在容器内”。同目录后台进程与宿主文件调用的竞态按 DEF-004 与详细设计 §11.7 验收，未满足出口条件前不宣称文件边界已全面抗竞态。所有阶段均使用 Harness worker，经受控沙箱接口执行代码。

**[2026-09-01 架构决策更新] 归档产物的独立复验同样属于 Agent 代码执行。** 宿主进程可管理 Git 元数据、持久化 State、复制/归档文件快照，但不得用宿主 Node、shell 或其他运行时直接执行 Agent 生成的源码、测试或脚本。终态 artifact 需要独立验收时，必须把耐久快照复制或只读挂载到一个**新的隔离沙箱/容器**后再执行，以同时证明归档可恢复性与 G7 隔离边界；“宿主 Git”不等于“宿主执行”。

### 十六、技术栈选型（含框架对比结论）

**语言与全栈基线：纯 TypeScript。** 前端（群聊界面）本就是 Web，编码 agent 生态（Harness、opencode、Claude Code、Codex CLI、多数 MCP server）也以 TS/Node 为主，纯 TS 让前后端 + agent 运行时统一成一套工具链，对单人长期打磨的作品集项目省心；Node 事件循环也天然适配"多 worker 各自长跑、到边界让出"的并发模型。

**薄 agent 内循环：DeepSeek Harness。** 复用它的可替换 agent loop（默认 `ReactLoopAgent`）、Turn/Step 两层模型、工具三段流水线、事件溯源会话日志（`deriveMessages()` 从日志投影历史、从不单独存储——正好落实我们"共享黑板 + 角色投影"的上下文纪律）、以及 fork/resume/replay。我们通过它的扩展点接入自己的逻辑：`agent/pre-step`（注入角色投影、拦截本步）、`agent/request`（按角色路由不同模型/推理档位）、`agent/turn-stopping` + inbox 的 `steer`/`inject`（实现配合式抢占——中途注入 leader 新指令，agent 跑到边界重读 inbox 再开一步）。

**编排与并发：自研轻量层（TypeScript）。** 不上重量级编排框架（对比：LangGraph.js/Mastra 虽 2026 已生产可用，但我们的编排图只有 4 个通用节点、角色是数据不进图，且 Harness 已自带事件溯源/resume/inbox，再叠一个重框架只会功能重叠）。自研层负责：4 个通用节点（coordinator/worker/integrate/humanGate）+ coordinator 条件路由、独立 worker 生命周期、配合式抢占的信号广播与安全点、worktree 分配与集成合并（见第十三节）。

工具接入统一走 **MCP（TS SDK）**（git / 文件 / 测试 / 静态检查各封装为 server）。代码执行用 **Docker 沙箱**（dockerode 驱动，运行于用户本机），并行隔离用 **git worktree**（simple-git）。模型由用户逐 Agent 配置兼容 OpenAI API 服务的 Base URL、API Key 与模型名（10.3，详见 §21）；规划/评审用强推理、编码用代码专精模型仅为选型建议，经 Harness `agent/request` 扩展点执行用户配置。前端做**群聊式界面**（消息流 + @指令 + 私聊/小群会话 + 并行进度 + 异议高亮 + 产出/trace 侧栏），用 **Next.js/React + SSE + HTTP POST**（[2026-08-24 选型同步]取代原 WebSocket/SSE，详见《技术选型文档》§9.2）；可观测直接从 Harness 的事件流派生 trace + 结构化日志。

**[2026-09-04 架构决策更新] D15——Trace 可观测边界。** Trace 只从当前任务官方 Harness JSONL session 中经官方格式检查、再由 Trace 读侧完成跨事件生命周期校验的事件读时派生，不复制进 `AppState`、Message、MessageBus 或另一份日志。服务端只输出角色、session lineage、turn/step 边界、时间、结束状态，以及工具名/调用状态/错误码；10.2 按下方更新增加同 Step 请求重试的最小白名单；模型输入与输出正文、system prompt、reasoning/chunk、工具 arguments/results、环境变量和文件正文一律不进入 Trace DTO。fork/resume child 通过 `parentSession + seedLength` 关联父 session，只展示 seed 后的 child-native 事件，避免重复历史。Trace 使用独立只读 HTTP GET 快照，运行中有界短轮询、终态最终刷新，不扩张 D6 消息 SSE；响应必须显式报告截断，损坏或跨 scope 日志 fail-closed。Phase 8 只展示顺序 worker 时间线，Phase 9 再扩展并行泳道。

**[2026-09-08 架构决策更新] D2 统一执行路线：** 所有角色使用基于 DeepSeek Harness 的自研 Agent 与 HarnessExecutor；取消外部编码 agent 接入及薄/厚切换。复用 Harness 的官方 loop、会话持久化、压缩与扩展点，自研角色、投影、轻编排、并发/抢占和协作控制；完整决策见 §21。

**[2026-09-08 架构决策更新] 10.2 重试可观测性。** 复用官方 `llm/retry`/`llm/retry-started` 事件，读时派生同一 Step 内的有限重试列表。`retryId` 标识重试链，`retryId+retry` 才标识一次等待；started 事件仅证明退避完成，不证明新请求已发送或已恢复。状态与精确 DTO 见详细设计 §6.1，仍禁止原始错误正文与请求/模型内容流入 Trace，不新建日志来源或 Trace SSE。10.2 已实现该 DTO 与桌面/移动端任务状态抽屉展示；实测证据见 `docs/evals/phase10-resilience-evidence.md`。

### 十七、分阶段实施路线（按产品打磨节奏）

**总原则：先回合制跑稳全链路，再升级真并行。** 早期用"单 worker 顺序执行"退化实现，把状态/上下文/通信/裁决验稳，避免一上来就扛并发复杂度。

**阶段 0 · 骨架**：搭 TS 工程 + Harness 单 agent 跑通，[2026-08-24 架构决策更新：Phase 0 采纳三角色闭环（对齐《开发计划安排》）]自研轻编排仅 Coordinator + Coder + Tester 三个角色跑最简单任务（Coder 写码 → Tester 跑测 → 失败回 Coder），验证 State 传递、worker 节点与 Harness loop 接入。底层预留 worker 抽象接口（初期退化为单 worker 顺序执行）。[2026-08-23 架构决策更新] 产出：最小闭环 demo（基于本地临时目录，不依赖容器与真实 Git 分支）。

**阶段 1 · 沙箱与工具**：接 Docker 沙箱 + 核心 MCP 工具（文件/运行命令/git），Coder 能真正写代码进沙箱并执行。产出：agent 能产出并运行代码。

**阶段 2 · 完整角色与回环**：补齐 PM / Architect / Tester / Reviewer，实现 coding↔testing↔review 回环与迭代上限。角色从一开始就用**数据驱动的注册表 + 通用 worker 节点 + HarnessExecutor**实现（承接阶段 7 的热插拔与阶段 9 的并行协作）。产出：完整协作闭环。

**阶段 3 · 上下文工程**：实现结构化交接包、角色投影视图、决策台账（含权威级别），把"上下文不随对话变长而崩"的地基打牢。产出：稳定的上下文机制。

**阶段 4 · 自适应编排**：实现复杂度路由 + 反馈式升级，让参与规模随任务自然伸缩。产出：对简单任务快、对复杂任务稳的编排。

**阶段 5 · 群聊界面（MVP）**：做群聊式界面（agent 成员实时消息流 + leader @指令 + 产出/trace 侧栏），落地"展示层与内部上下文双层分离"；消息先写任务 State 的 JSON 快照、再经 MessageBus→SSE 推送展示信封，SSE 建连必须在持久快照与实时尾流之间无缝衔接；阶段内只支持带 `projectId/taskId` 作用域的固定 `main` 群，并只承诺受信任边界内的单实例自托管运行；按 D9 接通服务端解释、原子持久化且可验证生效的 leader `@ROLE` 定向激活，完整 interrupt/resume 留阶段 9。产出：可演示且刷新后可恢复的群聊协作产品雏形。

**阶段 6 · 多形态通信 + Eval 骨架**：在阶段 5 已定稿的消息提交/投递端口之上，实现可持久恢复的项目级 Channel 注册表——一个全员 main 群 + 可动态新建且绑定任务的 sub 群（"私聊/小群"，participants 自动含 leader），带 `threadId/topic/createdBy` 生命周期元数据；增加 participants 路由、可从持久真相重建的角色 inbox、agent/leader 幂等发起与关闭 sub 群，以及关闭后的结论冒泡，不改写 MessageBus 的 State 所有权。Channel 生命周期按项目串行，Channel 事实先提交、D6 消息后补齐；participants 按集合标准化。与此同时按 D11 定稿统一 Eval 任务/结果契约、可重复运行器与 Phase 0–6 基线任务。产出：像真实团队一样通信的群聊 + 可增量演进的工程 Eval 地基。

**阶段 7 · 角色热插拔**：实现 leader 招募/移除角色、离职强制交接文档、新人入职读交接接手、责任转移与护栏（Coordinator 不可移除、`departing` 阻断新工作、当前 Step 安全排空后再交接）。产出：可增删成员的"活团队"。

**阶段 8 · 人工卡点与冲突裁决**：human-in-the-loop 卡点、checkpoint 续跑、异议双轨（阻塞/建议）、决策权威级别、结构化 trace 面板。产出：可控、可裁决、可观测的系统。

**阶段 9 · 真并行升级**：把退化的单 worker 顺序执行升级为**独立异步 worker 真并行** + 配合式抢占 + worktree 隔离 + 集成检查点；前端呈现"多人同时干活"。产出：真正并行的团队协作。

**阶段 10 · 基于 Harness 的产品化打磨与最终 Benchmark**：统一沿用自研 Harness Agent，完成错误恢复、模型调优、界面细节与体验、本地安装与一键启动；经外部评测 adapter 复用成熟 Coding Agent Benchmark 的任务、环境与 Outcome Grader，完成系统变体重复对照、方差/失败分类和可审计报告，再据实写 README 与产品介绍。产出：可直接演示且有工程证据的完整产品。**[2026-09-08 架构决策更新]** 取消原任务 10.1 外部执行器接入，编号不复用；其余 Phase 10 任务编号保持不变，活动依赖图见 `task-status.json`。评测 adapter 负责任务与判定适配，不是产品外部 Agent 执行器。

每阶段结束继续以确定性集成测试与 G5 真实链路作为阻断门禁；自阶段 6 起并行维护一组固定 Eval 任务，逐阶段追加 Channel、热插拔、humanGate、抢占与真并行场景。Eval 的模型运行允许方差并输出结构化结果，不能用一次跑分替代门禁或宣称统计结论。

### 十八、简历/面试视角（把产品讲出深度）

虽然定位是纯产品，但它作为简历项目仍有强讲点：**编排层**="能手写多 agent 状态流转与回环控制"；**真并行 + 配合式抢占**="知道 LLM 不能硬中断，用协作式抢占 + 安全点 + checkpoint 做到'改主意后全员响应新计划'，并用 git worktree 隔离并行、集成检查点合并，兼顾提速与一致"；**上下文工程**="知道多 agent 头号病灶是上下文割裂，并用共享黑板 + 角色投影 + 结构化交接把它治住，保证产品不随对话变长而崩"；**自适应编排**="不盲从多 agent，让协作规模随任务复杂度伸缩"；**群聊 + 多形态通信**="把人机协作做成可指挥的控制面，agent 能广播/私聊/拉小群像真实团队，同时用展示层/上下文层双层分离保证群聊不污染 agent 内部上下文"；**Leader 唯一裁决 + 异议双轨**="用单一权威兜底决策不一致，正面回应《Don't Build Multi-Agents》，agent 能顶嘴但阻塞/建议分轨、最终由人拍板"；**角色热插拔**="把 agent 团队做成可编辑的活组织——角色是数据不是代码（注册表 + 通用 worker 节点），离职强制交接、新人入职读交接接手"；**Harness 复用与自研边界**="复用单 agent loop、会话与压缩，自研角色投影、编排和协作控制，所有角色遵守同一执行契约"；**工程 Eval**="不靠架构自述证明效果，复用成熟任务评最终产物、自建协作语义 Grader 验证投影/抢占/Leader/并行，并报告成功率、成本、时延与方差"；**沙箱安全**="考虑了 agent 执行代码的隔离"；**MCP 工具层**="用业界标准协议解耦"。

高频追问需提前备答（开发过程中就记录，别临时编）：为何选纯 TS 全栈、为何复用 DeepSeek Harness 当薄 agent 内循环、为何不上 LangGraph.js/Mastra 而自研轻编排；群聊会不会让上下文爆炸、你怎么防（双层分离，且 Harness 的 `deriveMessages` 从事件流投影天然契合）；私聊/小群的上下文怎么隔离与回流；LLM 不能硬中断你怎么做抢占（Harness 的 turn-stopping + inbox steering + 安全点）；并行 worker 的状态怎么保证一致；leader 决策和 PM 需求矛盾时系统怎么走；自适应误分类怎么兜底；如何防死循环和控成本；哪些自己写、哪些复用 Harness，以及如何通过其扩展点保持执行可控。

### 十九、主要风险与应对

**群聊退化成全量广播（本项目最大的技术坑）**：严格执行"通道决定可见性、投影决定消费"的双层分离，agent 永不直接吃群里的原始消息流。**并行写乱共享状态**：一切写走 reducer + 字段级合并语义 + 代码以 worktree 为准 State 只存引用。**抢占延迟与撕裂**：配合式抢占接受秒级"到安全点"延迟以换一致性，绝不硬杀 LLM 造成半截状态。**死循环/不收敛**：`iterationCount` 硬上限 + 超限人工兜底。**沙箱安全**：严格网络/资源限制，文件限工作目录，不执行危险脚本。**中途删角色留下孤儿职责**：离职走"先暂停 → 强制交接文档 → 指定接手/招替补 → 才停用"的流程，无人接手则标记空缺并升级人工，绝不静默丢责任；Coordinator 不可删。**决策不一致/扯皮**：leader 唯一裁决 + 异议双轨 + 决策权威级别，不做 agent 自动共识。**成本失控**：分角色用不同档位模型、长上下文压缩、并行度上限。**框架锁定**：工具走 MCP、并发与业务逻辑与框架 API 解耦。**范围膨胀（长期打磨最大的坑）**：严格按阶段推进、先回合制后并行，每阶段有可演示产出才进下一阶段，避免无限加功能却始终不能演示。

### 二十、项目与多租户层（单用户 · 多项目隔离）

**为什么需要这一层。** 前面十九节都在讲"一个任务如何被一个 agent 团队协作完成"，但真实使用中，同一个用户（leader）往往**同时在推进多个项目**——上午调项目 A 的后端、下午起个项目 B 的原型。这两个项目的团队、代码库、沉淀的约定、群聊历史必须**互不串味**：项目 A 的架构决策不该污染项目 B 的 agent 上下文，项目 B 的实验代码也不该被 A 的 worker 看到。所以在"任务"之上再抽出一层**项目（Project）**作为长期存在的租户边界。层级关系是：**项目（Project）⊃ 任务（AppState）⊃ Worker**——项目是持久的世界，任务是项目里的一次协作，worker 是任务里的一个执行体。**注意与第三节的区分：这里做的是"单用户下的多项目隔离"，不是"账号级多租户/权限/计费"（那才是明确不做的）。**

**隔离模型：独立世界 + 全局调度器。** 每个项目是一个**自包含的 ProjectRuntime**——拥有各自独立的编排器、沙箱根目录、角色注册表、知识库、群聊集合、成本账本，彼此**默认全隔离**（互不可见）。项目之上只有一个很薄的**全局调度器（GlobalScheduler）**，它不介入任何项目内部逻辑，只做两件全局的事：其一，**并行配额分配**——所有项目共享一个全局并行上限（默认 3 个 worker 同时跑），通过 D17 异步 lease 与按项目轮转队列防止繁忙项目长期饿死其他项目；容量不足时项目排队，不承诺不可能实现的“每个活跃项目同时保底 1”。项目卡在 humanGate 时的 suspend/resolve/resume 先在 Phase 8 由单实例本地任务运行注册表落地，释放可执行 composition 占用的本地容量；Phase 9 再把同一生命周期与全局 lease 池对接。其二，**成本统一核算**——各项目的 token/费用汇总到全局账本，便于 leader 总览。这样"多项目"不是把系统改复杂，而是"多个独立世界 + 一个调度总管"。

**多任务但初期退化单任务。** 项目内**允许多个任务并存**（`activeTaskIds`），但初期**退化为单任务**——一个项目同时只跑一个任务，把复杂度后置。为此 `AppState` 从"全局唯一状态"降级为**任务级状态**，并带一个 `projectId` 回指所属项目；跨任务存在的 roster、Channel 与知识（约定、架构、术语、决策）不放在 `AppState`，分别归项目级协作快照与知识库。

**[2026-09-02 架构决策更新]通信与团队所有权随层级对齐。** Channel 与 roster 都是项目团队的长期协作事实，因此只存在于 `ProjectCollaborationSnapshot`；任务只在 `AppState.messages` 保存本任务产生的消息事实。传输层用 `projectId/taskId` 绑定两者：main 是项目级唯一大群，sub 在项目注册表中必须绑定创建它的 `taskId`。局部上下文引用使用 `{taskId,msgId}` 而非裸 `msgId`，避免跨任务歧义；角色 inbox 从协作快照与任务消息派生，不持有第二份事实。D12 要求 roster 与 main participants 同 revision 原子变化，消除两个项目级文件之间的短暂非法状态。

**团队知识库（两层结构）。** 每个项目有自己的知识库，分两层，对应"要不要长期喂给 agent"：

- **精炼层（refined，小、注入投影）**：项目的稳定共识——编码约定、架构总览、术语表、代码地图（文件→职责）、长期决策台账、角色默认配置。它很小，**随角色投影一起注入**每个 worker 的上下文，让新任务/新 agent 一上来就"懂这个项目的规矩"，无需重新摸索。
- **归档层（archive，大、按需检索）**：历史任务摘要、完整群聊消息、旧补丁等。它很大，**不进上下文**，只在需要时经 RAG 检索命中片段——呼应第八节"以产物为锚、按需检索"的纪律。

**知识库靠谁维护——Librarian 蒸馏回灌。** 知识库不会自己长出来。引入一个 **Librarian（图书管理员）职责**：在**每个任务收尾**时，把这次任务里产生的、值得沉淀的东西（新确立的约定、被推翻/新增的架构决策、复用性高的代码片段位置）**蒸馏**进精炼层，把原始过程**归档**进归档层。Librarian **默认由 Coordinator 代管**（不单设角色、省编制），但因为角色是数据可热插拔，项目大了可由 leader**按需招募**一个专职 Librarian。这样知识库是"任务跑完自动增厚"的，而非人工维护。

**跨项目：默认拒绝 + 受控导入。** 项目间**默认零共享**（连"项目 A 有个好用的缓存实现"这种事，项目 B 的 agent 也看不到）。确需复用时走**受控导入**流程，而非打通实时引用：leader 显式发起导入 → 把源项目的目标内容（一段约定 / 一份代码 / 一条决策 / 一条知识库条目）**快照拷贝**进目标项目 → 落一条**导入台账（ImportRecord，需 leader 批准、留审计痕迹）**。导入的是**副本不是链接**——源项目此后怎么改都不影响已导入的副本，避免跨项目的隐式耦合。这既满足"想复用"的现实需求，又守住"默认隔离"的边界。

**Leader 收件箱：混合式（存储分项目 + 呈现全局）。** 多项目并行时，leader 需要处理各项目冒上来的 humanGate（卡点/裁决/升级）。采用**混合式**：**存储上分项目**——每个项目维护自己的 humanGate 队列，建议型异议(advisory)只留在项目内、不打扰全局；**呈现上全局聚合**——一个**全局收件箱（GlobalInbox）只把各项目的阻塞型(blocking)待办**汇总到一处，让 leader 一眼看到"哪些项目正卡着等我"。点进某条待办即**带 leader 进入该项目的上下文**去处理。与 D4 配合时，卡点任务的可执行 composition 已被释放，而持久 State/session/worktree 保留供 Leader 裁决后重建并 Fork，从而实现"leader 不必盯着单个项目、被真正需要决策的事牵引着走"的多项目指挥体验。

**产品与讲点价值。** "我的产品不是只能做一个项目的玩具——它是一个能同时托管多个独立项目世界的工作台：每个项目有自己会随任务自动增厚的团队知识库，项目间默认隔离、要复用得走带审计的受控导入，而 leader 用一个全局收件箱统一指挥、被真正需要拍板的事牵引。"这把"多 agent 协作"从单任务演示升级为**可长期驻留使用的产品**。

**[2026-09-02 架构决策更新]D11 fail-closed 与证据生命周期补充：** Eval 的总状态必须由结构化 check 推导，不能由调用方自报：存在 execution/cleanup failure、任一 `fail`，或任何声明的 Outcome/Process/Safety check 为 `unknown` 时均不得记为通过；只有确实无法从生产端口取得的 Efficiency 指标可保留 `unknown`。每个 `pass` 必须来自实际 State、Harness/工具结果、文件/命令输出或经过类型判别的预期错误，禁止硬编码未观测事实。`maxIterations` 对应实际编排轮次 `iterations`，`repairIterations` 继续独立计量返工。Runner 先原子保存 `provisional` 结果，再执行已注册清理，最后以清理证据原子定稿 `final` 结果；崩溃遗留的 provisional 不得计入基线通过。实际执行与记录的模型/环境配置必须引用同一冻结配置；未映射任务、未完整通过运行时校验的 schema、非规范或经符号链接转向的 eval root 均 fail-fast。专用真实模型 Eval 命令缺凭据时明确失败，当前任务应执行的默认真实模型回归同样不得 skip；已配置凭据保留，缺凭据或环境阻断记录为未完成，遵循 AGENTS.md §3.1.3 的 Leader 测试约定。
