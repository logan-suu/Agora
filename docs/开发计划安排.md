**版本**：v1.6

## 1. 总览

### 1.1 开发原则

1. **先跑通，再优化**：每个阶段优先交付可演示的最小闭环，而非完美实现。
2. **接口先行**：模块间依赖通过接口定义解耦，允许并行开发和替换实现。
3. **AI-Native 开发**：充分利用 Cursor/Windsurf 的 Composer 能力，将详细设计文档作为上下文输入，让 AI 生成 90% 的样板代码。
4. **每阶段可演示**：每个阶段结束时必须有可运行/可演示的产出，便于秋招展示进度。
5. **风险前置**：最不确定的技术点（Harness 接入、投影覆写）在 Phase 0 优先验证。
6. **评测随能力演进**：确定性测试/G5 继续作为门禁；自 Phase 6 起维护渐进式工程 Eval，成熟 Benchmark 复用任务与结果判定，Agora 只补协作语义 Grader，未实测数据不得对外宣称。

### 7.3 具体任务

**复杂度评估（`packages/core/orchestration/complexity.ts`）** ：
- 输入：`goal`、文件数估算、依赖数
- 输出：`{ tier: 0|1|2, signals: Record<string, unknown> }`
- Tier 0：单文件/单函数 → 直接 CODER
- Tier 1：小型多文件 → PM(条件)→ARCH→CODER↔TESTER
- Tier 2：复杂多模块 → 全队 + 多子任务拆分（Phase 4 顺序调度；真并行 Phase 9）

**Coordinator 路由升级**：
- 读 `complexity.tier` 决定起始拓扑
- 每轮回到 Coordinator 检查升级条件：
  - 测试连续失败 N 轮且未加 REVIEWER → 加 REVIEWER
  - REVIEWER 指出设计问题 → 拉 ARCHITECT
  - iterationCount >= 8 → humanGate

**Coordinator 双层进度台账**：
- 外层 `task`：确定性维护 confirmed facts / hypotheses / role plan；内层 `progress`：维护 satisfied/loop/progress/next speaker/instruction
- Ledger 作为严格校验的结构化 Coordinator message append-only 持久化，不增加 AppState/Mutation 字段
- worker 仅投影 confirmed facts、本角色 plan 与当前指令；Coordinator 投影完整台账，禁止纯文本全员广播
- 普通完成只标 `completionCandidate`；`isRequestSatisfied` 归 leader authority，Phase 8 以前不由 LLM/Coordinator 自动置真
- 连续 stall 上限 3，达到上限后 revision++ 并从结构化 State 重建 facts/plan

**4.5 代表性正向场景验收（端到端验证）**：
- 测试用例 1：“实现一个函数”（预期 Tier 0，跳过 PM/ARCH）
- 测试用例 2：“实现一个 REST API 服务”（预期 Tier 2，全队出动）

> [2026-08-31 实测口径校准] Phase 4 的 Tier 2“全队出动”指 PM/ARCHITECT/CODER/TESTER/REVIEWER 全角色拓扑到位、Coordinator 路由与 Ledger 在场，并将多模块拆为多个子任务顺序调度；真并行批调度仍属 Phase 9。4.5 采用确定性真实执行链集成验证：仅脚本化非确定性的外部 LLM 响应，Harness、WorkerRuntime、角色投影、MCP、LocalTempSandbox、Reducer、Coordinator 与 Ledger/handoff 均使用真实实现。

**4.6 Phase 4 出口集成测试**：
- 定位：Phase 4 的累计发布门禁，不重复实现 4.5 的两个完整正向场景；4.5 的通过结果作为“参与规模随任务伸缩”的前置证据

### 9.3 具体任务

**Channel 管理（`packages/comm/channels/`）** ：
- `Channel` 接口：channelId, kind ('main'|'sub'), sub.taskId/threadId/topic/createdBy, participants, closed, sub.bubbledSummaryRef；不持久 localContext 或摘要正文
- 不变量：`'leader' ∈ participants` 恒成立
- 项目内恰有一个 `channelId='main'`，main 恒 `closed=false` 且 participants=当前已启用 roster+leader；sub `channelId` 项目内唯一且必须绑定当前任务
- `ProjectChannelStore`：`.data/projects/{projectId}/channels.json`，幂等 initialize + revision 校验 + 按项目串行 + 原子替换；进程重启可恢复
- Phase 5→6 升级：已有任务 State、缺失 `channels.json` 时惰性补建 main；损坏/非法快照 fail-fast，不自动覆盖
- no-op 语义：普通对象属性顺序不构成 Channel 变更；participants 是集合并标准化为 leader 在前、其余按 enabled roster 顺序，成员顺序不同不触发 revision；Channel 注册表顺序保留

**Channel/Inbox 路由升级（`packages/comm/channels/`）** ：
- `Project.channels` 是 Channel 注册表唯一真相源，`AppState.messages` 继续保存任务级消息事实
- `inboxFor(projectSnapshot, task, role)`：只返回当前任务中、Channel 作用域匹配且该角色为 participant 的 `InboxItem`；保留 `AppState.messages` 顺序，`to` 只标注 direct 优先级
- 提交前校验 Channel 存在/sub task 绑定/发送者 participant/closed；失败时不写 State、不 publish
- MessageBus 接口与“先提交、后投递”顺序不变；事件可唤醒 worker，但 inbox 每次从 Channel 快照 + 任务 State 重建
- `ChannelContextBuilder(projectSnapshot, task, role)` 同样读时派生：按 project/task/participants default-deny，main 只投允许的共享结构化事件，sub 只投群内允许的结构化条目；永不复制 display，未知 payload 只留 ref
- 每个 Channel 的 `{entries,omittedRefs,omittedRefCount}` 共用 4000 字符动态消息预算：较新 entries 保留完整结构化内容，剩余空间按事实顺序保留最近的旧 refs，计数记录全部遗漏；不在 pre-step 调 LLM，不向 Channel 回写消息索引

**Sub 群生命周期**：
- 动作契约：agent 最终回复末尾至多一个严格 `<agora-channel-action>{JSON}</agora-channel-action>`，open 可显式给安全稳定 threadId；Harness 校验/剥离 display 并以 assistant msgId 绑定 actionId 后通过现有 `StepResult.output` 交付，纯控制回复保留审计 Message 并生成非空 display；Leader 使用 `POST /api/messages` 的 `/channel open ROLE[,ROLE...] <topic>` / `/channel close <channelId>`；组合根绑定可信 actor，不修改 Executor/Store/MessageBus 签名
- 创建：稳定 actionId（Leader=msgId）以 taskId 长度前缀派生 `channelId='sub-'+taskId.length+'-'+taskId+'-'+actionId`，缺省 threadId=actionId；participants 自动包含 leader、agent 发起者与请求角色，并按 roster 标准化
- 去重：同 `taskId+threadId` 同 topic/participants 返回既有群，语义不同明确冲突，closed thread 不静默复活
- 通信：群内消息仅 participants 可见
- 发现/UI：`GET /api/channels?projectId&taskId` 按字段白名单只读返回 main + 当前 task sub 元数据（不返回 bubbledSummaryRef 指向的内容或 payload）；UI 初始化/动作完成刷新一次，仅 active run 持续短轮询，刷新错误独立且恢复后清除；可切群，SSE/POST 复用所选 channelId
- 关闭：仅 leader/participant 可置 `closed=true`，main 不可关闭，重复 close 为 no-op；6.2 写 main 生命周期公告，6.3 经 L3 生成器端口复用无工具薄 Harness，从目标 sub 的全部白名单结构化条目生成 conclusion/keyDecisions+rationale/openQuestions/sourceMsgIds；完整 entry 预算内装箱，超大单条用保留 ref 的结构化 fragment，中间输出有界并以每轮输入不超过 4000 字符的批次多轮归并；以稳定 channel-bubble msgId 先写 main，再只在 Channel 写 bubbledSummaryRef

## 16. AI-Native 开发工作流

### 16.1 推荐工具链
- **IDE**：Cursor 或 Windsurf（内置 Composer/Agent 模式）
- **上下文注入**：将 `docs/详细设计方案.md` 和 `docs/系统架构设计文档.md` 作为 Cursor Rules 或 AGENTS.md
- **代码生成**：每次让 AI 生成代码前，明确指定“严格按照 Phase X 的规格实现，不超出范围”

### 16.2 建议的 Cursor Rules（`.cursorrules`）

```markdown
# Agora 项目开发规则

1. 技术栈：TypeScript 5.9+，Node.js 20+，pnpm workspaces
2. 严格遵循 docs/详细设计方案.md 中的接口定义
3. Phase 0 约束：
   - 所有 Executor 统一为薄 Harness
   - Sandbox 使用 LocalTemp（非 Docker）
   - KnowledgeBase 仅读空对象，不写入
   - 全局调度器退化为单任务串行
4. 代码风格：Biome 格式化，Import 自动排序
5. 测试：Vitest 3.x，每个模块需有单元测试
```

### 16.3 每日开发流程
1. 晨会（5 分钟）：确认当前 Phase 的里程碑进度
2. AI 编码（2-3 小时）：将任务拆解为小单元，逐个让 AI 生成
3. 人工审查（1 小时）：检查 AI 生成的代码是否符合设计
4. 集成测试（30 分钟）：运行 Vitest 确保没有破坏已有功能
5. 提交（10 分钟）：commit message 遵循 Conventional Commits


## 17. 检查点：秋招 Demo 准备

在 Phase 5（Week 7）完成后，应准备一份**可用于秋招展示、且与真实执行能力一致的 Demo 录屏**。录屏必须使用任务 5.5 接通后的 Web→编排→消息持久化→SSE 链路；静态种子消息只能作为空状态视觉占位，不得作为执行证据。

**Demo 场景**：
1. 启动单实例自托管系统，在 UI 创建并启动任务：“实现一个带 TTL 的 LRU 缓存类，包含 get/set/delete 方法，并编写单元测试”
2. 观察 Coordinator 从真实 State 评估为 Tier 0，跳过 PM/Architect 并派发 Coder
3. 观察 Coder 的进度消息经 State 持久化后实时出现在 main 群，并展示实际代码产物入口
4. 观察 Tester 执行真实测试；若首次失败，保留一次可解释的 Coder↔Tester 修复回环，否则直接进入下一步
5. 观察 Reviewer 基于真实 diff/测试结果给出通过结论，Coordinator 将任务收尾为 `done`
6. 刷新页面，确认消息、最终状态与归档产物由 JSON State + `.data/.../artifacts/` 恢复，且终态 Harness/Docker 已释放；展示角色头像、消息流、产物引用与任务状态
7. 可补充演示一条有效 `@ROLE` 指派和一条 deferred/rejected 指令，明确 Phase 6/8/9 尚未解锁的边界，不宣称完整抢占、sub 群或 Serverless 后端能力

**真实性门禁**：关键链路必须连续展示浏览器操作、服务端执行与最终产物；不得剪接静态假消息冒充 Agent 实跑，不得以独立编排测试 + 独立 UI 演示替代 Web 触发的同一任务闭环。

**如果时间紧张**：优先完成 Phase 0-5，确保有可演示的 UI + 完整闭环，Phase 6-10 可作为“规划中”在面试中介绍。
